| 항목 | 내용 |

## 0. 세 줄 요약

1. 아홉 저장소 중 `db-schema`를 뺀 8개 전부, 검증계(stg)에는 있고 운영계(main)에는 없는 커밋이 쌓여 있다. 특히 `backend-api-main`은 371커밋(병합 제외 211건)이 밀려 있고, 그 main은 2026-08-06 시점 형상에 사실상 멈춰 있다.
2. 이 밀린 변경들은 서로 실행 순서로 얽혀 있다 — `skix-security`의 회원 식별 응답은 `backend-api-main` 신버전이 먼저 떠 있어야 정상 동작하고, `skix-streaming`·`frontend-web-backoffice`도 마찬가지로 backend 신버전에 의존한다. 그래서 저장소별로 따로따로 올릴 수 없고 **정해진 순서로 묶어 한 번에 운영 릴리스**해야 한다.
3. 순서·선행조건·트랙별 게이트는 이미 정리돼 있었다(2026-09-14 작성). 이 문서는 그 내용을 오늘 날짜 Git 실측으로 다시 확인하고, 실행 가능한 런북 형태로 옮긴 것이다. 남은 것은 §8의 결정 사항과 배포일 확정뿐이다.

## 1. 배경

### 1-1. 용어

| 용어 | 뜻 |
|---|---|
| **dev / stg / main(prd)** | 이 회사의 3단계 브랜치·환경. `dev`(개발계)에서 시작해 `stg`(검증계)로, 검증되면 `main`(운영계)으로 승격(merge)한다 |
| **승격(promotion)** | `stg`를 `main`에 머지하고 그 결과를 운영 환경에 배포하는 것. 이 문서의 핵심 동사 |
| **task-definition** | ECS(컨테이너 오케스트레이션)가 컨테이너를 띄울 때 쓰는 설정 묶음(이미지·환경변수·시크릿). 저장소의 `deploy/task-definition-<env>.json`에 정의돼 있다 |
| **다크 배포 / 플래그 OFF** | 코드는 올리되 기능 플래그를 꺼 둔 상태로 배포하는 것. 동작이 바뀌지 않으므로 순서상 먼저 올려도 안전하다 |
| **check-member** | `backend-api-main`이 다른 서버(security·streaming 등)에게 "이 사람이 이 기기의 멤버인가"를 답해주는 내부 API. 여러 트랙이 이 응답 형태 변경에 의존한다 |
| **fail-closed** | 의존하는 API 호출이 실패하면 요청 자체를 실패시키는 방어적 설계. 배포 순서를 어기면 이 성질 때문에 즉시 장애가 난다 |
| **선별 반영** | `stg`(또는 `dev`) 전체를 그대로 승격하지 않고, 특정 커밋만 의도적으로 제외한 채 승격하는 것. `skix-security`가 이 상태다(§4) |
| **백필(backfill)** | 이미 있는 데이터에 새 컬럼·테이블 값을 채워 넣는 일회성 배치 작업 |
| **재키잉(rekeying)** | 기존 데이터의 소유자 식별값(키)을 새 규칙으로 바꿔 다시 쓰는 작업. `skix-medcare` 소유자 키 통합 트랙에서 쓴다 |
| **B015** | OASYS(SK매직 계약·고객 시스템)가 하루 1회 계약정보를 밀어주는 연동 인터페이스. `backend-api-main`의 `feature/Oasys_B015` 작업 |
| **token-pii 트랙** | Cognito(사용자 인증) 토큰에서 전화번호 등 개인정보 클레임 의존을 걷어내고 `sub`(고유 식별자) 단독으로 사용자를 식별하도록 바꾸는 여러 저장소 공통 작업 |

### 1-2. 왜 여러 작업이 한 번의 운영 릴리스로 묶이는가

지난 반 년간 진행한 십여 개의 개별 작업이 전부 `stg`까지는 갔는데 `main`에는 하나도 못 올라갔다. 이유는 코드 품질이 아니라 **저장소 간 실행 순서 의존성**이다. 대표적으로:

- `skix-security`의 회원 식별 로직(`check-member` 응답에서 `loginId`를 해석해 담는 것)은 `backend-api-main`이 먼저 그 값을 채워 보내야 동작한다. 순서를 바꾸면 Cognito 로그인 경로 전체가 400으로 죽는다.
- `skix-streaming`의 `DeviceControlService`는 `check-member` 응답에 `loginId`가 없으면 즉시 실패(fail-fast)하도록 짜여 있다. `backend-api-main` 신버전 없이 올리면 라이브뷰·S1 출동이 전건 실패한다.
- `skix-streaming-signal`은 `skix-streaming`의 토큰 검증 API를 부르므로 streaming이 먼저다.
- `frontend-web-backoffice`(관제 화면)는 `backend-api-main`이 새로 만든 URL을 호출한다.
- `skix-openapi`의 파트너 신원 정규화 플래그는 `backend-api-main`·benjamin DB의 `user_accounts` 백필이 끝나야 켤 수 있다.
- `skix-medcare`의 소유자 키 통합·PHR 오픈은 `backend-api-main`의 사용자 식별 응답 형태(token-pii 트랙)를 전제로 설계돼 있다.
- `skix-security`의 `main`이 지금 2커밋을 의도적으로 뺀 "선별 반영" 상태인 것 자체가, `backend-api-main`이 아직 운영에 안 나가서 생긴 상태다(§4).

즉 어느 한 저장소만 먼저 승격하면 위 의존관계 중 하나가 끊겨 실서비스 장애로 이어진다. 그래서 배포는 "저장소 단위"가 아니라 "순서가 고정된 하나의 릴리스 묶음"으로 다뤄야 한다.

### 1-3. 이 문서가 다루는 범위

- 오늘 기준 저장소별 미승격 커밋 수와 9/14 대비 변화(§2)
- `backend-api-main`이 왜 8/6 형상에 멈춰 있는지, 그게 왜 지금은 안전하게 풀리는지(§3)
- `skix-security`의 선별 반영 상태와 이번에 해제해야 하는 이유(§4)
- 이번 릴리스에 묶여 있는 개별 트랙과, 각 트랙이 요구하는 운영 게이트를 한곳에 모은 것(§5)
- 운영 배포 순서와 그 이유, 선행조건(§6)
- 실행 가능한 런북 — main 승격부터 배포·백필·재키잉까지(§7)
- 아직 결정되지 않아 배포일을 못 잡는 항목들(§8)

개별 트랙의 API 계약·화면 설계·앱 요청 문구 같은 상세는 이 문서의 범위가 아니다. 이 문서는 "여러 작업이 왜 한 릴리스로 묶이고, 그 순서와 게이트가 무엇인가"만 다룬다.

## 2. 저장소별 검증계→운영계 미승격 현황 (2026-09-22 실측)

### 2-1. 실측 표

측정 명령(각 저장소에서 `git fetch origin` 후 실행):

```bash
git rev-list --count origin/main..origin/stg            # stg에는 있고 main에는 없는 커밋(병합 포함)
git rev-list --no-merges --count origin/main..origin/stg  # 위에서 병합 커밋만 뺀 것 — 실제 내용 변경 개수에 가깝다
git rev-list --count origin/stg..origin/main             # 반대 방향 — main에만 있는 커밋
```

| 저장소 | stg→main 미승격 (전체) | 〃 (병합 제외) | main에만 있는 커밋 (전체) | 〃 (병합 제외, 실내용) | 9/14 대비 |
|---|---:|---:|---:|---:|---|
| `backend-api-main` | **371** | 211 | 0 | 0 | 341 → 371 (**+30**, 9개 저장소 중 유일하게 증가) |
| `skix-security` | 26 | 12 | 14 | 1 | 26 → 26 (변화 없음) |
| `skix-medcare` | 37 | 28 | 14 | 0 | 37 → 37 (변화 없음) |
| `skix-openapi` | 32 | 18 | 26 | 1 | 32 → 32 (변화 없음) |
| `skix-openapi-docs` | 11 | 5 | 6 | 2 | 9/14 조사에는 없던 저장소(이번에 새로 편입) |
| `skix-streaming` | 6 | 4 | 0 | 0 | 6 → 6 (변화 없음) |

**핵심 관찰**: 9/14 이후 8일 동안 `backend-api-main`만 `dev`에서 `stg`로 계속 병합되며 30커밋(병합 포함)이 늘었다(마지막 반영일 2026-09-18). 나머지 7개 저장소는 9/14 이후 `stg` 쪽 변화가 전혀 없다 — 즉 실질적인 병목은 여전히 **"승격을 안 한 것"**이지 "검증계 작업이 안 끝난 것"이 아니다.

### 2-2. "main에만 있는 커밋"이 있는 이유 — 실제로 앞서 있는 게 아니다

표의 "main에만 있는 커밋" 열은 `skix-security`(14)·`skix-medcare`(14)·`skix-openapi`(26)·`skix-openapi-docs`(6)·`frontend-web-backoffice`(1)에서 0이 아니다. main이 실제로 더 진행된 것처럼 보이지만, 병합 커밋을 빼고 보면 대부분 사라진다(security 1, openapi 1, openapi-docs 2, medcare·backoffice는 각 0~1). 즉 대부분은 `dev → stg → main`을 서로 다른 시점에 병합해 온 **병합 이력의 모양 차이**일 뿐, main이 실제로 갖고 있는 고유 내용은 거의 없다.

실측으로 확인한 예외 4건:

| 저장소 | main만의 실제 커밋 | 내용 | 비고 |
|---|---|---|---|
| `skix-security` | `f19e9d7` (2026-08-31) | R047 구독 해지 시 PIN 설정 이력 무효화 | `dev`의 `955ba0a`와 **내용은 같고 해시만 다르다**(cherry-pick으로 먼저 운영 승격 라인에 올린 것). 승격 시 같은 내용이 양쪽에 있는 상태가 되므로 충돌이 나면 "중복 적용"이 아니라 정상 상황으로 보고 내용 기준으로 해소한다 |
| `skix-openapi` | `73236b5` (2026-07-09) | 소개 문서 문구 수정 | 내용 영향 없는 문서 오탈자 수준. 승격 시 자동으로 함께 남는다 |
| `skix-openapi-docs` | `3849247`·`aa2302e` (2026-07-21) | 로그인 후 메인 페이지, og:image 포맷 변경 | 정적 문서 사이트의 오래된 변경. 승격에 지장 없음 |
| `frontend-web-backoffice` | `fd7de620` (2026-09-08) | 로그인 화면에서 외부 사용자에게만 회원가입 버튼 노출 | `hotfix/security-fix` 브랜치를 `stg`를 거치지 않고 `main`에 직접 머지한 것(7줄짜리 소규모 수정). `stg`를 `main`에 머지하면 이 커밋은 그대로 조상으로 남으므로 별도 조치 불필요 |

### 2-3. `db-schema`는 다른 모델이다

`db-schema`는 `dev`/`stg`/`main` 3브랜치 승격 구조가 아니다. `main` 브랜치 하나에 각 환경(`dev.sql`/`stg.sql`/`prod.sql`)의 스키마 덤프와 DDL 변경 이력을 그때그때 기록하는 저장소다. 그래서 "stg에는 있고 main에는 없는 DDL"이라는 개념 자체가 없다 — 어떤 환경에 DDL을 실행하면 그 사실을 같은 저장소의 `main`에 커밋한다.

이번 릴리스가 요구하는 DDL은 이미 대부분 3환경에 선적용돼 있다(2026-09-14 실측 확인): `remote_mapping_session`(관제 원격 맵핑), `oasys_membership_apply_attempt`(OASYS 직접구독 원장), `oasys_order_device_day`(B015), `history_clean_area_result_stat`, `medcare_user_identity`·`kmeta_streams.cheiron_sub`·`SCRAPE_FAILURE_REASON`(medcare 계열), 공통코드 옵션 컬럼(`819d040`, 커밋 메시지 "공통코드 상세 테이블 옵셔02 컬럼 추가" — `backend-api-main`의 날씨 API 커밋 `0e1380eb`와 짝) 등. 남은 것은 애플리케이션 코드 승격뿐이며, **배포 직전에 §7-0에서 실물 스키마를 다시 한번 대조**한다.

## 3. `backend-api-main`: main이 8/6 형상에 멈춰 있는 사정

`origin/main`의 HEAD는 `7d9ac170`(2026-09-01)이고, 이 커밋 자체의 메시지가 사정을 그대로 담고 있다(오늘 `git show`로 원문 확인):

```
[revert] hotfix/20260827_oasys_b015 커밋을 main에서 제거 (150ad08b 상태로 복구)

잘못 push된 10개 커밋(3c51da85..76f3f85c)의 변경사항을 되돌립니다.
해당 작업은 hotfix/20260826 브랜치에 보존되어 있습니다.
```

즉 B015(OASYS 계약정보 연동) 관련 커밋 10개가 정식 절차(`dev → stg → main`)를 거치지 않고 **`main`에 직접 잘못 반영됐다가, 되돌려진 것**이다. 되돌린 뒤 `main`의 트리는 그 시점의 병합 지점(`60f0643e`, 2026-08-06)과 바이트 단위로 동일하다 — 그래서 "main이 8/6 형상"이라는 표현이 나온다. 이후 `main → dev` 역머지(`2f0358e8`, 내용 변화 0)를 한 번 했지만 그것도 이력 정리 효과뿐이었다.

**결과적으로 지금 `stg`→`main` 승격(rev-list 371)에는, 되돌려졌던 B015 관련 코드가 정상 경로로 다시 포함돼 있다.** `stg`의 B015 구현은 되돌려진 버전보다 발전된 형태다 — `OasysContractSyncService`가 B015가 보낸 주문번호(`ordNo`)와 조회 전문(R011)의 값을 교차검증하고, `OasysContractRef.isShared()`가 공유 행(대수 2대 이상 또는 임시계약번호 `T202ZEA19458`)인지 판정해 공유 행을 실주문번호로 잘못 덮어쓰는 사고를 차단한다. 오늘 `stg` 코드로 직접 확인했다:

```java
// src/main/java/com/skmagic/api/oasys/model/OasysContractRef.java (origin/stg)
public static final String PROVISIONAL_CONTRACT_NO = "T202ZEA19458";
private static final int SHARED_DEVICE_CNT = 2;
public boolean isShared() {
    return deviceCnt >= SHARED_DEVICE_CNT || PROVISIONAL_CONTRACT_NO.equals(contractNo);
}
```

단위 테스트(`OasysContractRefTest`, `OasysContractSyncServiceTest`)도 `stg`에 존재한다. **따라서 "B015가 운영에 되돌아온다"는 이번 승격의 리스크가 아니라, 오히려 사고 방지 로직이 갖춰진 채로 정식 승격되는 것**이다. 승격 자체를 막을 이유는 없고, 배포 후 실측(§5의 "탈퇴/contract_no" 트랙, `2844154c`)만 확인하면 된다.

**남아 있던 되돌리기 원본은 `hotfix/20260826` 브랜치에 그대로 있다.** 이 브랜치는 참고용으로만 두고, 승격은 반드시 `stg`(더 발전된 버전)에서 한다 — `hotfix/20260826`을 다시 꺼내 쓰면 가드 로직 없이 사고 벡터가 그대로 부활한다.

## 4. `skix-security`: main 선별 반영과 이번에 해제해야 하는 이유

`skix-security`의 `main`은 `dev`(및 `stg`) 전체가 아니라 **2커밋을 의도적으로 뺀 상태**다.

| 제외된 커밋 | 날짜 | 내용 |
|---|---|---|
| `b1b148b` | 2026-08-22 | 토큰에서 `loginId` 클레임 의존을 걷어내고 인가 응답으로 해석(`CallerIdentity` 재설계, `check-member` 응답 신뢰) |
| `cf5f56b` | 2026-08-23 | `check-member` 응답을 아웃바운드 로그에 저장하지 않음(PII 로그 제거) |

**제외 이유는 코드 결함이 아니라 순서 문제였다.** 이 두 커밋은 `backend-api-main`이 `check-member` 응답에 해석된 `loginId`를 실어 보내는 것(`59b359a4`)을 전제로 동작한다. `backend-api-main` 운영 배포보다 `skix-security`가 먼저 이 내용을 반영하면, 응답에 `loginId`가 없어 Cognito 로그인 경로 전체가 죽는다. 그래서 "플랫폼(`backend-api-main`)이 운영에 나갈 때 함께 승격한다"는 조건으로 미뤄 왔다.

**이번 릴리스가 바로 그 조건을 충족하는 시점이다.** §6의 배포 순서에서 `backend-api-main`이 `skix-security` 바로 앞 단계로 이미 예정돼 있다 — 즉 이번에는 두 커밋을 뺄 이유가 없다. **`skix-security`를 승격할 때는 선별 반영을 그만두고 `stg` 전체를 `main`에 머지한다.**

주의할 점 3가지(승격 시 그대로 적용):

1. `main`이 이미 `f19e9d7`(§2-2의 PIN 이력 무효화, `dev`의 `955ba0a`와 내용 동일·해시만 다름)를 갖고 있으므로, `stg`를 통째로 머지하면 같은 내용이 양쪽 이력에 존재하는 상태가 된다. 충돌이 나면 "중복 적용"이 아니라 정상 상황이니 **내용 기준으로 해소**한다.
2. 검증: 머지 뒤 `git merge-base --is-ancestor b1b148b origin/main`과 `cf5f56b`에 대한 같은 명령이 **성공**해야 한다(과거에는 실패가 정상이었지만 이번에는 포함시키는 것이 목적이므로 성공이 맞다).
3. 이 조합(선별 반영 해제 + `backend-api-main` 신버전)은 지금까지 한 번도 함께 빌드된 적이 없다. **push 전 `./gradlew clean test` 필수.**

## 5. 트랙별 개요와 운영 게이트

이번 릴리스에 묶여 있는 트랙들이다. 각 트랙의 설계 배경은 요약만 두고, "운영에 올리기 전에 무엇이 확인돼야 하는가"를 게이트 항목 그대로 옮겨 담았다.

### 5-1. Cognito sub 통합·토큰 PII 제거 (token-pii)

관련 저장소: `backend-api-main`·`skix-medcare`·`skix-security`·`skix-streaming`·`skix-streaming-signal`. Cognito 토큰에서 전화번호 등 개인정보 클레임 의존을 걷어내고 `sub` 단독으로 사용자를 식별하도록 바꾸는 작업. 개발계·검증계는 S0(데이터 사전 점검)~S3(소비자 3개 배포)까지 완주했고, 운영계는 전 단계 미실행이다.

| 단계 | 내용 |
|---|---|
| S0 | 선점·중복·UNIQUE 인덱스 사전 점검 |
| S1 | `backend-api-main` 배포 |
| S2 | `user_accounts` 백필 (benjamin DB) |
| S3 | 소비자 3개(medcare·security·streaming) 배포 |
| S4 | 로그 관찰 |
| S5 | 앱 반영(스토어 릴리스) |
| S6 | Cognito 읽기 속성 축소 |
| S7 | Cognito 속성 파기(비가역) |

**운영 게이트**
- S0~S3 배포 전: S0 사전 점검 4종 결과가 `0·0·0·1 이상`일 것(하나라도 어긋나면 배포 금지), 검증계가 S4까지 통과해 있을 것, RDS 스냅샷 확보.
- S6(읽기 속성 축소) 전: `SUB_FALLBACK layer=claim` 로그가 그 환경에서 7일간 0건(운영계 기준. dev/stg는 기간 대신 주요 경로 실호출 확인으로 대체), 앱 전환 버전이 보급됨(운영계는 스토어 보급률 확인, 실측상 30일 내 96% 도달), **iOS 소셜 로그인이 `phone_number` 의존을 끊은 버전인지 확인 — 빠뜨리면 카카오·구글·애플 로그인이 한꺼번에 죽는다**, 파기 대상 속성의 서버 소비가 0건(코드상 백오피스 목록 조회를 DB 기반으로 바꿔 충족됨 — 그 커밋이 배포됐는지만 확인), `skix-streaming`의 sub 전환이 그 환경에 배포됐는지.
- S7(파기) 전: S6 이후 확인 5종 통과.

### 5-2. 관제 원격 맵핑

관련 저장소: `backend-api-main`·`db-schema`(DDL). `backend-api-main`의 `main`에는 원격 맵핑 코드가 0건.

**운영 게이트**: 배포 전 차단 이슈(P0) 2건 확인, `backend-api-main` main 승격, 기기 3종(DeviceAgent·LiveView·SDK)과 AMR 펌웨어 배포(넷 다 맞아야 조그 기능이 열린다), 기기 반영 확인 후 서버 env 상향(순서 역전 금지, relay 90분), 데드맨(정지) 6개 시나리오 실측(스틱 놓음/탭 종료/프로세스 종료/망 단절/채널 끊김/재연결 중 중단 — 합격 기준은 "정지하는가" 하나), 맵 업로드 설정이 실기에서 켜져 있는지 확인(기본값 꺼짐), prd KVS 활성화 시 `KVS_CHANNEL_NAME_PREFIX`·`KVS_ENVIRONMENT_TAG` 명시(누락 시 운영에 dev 이름 채널이 삭제 불가능한 채로 생성됨), presigned URL 실효 수명 확인, relay 장시간 연결의 TURN 비용·안정성 실측.

### 5-13. 보안조사 — PASS CI 평문 왕복 (AXDO-2102)

관련 저장소: `backend-api-main`(협력사 백엔드가 직접 수정 반영). 조사는 완료됐고 방향은 맞지만 구현이 다르고 **테스트가 0건**이다. `dev`·`stg`에는 이미 반영돼 있다.

**승격 전 확인**: 최종 형상은 `c7b20f20`(2026-09-15, 가입 시 `messageAuthCode`로 Redis에서 CI 조회) 이후이고, 중간 커밋 2건(`3bfd5321`·`bdd9a2bc`)은 `633b2496`이 되돌린 임시 형태이므로 무시한다. **리뷰 담당이 없는 상태로 승격하면 안 된다** — `NiceAuthController`·`UserController`·`UserService` 3개 파일을 건드렸는데 이 경로(`/app/user/pass/info`, `syncOasysOnJoin`)에 기존 테스트도 없어 회귀를 막을 자동 검증이 전혀 없다. 승격 전 코드 리뷰를 이 릴리스의 진입 조건으로 둘 것을 권고한다.

**릴리스 차단 결함 — 고치거나 빼고 승격한다**: Android 앱은 어느 브랜치에서도 가입 요청 본문에 `messageAuthCode`를 보내지 않는다(`ReqUserJoin.kt`, `ReqSocialSignup.kt` 전수 확인). 최종 형상은 이 값으로 Redis에서 CI를 찾으므로, 이 변경이 운영에 올라가면 **Android 신규 가입이 전부 오류 없이 OASYS 연동(통합고객번호·SafeKey) 없이 끝난다.** stg를 통째로 승격하면 이 변경이 함께 넘어간다. 서버만 고치는 방법이 있다. 두 가입 경로가 이미 조회하는 `latestAuthCode`(`UserService.java` 194행·1004행 부근)를 재사용하되, `invalidateUnusedAuthCodes`(325행·1027행 부근)가 실행되기 전에 꺼내야 한다. 이 수정이 들어가거나 AXDO-2102 커밋을 승격에서 제외하기 전에는 `backend-api-main` `main` 승격을 하지 않는다.

## 6. 운영 배포 순서

### 6-1. 순서와 이유

| 단계 | 대상 | 이 위치인 이유 |
|---:|---|---|
| 00 | (§7-0) 전 저장소 `stg → main` 승격 | 배포보다 먼저 코드가 `main`에 있어야 한다. `skix-security`는 §4에 따라 선별 반영을 해제하고 통째로 승격 |
| 01 | `skix-openapi` | 신규 기능이 전부 플래그 `false`인 다크 배포라 먼저 올려도 무해하다 |
| 02 | `backend-api-main` | 이후 단계 전부가 backend 신버전(check-member의 sub 지원, identity API, PHR0003 푸시 코드)에 의존한다 |
| 03 | `skix-security` | **02 직후 곧바로.** 사이에 시간이 뜨면 SafeCare LLM 스케줄 등록이 `DVRG0050`으로 실패한다(새 backend가 부르는 구독 조회 API가 구버전 security에 없다) |
| 04 | token-pii `user_accounts` 백필 | 반드시 02 이후. 먼저 하면 복수 계정 사용자 일부가 로그인 못 한다 |
| 05 | `frontend-web-backoffice` | 관제 화면이 backend 신규 URL을 부른다 |
| 06 | `skix-streaming` | backend 신버전 없이 올리면 라이브뷰·S1 경로가 즉시 실패 |
| 07 | `skix-streaming-signal` | streaming의 토큰 검증 API를 부른다 |
| 08 | `skix-medcare` | backend 신버전 필요 |
| 09 | medcare 파티션 출처·identity 백필 | 08 직후 |
| 10 | (필요 시) `skix-openapi-docs` 문서 사이트 재배포 | §5-10의 파트너 API 플래그를 켜는 시점에 맞춰, 그 시점의 반영 상태로 다시 배포한다(정적 사이트라 배포 자체는 언제든 가능하지만, 꺼진 기능을 문서에 먼저 노출하지 않는다) |

### 6-2. 검증계와 순서가 반대인 이유

검증계에서는 `skix-security → backend-api-main → skix-medcare → skix-openapi` 순서로 배포했다(2026-09-03). 그때는 `GET /internal/v1/devices/{serial}/subscription`의 제공자(provider)가 `dev`에만 있고 소비자(`backend-api-main`)는 이미 `stg`에 있어, 소비자가 fail-closed라 security를 먼저 올려야 했다.

**운영계는 반대다.** 운영 `backend-api-main`은 아직 `check-member`에 `loginId`가 필수 파라미터인 구버전이 떠 있다. 이 상태에서 `skix-security`를 먼저 올리면 `loginId`를 안 주는 security의 Cognito 경로 전부가 400이 된다. 반대로 backend를 먼저 올렸을 때의 위험(구버전 security가 새 필드를 조용히 버리는 것, 예: OASYS 직접구독 WebView의 `plan` 필드)은 해당 기능이 아직 프론트가 없어 호출자가 없으므로 무해하다.

### 6-3. 선행 조건 요약

- **DDL**: §2-3에서 정리한 대로 대부분 3환경 선적용 완료. 배포 직전 실물 스키마 재대조(§7-0).
- **SSM 파라미터**: `skix-openapi`(내부키 2종), `skix-medcare`(3종), `skix-security`(태스크정의 재등록만, 값 변경 없음) — §7-1에서 상세.
- **태스크정의 리비전**: `cloudshell-push.sh`는 리비전을 등록하지 않고 최신 리비전으로 `update-service`만 한다. **이미지 푸시 전에 반드시 새 리비전을 먼저 등록**해야 한다.

### 6-4. 앱 스토어 릴리스가 게이트인 항목

| 트랙 | 게이트가 되는 이유 |
|---|---|
| token-pii S6(§5-1) | iOS 소셜 로그인이 `phone_number` 의존을 끊은 버전이어야 파기 후에도 로그인이 유지된다 |

# 세 ECS 서비스(openapi/medcare/security)의 main 태스크정의 파일이 stg와 일치하는지
git diff --stat origin/stg origin/main -- deploy/    # 기대: 출력 없음 (openapi·medcare는 §7-1에서 새 env가 추가되므로 그 파일만 예외)

### 7-1. 태스크정의

> **`cloudshell-push.sh`는 태스크정의 리비전을 등록하지 않는다.** 최신 리비전을 그대로 쓰며 `update-service`만 한다. 새 env가 들어가려면 **이미지 푸시 전에** 리비전을 먼저 등록해야 한다.

**등록 대상** — 세 서비스 모두 저장소 `main`의 `deploy/task-definition-prd.json`을 수정 없이 새 리비전으로 등록한다(배포 시점 값이 이미 들어 있다).

| 서비스 | 패밀리 | main 파일에 새로 들어간 것 |
|---|---|---|
| `skix-openapi` | `skix-openapi-prd-tdef` | env `APP_INTERNAL_ENFORCE_API_KEY`·`IDENTITY_NORMALIZE_ENABLED`·`DEVICE_SETTINGS_PUBLIC_ENABLED`·`USAGE_PUBLIC_ENABLED`·`WEATHER_PUBLIC_ENABLED`(전부 `false`) · secret `APP_INTERNAL_API_KEY`·`NAMUHX_INTERNAL_API_KEY`(SSM `/skix-openapi/prd/…`) |
| `skix-medcare` | `skix-medcare-prd-tdef` | env `CHAT_TITLE_GENERATION_ENABLED`·`IDENTITY_ALIAS_READ_ENABLED`·`IDENTITY_CANONICAL_WRITE_ENABLED`(전부 `false`). 기존 `CHAT_PHR_ATTACHMENT_ENABLED`·`PHR_PUSH_ENABLED`는 `false` 유지 |
| `skix-security` | `skix-security-prd-tdef` | 새 키는 없음 — 실물 리비전을 저장소 파일과 맞추기 위해 재등록만 |

**등록 전 확인** (①저장소 파일 대조 → ②SSM 파라미터 존재 확인 → ③실행 중 리비전과 비교)

```bash
# ① 로컬 맥, 세 저장소 각각 — main 승격 직후
git diff --stat origin/stg origin/main -- deploy/          # openapi·medcare는 새 env만 차이나야 정상
git show origin/main:deploy/task-definition-prd.json > skix-<서비스>-prd.json   # VDI로 옮길 파일
```

```bash
# ② VDI의 CloudShell prd (읽기 전용) — 맥에서 옮긴 파일을 그대로 붙여넣어 사용
for s in openapi medcare security; do
  echo "== skix-$s"
  jq -r '.containerDefinitions[0].secrets[].valueFrom | sub(".*:parameter";"")' skix-$s-prd.json | while read -r p; do
    aws ssm get-parameter --region ap-northeast-2 --name "$p" --query Parameter.Name --output text >/dev/null 2>&1 \
      && echo "  OK      $p" || echo "  MISSING $p"
  done
done
# 기대: MISSING 없음. 하나라도 있으면 그 서비스의 새 태스크는 기동하지 못한다.
```

```bash
# ③ VDI의 CloudShell prd (읽기 전용) — 실행 중 리비전과 비교
proj='{family, taskRoleArn, executionRoleArn, cpu, memory, networkMode, requiresCompatibilities,
       container: (.containerDefinitions[0] | {name, image, essential, portMappings, logConfiguration,
         environment: ((.environment // []) | sort_by(.name)), secrets: ((.secrets // []) | sort_by(.name))})}'
svc() { case $1 in openapi) echo skix-openapi-prd-svc ;; *) echo skmg-airbot-prd-$1-svc ;; esac; }
for s in openapi medcare security; do
  RUN=$(aws ecs describe-services --region ap-northeast-2 --cluster skmg-airbot-prd-ecs-cluster \
          --services "$(svc $s)" --query 'services[0].taskDefinition' --output text)
  LATEST=$(aws ecs describe-task-definition --region ap-northeast-2 --task-definition skix-$s-prd-tdef \
          --query taskDefinition.taskDefinitionArn --output text)
  echo "================ skix-$s   실행중=${RUN##*/}   최신=${LATEST##*/}"
  diff <(aws ecs describe-task-definition --region ap-northeast-2 --task-definition "$RUN" --query taskDefinition | jq -S "$proj") \
       <(jq -S "$proj" skix-$s-prd.json)
done
```

기대 결과: `skix-openapi`는 파일 쪽(`>`)에 env 5종·secret 2종 추가만, `skix-medcare`는 env 3종 추가만, `skix-security`는 차이 없음. **실물 쪽(`<`)에만 있는 줄**은 콘솔에서 따로 넣은 값이므로, 그대로 등록하면 지워진다 — 의도된 값이면 파일에 추가해 저장소에 커밋 후 등록한다.

**웹 콘솔 등록** (각 서비스의 배포 단계 직전, prd 계정·서울 리전 콘솔): ECS → 태스크 정의 → 패밀리 `skix-<서비스>-prd-tdef` → 최신 개정 선택 → 새 개정 생성 → JSON을 사용하여 새 개정 생성 → 기존 JSON을 전부 지우고 위 `skix-<서비스>-prd.json` 내용을 그대로 붙여넣기 → 생성. 새 개정 번호가 ③의 "최신"보다 1 큰지 확인한다.

**배포 이후 값 전환** — 배포 당일에는 켜지 않는다. 게이트가 충족될 때마다 반복한다(저장소 파일 값 수정·커밋 → 웹 콘솔에서 새 개정 등록 → 서비스 업데이트 시 "새 배포 강제" 체크).

| 순서 | 패밀리 | 바꿀 값 | 게이트 |
|---:|---|---|---|
| 1 | medcare | `IDENTITY_ALIAS_READ_ENABLED` → `true` | §5-3 게이트 (a) CONFLICT 0 |
| 2 | medcare | `IDENTITY_CANONICAL_WRITE_ENABLED` → `true`(alias-read는 `true` 유지) | 1번이 전 태스크에 전파된 뒤. 이후 §7-3 재키잉 |
| 3 | openapi | `IDENTITY_NORMALIZE_ENABLED` → `true` | §5-9의 token-pii 백필 후 `sub_not_registered = 0` |
| 4 | openapi | `APP_INTERNAL_ENFORCE_API_KEY` → `true` | openapi 로그 `valid=true`가 3번 이후에도 100% 지속 |
| 5 | medcare | `PHR_PUSH_ENABLED`·`CHAT_PHR_ATTACHMENT_ENABLED` → `true` | 2번 완료 + 앱 스토어 릴리스(§6-4) |
| 6 | medcare | `CHAT_TITLE_GENERATION_ENABLED` → `true` | iOS·Android 모두 `entryType`을 싣는 버전 보급(§6-4) |
| 7 | openapi | `DEVICE_SETTINGS_PUBLIC_ENABLED`·`USAGE_PUBLIC_ENABLED`·`WEATHER_PUBLIC_ENABLED` → `true` | 사업 결정. 날씨는 openapi DB의 `open_api_plans`·`open_api_clients.scopes_override`에 `weather` 스코프 추가 필요. 이 단계에서 `skix-openapi-docs`도 함께 재배포 |

⚠️ 2번 이후 두 identity 플래그를 함께 끄지 않는다. canonical로 적힌 신규 데이터가 다른 로그인 수단에서 안 보인다. 문제가 생기면 `CANONICAL_WRITE`만 끈다.

### 7-3. 백필과 재키잉

**7-3-1. token-pii `user_accounts` 백필 (benjamin DB, 배포 02 이후에만)**

사전 점검(선점 0·중복 0·중복 sub 0·UNIQUE 인덱스 1 이상 기대):

```sql
SELECT
    (SELECT COUNT(*) FROM `user` u
      WHERE u.delete_yn = 'N' AND u.sub IS NOT NULL
        AND EXISTS (SELECT 1 FROM user_accounts ua
                     WHERE ua.sub = u.sub COLLATE utf8mb4_general_ci
                       AND (ua.user_id IS NULL OR ua.user_id <> u.id))) AS preempted,
    (SELECT COUNT(*) FROM `user` u
      WHERE u.delete_yn = 'N' AND u.sub IS NOT NULL
        AND EXISTS (SELECT 1 FROM `user` u2
                     WHERE u2.id <> u.id AND u2.sub = u.sub AND u2.delete_yn = 'N')) AS duplicated,
    (SELECT COUNT(*) FROM (SELECT sub FROM user_accounts WHERE sub IS NOT NULL
                            GROUP BY sub HAVING COUNT(*) > 1) x) AS dup_account_sub,
    (SELECT COUNT(*) FROM (SELECT index_name FROM information_schema.statistics
                            WHERE table_schema = DATABASE() AND table_name = 'user_accounts' AND non_unique = 0
                            GROUP BY index_name HAVING COUNT(*) = 1 AND MAX(column_name) = 'sub') z) AS unique_index_on_sub_only;
```

기대 `0·0·0·1 이상`. 하나라도 어긋나면 진행하지 않는다(선점이 남으면 그 사용자가 남의 신원으로 API를 쓰게 된다). RDS 스냅샷 확보 후 실행:

```sql
CREATE INDEX ix_user_sub ON `user` (sub);   -- 이미 있으면 ERROR 1061, 무시

CREATE TABLE backfill_targets_prd (
    user_id BIGINT NOT NULL PRIMARY KEY,
    sub VARCHAR(128) COLLATE utf8mb4_general_ci NOT NULL,
    auth_provider VARCHAR(20) NOT NULL
);

START TRANSACTION;
INSERT INTO backfill_targets_prd (user_id, sub, auth_provider)
SELECT u.id, u.sub,
       CASE u.auth_provider WHEN 'K' THEN 'Kakao' WHEN 'N' THEN 'Naver'
                            WHEN 'G' THEN 'Google' WHEN 'S' THEN 'SignInWithApple' ELSE 'EMAIL' END
FROM `user` u
WHERE u.delete_yn = 'N' AND u.sub IS NOT NULL
  AND (u.auth_provider IS NULL OR u.auth_provider IN ('K','N','G','S'))
  AND NOT EXISTS (SELECT 1 FROM user_accounts ua WHERE ua.sub = u.sub COLLATE utf8mb4_general_ci)
  AND NOT EXISTS (SELECT 1 FROM `user` u2 WHERE u2.id <> u.id AND u2.sub = u.sub AND u2.delete_yn = 'N');

SELECT COUNT(*) AS target_rows FROM backfill_targets_prd;   -- 약 1,160건 예상(2026-08 실측)

INSERT INTO user_accounts (user_id, sub, auth_provider)
SELECT t.user_id, t.sub, t.auth_provider FROM backfill_targets_prd t;

SELECT ROW_COUNT() AS inserted_rows, (SELECT COUNT(*) FROM backfill_targets_prd) AS target_rows; -- 같아야 함
COMMIT;   -- 같을 때만. 다르면 ROLLBACK(재실행은 멱등)
```

사후 검증: `sub_not_registered = 0`(3-1의 사전 점검 쿼리 패턴을 NOT EXISTS로 재사용), `user_accounts`의 `sub`/`user_id`/`auth_provider` NULL 전부 0. `backfill_targets_prd`는 지우지 않는다(sub는 UUID라 PII 아님).

UPDATE kmeta_streams SET cheiron_sub = user_strid WHERE cheiron_sub IS NULL;

**7-3-3. 재키잉 (소유자 키 통합, 배포일과 날짜를 나눠서 진행)**

순서: alias-read ON → canonical-write ON → 재키잉 SQL → 병합(convertAll). openapi 쪽은 운영 대상이 0건이라 재키잉 없음.

- **① alias-read ON**: 전 태스크 교체 확인, 갈라진 사용자 표본으로 두 로그인 수단에서 대화 목록이 같은지, 대화 이어가기·제목 변경·폴더·검색 정상 확인.
- **② canonical-write ON**: 전 태스크 드레인 확인, 신규 대화 1건 생성 후 `kmeta_streams`의 `user_strid`(대표 sub)·`cheiron_sub`(로그인한 sub) 확인, 기존 대화(다른 로그인 수단 소유)에 이어서 질문해 답변 저장 성공 확인(실패 시 즉시 canonical-write만 `false`).

**③ 재키잉 SQL** (실행 위치: medcare DB). 선행 확인: ②의 전 태스크 드레인, 유지보수 배치(identity backfill 02:30·reconcile 일요일 03시·drift 매일 04시)를 피한 창(05시 이후 권장. 이 SQL은 배치 잠금을 쓰지 않는다), identity backfill 재실행 후 CONFLICT 0 재확인, RDS 스냅샷.

```sql
-- ═══ §0. 사전 점검 (읽기 전용) ═══

-- 0-1. 매핑 상태. NORMAL 이 아닌 그룹은 대상에서 빠진다
SELECT status, COUNT(*) AS rows_, COUNT(DISTINCT owner_key) AS owners FROM medcare_user_identity GROUP BY status;

-- 0-3. 테이블별 영향 행 수 = dry-run. 이 값을 기록해 둔다(§2 검증의 기대값)
SELECT 'kmeta_streams' AS tbl, COUNT(*) AS rows_
  FROM kmeta_streams t JOIN medcare_user_identity m ON m.sub = t.user_strid
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key
UNION ALL SELECT 'kmeta_conversation_search', COUNT(*)
  FROM kmeta_conversation_search t JOIN medcare_user_identity m ON m.sub = t.auth_sub
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key
UNION ALL SELECT 'customer_folders', COUNT(*)
  FROM customer_folders t JOIN medcare_user_identity m ON m.sub = t.folder_auth_sub
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key
UNION ALL SELECT 'customer_folder_chat', COUNT(*)
  FROM customer_folder_chat t JOIN medcare_user_identity m ON m.sub = t.chat_auth_sub
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key
UNION ALL SELECT 'customer_if_log', COUNT(*)
  FROM customer_if_log t JOIN medcare_user_identity m ON m.sub = t.customer_if_auth_sub
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;

-- 0-4. ★ 유니크 충돌 ★ customer_folder_chat 만 위험하다. 기대 0행
SELECT COALESCE(m.owner_key, fc.chat_auth_sub) AS new_owner, fc.chat_str_id, COUNT(*) AS rows_,
       GROUP_CONCAT(fc.chat_id) AS chat_ids, GROUP_CONCAT(fc.chat_auth_sub) AS current_owners
FROM customer_folder_chat fc
LEFT JOIN medcare_user_identity m ON m.sub = fc.chat_auth_sub AND m.status = 'NORMAL'
GROUP BY new_owner, fc.chat_str_id HAVING COUNT(*) > 1;

-- 0-5. 파티션 출처 — 기대 0 (0 이 아니면 7-3-2 ①(파티션 출처 백필) 누락. 여기서 멈춘다)
SELECT COUNT(*) AS cheiron_sub_null FROM kmeta_streams WHERE cheiron_sub IS NULL;


-- ═══ §1. 충돌 해소 — 0-4 가 0행이 아닐 때만 ═══
-- 최근에 담은 폴더를 남기고 나머지는 격리 테이블로 옮긴 뒤 지운다
CREATE TABLE IF NOT EXISTS rekey_quarantine_folder_chat LIKE customer_folder_chat;
ALTER TABLE rekey_quarantine_folder_chat
    ADD COLUMN IF NOT EXISTS quarantined_at datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    ADD COLUMN IF NOT EXISTS run_id varchar(64) DEFAULT NULL;

SET @run_id = 'rekey-YYYYMMDD-1';

INSERT INTO rekey_quarantine_folder_chat
SELECT fc.*, CURRENT_TIMESTAMP(6), @run_id
FROM (SELECT x.chat_id,
             ROW_NUMBER() OVER (PARTITION BY COALESCE(m.owner_key, x.chat_auth_sub), x.chat_str_id
                                ORDER BY x.create_date DESC, x.chat_id DESC) AS rn
      FROM customer_folder_chat x
      LEFT JOIN medcare_user_identity m ON m.sub = x.chat_auth_sub AND m.status = 'NORMAL') ranked
JOIN customer_folder_chat fc ON fc.chat_id = ranked.chat_id
WHERE ranked.rn > 1;

DELETE fc FROM customer_folder_chat fc
JOIN rekey_quarantine_folder_chat q ON q.chat_id = fc.chat_id AND q.run_id = @run_id;
-- 0-4 재실행 → 0행 확인. 아니면 멈춘다


-- ═══ §2. 적용 — journal + UPDATE 한 트랜잭션 ═══
CREATE TABLE IF NOT EXISTS rekey_journal (
    id         bigint       NOT NULL AUTO_INCREMENT,
    run_id     varchar(64)  NOT NULL,
    table_name varchar(64)  NOT NULL,
    pk_value   varchar(500) NOT NULL,
    old_owner  varchar(128) NOT NULL,
    new_owner  varchar(128) NOT NULL,
    applied_at datetime(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    KEY idx_rekey_journal_run (run_id),
    KEY idx_rekey_journal_table_pk (table_name, pk_value)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

SET @run_id = 'rekey-YYYYMMDD-1';   -- §1 과 같은 값

START TRANSACTION;

-- 변경 전 값 기록
INSERT INTO rekey_journal (run_id, table_name, pk_value, old_owner, new_owner)
SELECT @run_id, 'kmeta_streams', t.strid, t.user_strid, m.owner_key
  FROM kmeta_streams t JOIN medcare_user_identity m ON m.sub = t.user_strid
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
INSERT INTO rekey_journal (run_id, table_name, pk_value, old_owner, new_owner)
SELECT @run_id, 'kmeta_conversation_search', t.stream_strid, t.auth_sub, m.owner_key
  FROM kmeta_conversation_search t JOIN medcare_user_identity m ON m.sub = t.auth_sub
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
INSERT INTO rekey_journal (run_id, table_name, pk_value, old_owner, new_owner)
SELECT @run_id, 'customer_folders', CAST(t.folder_id AS CHAR), t.folder_auth_sub, m.owner_key
  FROM customer_folders t JOIN medcare_user_identity m ON m.sub = t.folder_auth_sub
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
INSERT INTO rekey_journal (run_id, table_name, pk_value, old_owner, new_owner)
SELECT @run_id, 'customer_folder_chat', CAST(t.chat_id AS CHAR), t.chat_auth_sub, m.owner_key
  FROM customer_folder_chat t JOIN medcare_user_identity m ON m.sub = t.chat_auth_sub
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
INSERT INTO rekey_journal (run_id, table_name, pk_value, old_owner, new_owner)
SELECT @run_id, 'customer_if_log', CAST(t.customer_if_id AS CHAR), t.customer_if_auth_sub, m.owner_key
  FROM customer_if_log t JOIN medcare_user_identity m ON m.sub = t.customer_if_auth_sub
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;

-- 재키잉. cheiron_sub 는 건드리지 않는다
UPDATE kmeta_streams t JOIN medcare_user_identity m ON m.sub = t.user_strid
   SET t.user_strid = m.owner_key WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
UPDATE kmeta_conversation_search t JOIN medcare_user_identity m ON m.sub = t.auth_sub
   SET t.auth_sub = m.owner_key WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
UPDATE customer_folders t JOIN medcare_user_identity m ON m.sub = t.folder_auth_sub
   SET t.folder_auth_sub = m.owner_key WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
UPDATE customer_folder_chat t JOIN medcare_user_identity m ON m.sub = t.chat_auth_sub
   SET t.chat_auth_sub = m.owner_key WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
UPDATE customer_if_log t JOIN medcare_user_identity m ON m.sub = t.customer_if_auth_sub
   SET t.customer_if_auth_sub = m.owner_key WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;

-- ★ COMMIT 전 검증 3종 ★
-- (a) journal 건수 = 0-3 기록값
SELECT table_name, COUNT(*) AS journaled FROM rekey_journal WHERE run_id = @run_id GROUP BY table_name;
-- (b) 잔여 0
SELECT COUNT(*) AS remaining FROM kmeta_streams t JOIN medcare_user_identity m ON m.sub = t.user_strid
 WHERE m.status = 'NORMAL' AND m.sub <> m.owner_key;
-- (c) cheiron_sub NULL 수 = 0-5 값
SELECT COUNT(*) AS cheiron_sub_null FROM kmeta_streams WHERE cheiron_sub IS NULL;

COMMIT;     -- 3종 모두 기대값일 때만. 아니면 ROLLBACK


-- ═══ §3. 사후 확인 ═══
-- 여러 파티션의 대화가 한 소유자 아래로 모인 사용자
SELECT user_strid, COUNT(*) AS convs, COUNT(DISTINCT cheiron_sub) AS partitions
FROM kmeta_streams GROUP BY user_strid HAVING COUNT(DISTINCT cheiron_sub) > 1 ORDER BY convs DESC;
```

**④ 병합(convertAll)**: `POST .../medcare/v1/internal/conversations/convertAll` → 완료 로그 확인 → `GET .../conversations/drift`로 `missingInKmeta`·`ownerlessStreams`·`missingSearchIndex` 이상 없음 확인. `staleInKmeta`가 보여도 운영에서는 지우지 않고 조사한다.

### 7-4. 롤백 공통 원칙

- 애플리케이션: 이전 이미지·jar로 되돌린다.
- DB: 이번 릴리스로 추가된 테이블·컬럼은 삭제하지 않는다(구버전이 참조하지 않고, 조사 자료로 남긴다).
- 재키잉 SQL은 `rekey_journal`에 변경 전 값을 기록해 두므로, 문제가 생기면 journal 기준으로 개별 복원할 수 있다(전체 룰백은 RDS 스냅샷).
- Nginx/프론트: 되돌리면 해당 화면만 접근 불가, 서버 기존 기능에는 영향 없음.

| 3 | **§5-13 PASS CI 리뷰 담당 지정** | 테스트 0건인 협력사 커밋을 승격 대상에 포함할지, 리뷰를 먼저 마칠지 결정 필요 |
| 4 | **openapi 파트너 공개 API 3종(§5-9의 7번) 공개 여부·시점** | `DEVICE_SETTINGS_PUBLIC_ENABLED`·`USAGE_PUBLIC_ENABLED`·`WEATHER_PUBLIC_ENABLED`는 사업 결정 사안. 날씨는 스코프 설정 작업이 추가로 필요하다 |
| 5 | **`APP_INTERNAL_ENFORCE_API_KEY`(§5-10) 운영 전환 여부·시점** | 백오피스가 실제로 내부키를 보내는지 확인 후 결정. 안 보내는 상태에서 켜면 클라이언트 발급 기능이 죽는다 |
| 6 | **medcare PHR 첨부(§5-6) AI팀 7개 항목 회신** | 회신 전에는 이 트랙의 플래그를 켤 수 없다(승격 자체는 가능, 다크 상태 유지) |
| 7 | **탈퇴 행 부활 / 익명화 / retention 테이블 설계의 착수 시점** | 이번 릴리스와 무관하게 진행 가능하지만, `backend-api-main`의 `feature/medcare-withdrawal-purge`(`b2138c78`)를 이 트랙에 흡수하기로 한 결정이 있어 일정 조율이 필요하다(개인정보 처리방침의 보유·이용기간 표 대조가 선행 조건) |
| 8 | **CS 공지 시점** | medcare 소유자 키 통합(§5-3) 재키잉 시 채팅 한도·폴더 상한이 사람 단위로 합산되는 변화가 있다. 배포일과 함께 공지 시점을 정해야 한다 |
| 9 | **앱 스토어 릴리스 일정과의 정렬(§6-4)** | 4개 트랙의 플래그가 앱 배포 시점에 종속된다. 서버 릴리스일과 앱 릴리스일 사이의 간격을 정해야 한다 |
| 10 | **관제 원격 맵핑 기기·펌웨어 배포 일정과의 정렬(§5-2)** | 서버 승격만으로는 기능이 열리지 않는다. DeviceAgent·LiveView·SDK·AMR 펌웨어 4곳의 배포 일정을 서버 릴리스와 맞춰야 한다 |
