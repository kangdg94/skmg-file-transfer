## 0. 세 줄 요약

1. 이 서비스는 API 요청과 IoT 수신 경로에서 분리한 무거운 집계·보정 작업을 일정 주기로 실행한다. Redis 최신 상태를 RDS에 되쓰고, 날씨를 좌표 격자별로 수집하며, Athena 원문을 운영 통계로 압축한다.
2. 최근 6개월에는 IoT write-back, 외부 API 호출량, 좌표 기반 날씨 수집·예열, NMX 전환, Athena 집계를 반영했다. `dev`·`stg`·`main` 사이 커밋 차이는 없다.
3. 다만 Git 일치가 실배포 일치를 보장하지 않는다. 첫 주에는 실행 jar와 프로필, 운영 TTL, Athena IAM·쿼리 결과, 날씨 실 DB를 대조해야 한다.

## 1. 이 프로젝트가 하는 일

- Redis에 쌓인 기기 최신 상태를 `statistics_operation` 같은 RDS 통계 테이블로 주기적으로 반영한다.
- 좌표 격자별 현재 날씨를 외부 공급자에서 가져와 DB와 Redis에 저장하고 API 캐시를 미리 데운다.
- 외부 API 호출량을 일·월 단위로 집계해 사용량과 과금 근거를 만든다.
- S3에 저장된 IoT 원문을 Athena로 읽어 공기질·동작 통계를 만든다.
- 장기 작업의 락, 재시도, 기준 시각과 처리량을 관리한다.

이 저장소는 실시간 사용자 API를 제공하지 않는다. 스케줄이 멈춰도 즉시 5xx가 나지 않아 장애가 늦게 발견될 수 있으므로, 마지막 성공 시각과 처리 건수를 운영 지표로 봐야 한다.

### 용어

| 용어 | 뜻 |
|---|---|
| **write-back** | Redis 최신 상태를 일정 주기로 관계형 DB 통계 행에 반영하는 작업이다. |
| **격자 캐시** | 위경도를 격자 키로 양자화해 같은 지역의 날씨 응답을 재사용하는 구조다. |
| **캐시 예열** | API 요청 전에 활성 위치의 날씨를 Redis에 채워 첫 요청 지연을 줄이는 작업이다. |
| **Athena 집계** | S3 IoT 원문을 SQL로 조회해 기존 RDS 원장을 대체할 통계를 만드는 작업이다. |
| **NMX** | 날씨 공급자 연동에 쓰는 신규 방식이다. 구 방식과 응답·인증·실패 처리가 다르다. |

## 2. 전체 구성

```text
[Spring Scheduler]
   ├─ Redis 최신 상태 ──→ MySQL statistics_operation
   ├─ 활성 좌표 목록 ──→ 날씨 공급자 ──→ MySQL + Redis
   ├─ 외부 API 원장 ───→ 일·월 사용량 집계
   └─ Athena/S3 IoT 원문 ──→ 공기질·동작 통계
```

배치는 중복 실행과 부분 실패를 전제로 봐야 한다. 동일 구간을 다시 돌려도 결과가 중복되지 않는지, 기준 시각이 UTC인지 KST인지, 다음 실행이 이전 실행과 겹칠 때 락이 어떻게 작동하는지를 작업별로 확인한다.

## 3. 코드 구조

| 경로 | 책임 |
|---|---|
| `src/main/java` | 스케줄 진입점, 업무 서비스, DB·Redis·외부 연동 |
| `src/local` | 로컬 환경 설정·리소스 |
| `src/vdi` | 개발계 환경 설정·리소스 |
| `src/stag` | 검증계 환경 설정·리소스 |
| `src/prod` | 운영 환경 설정·리소스 |
| `build.gradle` | `profile`에 따른 source set과 jar 버전 구성 |

환경 이름은 일반적인 `dev`·`stg`가 아니라 빌드 프로필 `vdi`·`stag`를 사용한다. 프로필 오타나 기본값은 다른 환경 설정을 포함한 jar를 만들 수 있으므로 산출물 이름만 믿지 말고 내부 설정과 실행 인자를 확인한다.

## 4. 데이터와 외부 의존성

| 종류 | 대상 | 용도 |
|---|---|---|
| MySQL | `statistics_operation` | Redis 최신 동작 상태 write-back |
| MySQL | `outdoor_weather_history` 계열 | 좌표·시각별 날씨 이력과 API 조회 근거 |
| MySQL | `external_api_call_count` | 공급자·앱·endpoint별 호출량 집계 |
| MySQL | 요약 통계 테이블 | 일·월 단위 운영 지표 |
| Redis | `lastSeen`, 동작·전원 키 | write-back 입력 |
| Redis | 날씨 현재값·활성 격자 | API 캐시와 예열 대상 |
| Athena | IoT 원문 테이블 | RDS 원장 축소 후 통계 원천 |
| 외부 API | 날씨 공급자 | 현재 날씨·예보 수집 |

실 테이블명·컬럼·인덱스는 환경별 DB와 대조한다. 저장소의 쿼리와 DDL만으로 백필 완료나 레거시 테이블 퇴역을 단정할 수 없다.

## 5. 빌드·테스트·로컬 실행·배포

```bash
./gradlew clean test
./gradlew clean bootJar -Pprofile=vdi -Pversion=<version>
./gradlew clean bootJar -Pprofile=stag -Pversion=<version>
./gradlew clean bootJar -Pprofile=prod -Pversion=<version>
```

배포 자동화와 정확한 EC2 경로는 저장소에서 확정되지 않는다. VDI에서 대상 프로필 jar를 만들고 환경별 서버에 전달한 뒤 기존 실행 스크립트로 교체하는 흐름으로 파악된다. 배포 전후 다음을 기록한다.

1. Git 커밋, 프로필, jar checksum.
2. 현재 프로세스의 jar 경로·시작 시각·JVM timezone.
3. 주요 스케줄의 다음 실행과 마지막 성공 시각.
4. DB·Redis·Athena 권한과 처리 건수.
5. 롤백 jar와 재처리할 시간 구간.

## 8. 남은 일

### 즉시

1. 세 환경 프로세스의 커밋·jar checksum·빌드 프로필·JVM timezone을 기록한다.
2. 운영 날씨 예열 주기와 API fresh TTL을 실값으로 대조하고 한 값으로 정렬한다.
3. Athena workgroup·database·output location·IAM과 최근 7일 처리 건수를 확인한다.
4. 날씨 테이블의 백필 범위, 중복 좌표, 최신 시각, 레거시 소비자를 조회한다.
5. 각 배치의 마지막 성공 시각·처리량·실패 알람을 대시보드에 올린다.

### 원장 전환 게이트

- `map_id` 백필이 완료돼야 한다.
- 같은 시간 구간을 RDS 원장과 Athena 집계로 대사해 허용 오차를 정한다.
- API·리포트 소비자가 새 집계를 읽는지 확인한다.
- 재처리 가능한 기간과 쿼리 비용 상한을 정한 뒤 기존 공기질 INSERT를 끈다.

### 후속

- 환경별 수동 jar 배포를 checksum과 실행 설정까지 재현 가능한 절차로 만든다.
- 작업별 분산 락·멱등 키·backfill 명령을 표준화한다.
- 사용하지 않는 날씨 활성 키와 레거시 테이블을 소비자 0건 확인 뒤 정리한다.

## 9. 운영 중 자주 만날 상황

| 상황 | 확인 방법 |
|---|---|
| 날씨 외부 호출 급증 | 활성 격자 수 → Redis 현재값 TTL → 예열 마지막 성공 → 공급자 오류 순서로 본다. |
| 날씨가 오래됨 | DB 최신 관측 시각, Redis TTL, 스케줄 실행 시각, JVM timezone을 비교한다. |
| write-back이 0건 | Redis `lastSeen` 생성 여부, 대상 선별 조건, DB 권한과 upsert 결과를 본다. |
| 통계가 특정 시간대만 비어 있음 | Athena partition과 payload timestamp, KST 변환 경계, 재처리 구간을 확인한다. |
| 배치가 겹쳐 실행됨 | 락 키·만료시간, 이전 프로세스 생존 여부, 한 작업의 최장 실행 시간을 비교한다. |
| 외부 API 사용량이 맞지 않음 | 원시 호출 원장과 일 집계의 공급자·앱·endpoint·기준일을 같은 조건으로 대사한다. |
