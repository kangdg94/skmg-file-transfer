## 0. 세 줄 요약

1. **관제 요원이 관리자 웹에서 로봇 카메라 영상을 보며 조이스틱으로 로봇을 몰아 SLAM 지도를 만드는 기능**이다. 지금까지는 사람이 현장에 가서 리모컨으로 몰아야만 지도가 만들어졌다.
2. 서버 3저장소는 구현이 끝났고 브랜치 반영도 대부분 됐다. 기기(`packages-mr7`)와 관제 프론트(`frontend-web-backoffice`)도 **각각 작업을 마치고 실기 E2E까지 통과시킨 흔적이 있는데, 세 브랜치 모두 8월 말 이후 멈춘 채 어느 주 브랜치에도 머지되지 않았다.**
3. 남은 것은 **멈춰 있는 타 팀 브랜치 회수**, **기기 relay 상한 90분 반영(이게 없으면 10분 넘는 맵핑이 성립하지 않는다)**, 그리고 **운영 배포 순서 P0 2건**(`purpose` 컬럼 ALTER 선행 / `KVS_RELAY_MAX_DURATION_MS` 실값 확인)이다.

## 1. 배경

### 1-1. 용어

| 용어 | 뜻 |
|---|---|
| **AMR** | 로봇 본체(Autonomous Mobile Robot). ROS 기반 펌웨어이고 저장소는 `amr`. |
| **SLAM / 맵핑** | 로봇이 주행하며 실내 지도를 만드는 것. 만들어진 지도를 서버에 등록하고 변환(이미지·분할)까지 해야 실제로 쓰인다. |
| **수동 맵핑(`MANUAL_MAPPING`)** | 사람이 로봇을 몰아서 지도를 만드는 AMR 상태. 원격 맵핑은 이 상태를 그대로 재사용한다. |
| **조그(jog)** | 조이스틱으로 로봇을 미세 조작하는 것. 관제 웹의 조이스틱 → 데이터채널 → 로봇 바퀴. |
| **스테이션 / 도킹** | 충전 거치대. 로봇이 여기 붙어 있는 상태가 `ONSTATION`, 빠져나오는 것이 `UNDOCKING`. |
| **KVS** | AWS Kinesis Video Streams. 여기서는 그중 **WebRTC 시그널링 채널**을 써서 로봇(MASTER)과 브라우저(VIEWER)가 P2P로 영상·데이터채널을 주고받는다. |
| **relay / TURN** | P2P가 직접 안 될 때 중계 서버를 경유하는 방식. 비용이 들고 연결 지속 시간에 상한이 걸린다. |
| **DataChannel** | KVS WebRTC 연결 위의 양방향 메시지 채널. 조그 명령(`MOVE`/`ROTATE`)이 여기로 간다. |
| **`controlPurpose`** | 이번에 새로 만든 필드. KVS 세션 시작 전문에 실려 그 세션이 원격 맵핑용(`REMOTE_MAPPING`)인지 일반 라이브뷰(`LIVE_VIEW`)인지 알린다. **"이것이 원격 맵핑이다"의 유일한 판정 근거다.** |
| **DeviceAgent / IotAgent / LiveView** | 로봇 위 Android 앱들. `packages-mr7`에 DeviceAgent·IotAgent·런처가, `liveliew`에 LiveView(KVS MASTER)가 있다. |
| **PUI** | 로봇 몸체에 달린 화면(Product UI). 런처가 띄운다. |
| **AIDL / AAR** | Android 프로세스 간 통신 인터페이스 정의(AIDL)와, 그것을 담아 배포하는 프리빌트 라이브러리(AAR). LiveView가 DeviceAgent를 부를 때 이 경로를 탄다. |
| **원장(`remote_mapping_session`)** | 이번에 만든 테이블. 맵핑 한 건의 상태·종료 사유를 기록하는 서버측 진실. |
| **SLAM0001 / SLAM0004** | 맵핑 시작 / 맵핑 취소 MQTT 명령 코드. |
| **comeback** | 스테이션 복귀 명령. **지도 저장의 트리거가 "복귀 도착"이라서** 맵핑 "완료"가 종료 명령이 아니라 이 복귀 명령으로 구현되어 있다. |
| **fence** | KVS 세션의 단조 증가 토큰. 기기가 과거 세션 명령을 거부하는 데 쓴다. |
| **correlationId** | 한 명령의 추적 키. 기기 응답이 이 키로 돌아와 원장과 맞춰진다. |

### 1-2. 문제

로봇을 새로 설치하거나 공간이 바뀌면 지도를 다시 만들어야 하는데, **사람이 현장에 가서 리모컨으로 로봇을 몰아야만** 지도가 만들어졌다. 설치 건마다 출장이 필요하고, 운영 중 로봇의 재맵핑도 마찬가지였다.

기술적으로 막고 있던 것은 세 가지였다.

- 맵핑 중에는 조그가 막혀 있다. 로봇이 맵핑 중에는 동작 모드를 `NORMAL`로 보고하는데, 기존 라이브뷰 조그는 "수동제어 모드일 때만" 열리도록 되어 있어 **맵핑 중에는 영영 열리지 않는다.**
- 로봇 화면(PUI)이 맵핑 중 자동으로 맵핑 화면을 띄우고, 그 화면이 없는 상태에서 맵핑 진행 콜백을 받으면 **출하 런처가 맵핑을 자동 취소한다.** 즉 화면만 안 띄우면 첫 콜백에 지도가 사라진다.
- KVS relay 연결이 10분에 끊긴다. 맵핑 한 건은 최악 40분 주행 + 복귀·업로드다.

### 1-3. 요구사항·전제

- 관제 웹에서 **맵핑 시작 → 원격 주행 → 완료(복귀·저장·등록) 또는 취소(폐기)** 를 끝낸다.
- 사용자는 **내부 관제 인원**이고, **요원이 영상을 보면서 조작하는 것(attended)** 이 전제다. 이 전제가 아래 여러 결정의 근거다.
- **기존 운영 경로 무회귀**: 앱 발 SLAM 맵핑, 기존 관제 제어, 고객 라이브뷰(조그 권한 포함)를 한 줄도 바꾸지 않는다. 이번 변경은 기존 조건에 **OR 항을 더하는 것**이지 기존 조건을 바꾸는 것이 아니다.
- **요원이 "완료"로 종결한 세션에 한해** 지도가 등록·변환된다. 감독 없이 만들어진 지도는 남기지 않는다.
- 크리덴셜(STS·presigned URL)이 로그·DB·응답에 새로 노출되는 경로를 만들지 않는다.
- **완성도 기준은 MVP**다. 핵심 불변식은 설계로 막고, 희귀 실패는 운영(런북·수동 처리)으로 흡수하며, 반복 비용이 실측되기 전의 자동화는 하지 않는다.

**`packages-mr7` `kvs-mapping`이 구현한 것** (4커밋, 14파일, +165/-26):

- AIDL 확장 방식이 **결정되어 이미 구현돼 있다** — 새 메서드(V2)가 아니라 **`startKvsSession`에 `String controlPurpose` 인자 추가**, 그리고 프리빌트 AAR(`devicecontrolapi-release_1.0.0.aar`) 재빌드까지 포함. 오래 회신 대기 중이던 항목이 코드로 답이 나와 있다.
- 조그 게이트 확장(요청 §3-1): `StreamingManager.movementControl`이 `!isRemoteMappingSession() && !isManualControl()`일 때만 막도록 바뀜 — **기존 라이브뷰 조건은 그대로 두고 OR 항만 추가**한 형태로, 요청한 무회귀 조건을 지켰다.
- PUI 화면 억제 래치(요청 §3-2): `SKMPreferences.IS_REMOTE_MAPPING` 플래그로 구현. 맵핑 시작 시 세션 목적을 보고 세우고 맵핑 종료 시 내린다.
- 세션 종료 시 취소 + 복귀(요청 §3-3): 원격 발 취소면 `AMRMotor.returnToStation()` 호출. 로컬 PUI 취소는 기존대로 복귀 안 함.
- 복귀 구간 부수효과 가드(요청 §3-4, 권장 항목): 래치가 참이면 새 세션의 `stopAllAction`·`changeAmrManualMode`를 건너뛰도록 구현.
- **요청서에 없던 차단 지점 1건을 실기에서 찾아 고쳤다** — `StateManager.checkBlockedStatus`가 KVS 세션 중 `setAMROperation`을 막고 있어서 **맵핑 시작 명령 자체가 통과하지 못했다.** `REMOTE_MAPPING` 세션이면 통과시키도록 수정.
- 커밋 메시지에 **실기 E2E 통과 기록**: "맵핑 시작→조그→완료(comeback)→복귀·도킹→맵 저장·업로드 end-to-end 동작" (2026-08-21).

**`frontend-web-backoffice` `feature/remote`가 구현한 것** (7커밋, 13파일, +1,476/-30):

- `RemoteMapping.vue`(1,013줄), `useMappingSession.ts`(211줄), 맵핑 API 클라이언트 3파일, 다국어 문구.
- 코드 주석이 전달한 요청서의 절 번호(§2-3, §3-5, §3-6)를 그대로 인용하고 있다 — **요청 내용이 정확히 반영됐다.** 확인된 구현: `beforeunload` 이탈 방지, 복귀 중(`ENDING`) KVS 재오픈 차단, `terminationType` 분기(`UPLOAD_FAILURE`를 별도 문구로), `isDocked` 기반 시작 버튼 비활성화 + 사유 문구, `ENDED` 확인 후 세션 종료, 강제 종결 호출부(테스트용).

**`liveliew`의 미반영이 기능 게이트다** — relay 상한 상수 `RELAY_TIME_LIMIT_MAX_MS`가 `origin/direct_kvs`·`origin/refactoring` 양쪽에서 **여전히 600,000ms(10분)** 이다. 요청한 90분(5,400,000)이 반영되지 않았다. 안내 문구(`streaming_connected_description`)도 기존 그대로다.

## 3. 무엇을 만들었나

### 3-1. 전체 흐름

```
① 세션    관제웹 → skix-security: POST .../kvs/mapping-sessions   (맵핑 전용 경로)
          → 자사 AWS KVS 채널 발급 → MQTT kvsSessionStart{controlPurpose: "REMOTE_MAPPING"}
          → LiveView 세션 수락 → DeviceAgent가 목적을 기억(조그 권한 확정)
          관제웹은 VIEWER로 붙고 DataChannel이 OPEN 되어야 다음 단계 버튼이 열린다

② 시작    관제웹 → backend-api-main: POST .../mapping-session/start
          → 시작 조건 게이트(도킹·전원·LLM·배터리·바이탈사인·동작상태)
          → 원장 3행 선커밋(remote_mapping_session + history_control + history_map)
          → SLAM0001 발행   ※ 전문에 원격 표식 없음 — 판정은 ①의 세션이다
          로봇: ONSTATION → (스스로) UNDOCKING → MANUAL_MAPPING
                ※ 도킹 해제 명령을 따로 보내지 않는다. 보내면 지도가 파괴된다
          기기의 "In Progress" 최초 수신 → 원장 STARTING → ACTIVE 승격 (통상 10초 내외)

③ 주행    조이스틱(100ms) → DataChannel → LiveView → DeviceAgent(물리 상태 게이트)
          → AMR /soc_vel → 예측정지·데드맨 → 바퀴

④ 완료    관제웹 → backend-api-main: POST .../{id}/finish   (ACTIVE 에서만)
          → 원장 ENDING(FINISH) CAS → comeback(복귀) 명령 발행
          → 로봇 자율 복귀 → 스테이션 도착 → 지도 저장 → S3 업로드
          → 서버가 업로드 도착을 CAS로 판별 → 맵 등록·변환 → 원장 ENDED
          관제웹은 ENDED 확인 후에 KVS 세션을 닫는다

⑤ 취소    관제웹 → backend-api-main: POST .../{id}/cancel
          → 원장 ENDING(CANCEL) CAS → SLAM0004 발행 → 지도 폐기
          → 기기 확인 신호로 CANCELLED 수렴 → 로봇은 스테이션으로 복귀

⑥ 세션종료(사유 불문 — 단절·relay 상한·lease 만료·정상 close)
          기기: 로봇이 맵핑 중이면 맵핑 취소를 로컬 발행(저장 없음) 후 복귀
          → 취소 보고가 서버에 닿으면 원장 FAILED(DISCONNECT)
          → 닿지 않으면 ACTIVE 잔존 → §9 런북으로 회수
```

②에서 **도킹 해제를 호출하지 않는 것**, ③에서 **DeviceAgent를 조그 허용의 최종 권위로 두는 것**, ⑥에서 **종료를 기기 로컬로 실행하는 것**이 이 설계의 세 축이다.

### 3-3. 데이터

**MySQL — `remote_mapping_session`** (backend-api-main DB. dev 스키마 `airbotdev`, stg·prd 스키마 `benjamin`). 맵핑 한 건의 **상태 원장**이며 동시에 **동시성 게이트**다. DDL 전문은 부록 B.

핵심 장치는 두 가지다.

- `active_flag` 생성 컬럼 — `status IN ('STARTING','ACTIVE','ENDING')`이면 `1`, 종결 상태면 `NULL`. `UNIQUE KEY uk_rms_serial_active (serial, active_flag)`와 짝을 이뤄 **serial당 활성 세션 1개**를 DB가 보장한다. 종결되면 `NULL`이 되어 UNIQUE 중복이 허용되므로 다음 맵핑이 열린다.
- `termination_type` 6종 — `FINISH` / `CANCEL` / `DISCONNECT` / `FORCE` / `SLAM_FAILURE` / `UPLOAD_FAILURE`. **`ENDING` 전이 시점에 확정**하고, 나중에 맵 업로드가 도착했을 때 **등록 여부를 이 값으로 가른다**(`FINISH`만 등록).

**`security.kvs_session_history.purpose`** (skix-security DB) — `varchar(32) NULL`. `NULL`이면 일반 라이브뷰, `REMOTE_MAPPING`이면 원격 맵핑 세션. **이 컬럼이 없으면 일반 라이브뷰까지 전량 실패한다**(§7-1 P0-①).

**신규 Redis 키·SSM 파라미터는 없다.** 설정은 아래 env 2개뿐이고 둘 다 기본값이 있다.

| 환경변수 | 기본값 | 뜻 |
|---|---|---|
| `KVS_RELAY_MAX_DURATION_MS` | `80000` | **일반 라이브뷰** 세션에 싣는 기기측 relay 한도 |
| `KVS_MAPPING_RELAY_MAX_DURATION_MS` | `600000` | **맵핑** 세션에 싣는 기기측 relay 한도. 목표는 `5400000`(90분)이고 **기기 반영 확인 후에만** 올린다 |

### 3-4. ★ 시간 제한이 여러 개다 — 어느 것이 무엇인지

원격 맵핑에서 "몇 초/몇 분"이 나오는 값이 많고 **서로 주체가 다르다.** 여기서 헷갈리면 엉뚱한 값을 만진다.

| 값 | 현재 | 누가 갖고 있나 | 무엇을 끊나 |
|---|---|---|---|
| **피어 유실 유예(grace)** | **5초** | 기기(LiveView) | 뷰어가 사라지고 5초 안에 재협상이 붙으면 **세션 유지 → 맵핑 이어감**. 못 붙으면 세션 종료 → 맵핑 취소. **이 5초가 화면 설계의 가장 큰 제약**이고, 늘리지 않기로 기기 담당과 합의했다 |
| **네트워크 유실 한도** | 60초 | 기기(LiveView) | 망 자체가 죽었을 때의 별도 한도. 유지 |
| **relay 연결 지속 상한(천장)** | **600초 (미상향)** | 기기(LiveView) `RELAY_TIME_LIMIT_MAX_MS` | 기기가 **수락하는 값의 범위 상한**. 서버가 이보다 큰 값을 실으면 기기가 범위 밖으로 보고 **기본값 80초로 되돌린다** |
| relay 값(라이브뷰) | 80초 | 서버가 세션마다 전달 | 일반 라이브뷰의 relay 지속 |
| relay 값(맵핑) | **600초. 목표 90분** | 서버가 세션마다 전달 | 맵핑 세션의 relay 지속. 상한 도달 = 세션 종료 = **작업 사망** |
| 서버측 relay 강제 종료 | 70초 | 서버 `relay-force-quit-seconds` | **일반 라이브뷰만.** 맵핑 세션은 서버가 relay 시간으로 끊지 않는다(UNLIMITED) |
| 서버 검증 천장 | 90분 | 서버 `DEVICE_RELAY_MAX_MS` | 설정값이 이 범위 밖이면 **부팅 실패**(§7-1 P0-②) |
| 뷰어 자격증명 유효 | 15분 | KVS STS | 이 시간이 지나면 새로고침해도 같은 세션으로 재연결 불가 |
| 맵핑 권장 마감 | 60분 | 서버 `MAPPING_WINDOW_MINUTES` → `mapping_expires_at` | **강제 종료가 아니라 화면 경고용.** 경고(60분) → 여유 → 상한(90분) 순서가 되도록 정했다 |

**relay 90분은 완화책이 아니라 전제조건이다.** 세션 종료 = 작업 사망이므로, 기기가 600초인 상태에서는 **10분 넘는 맵핑이 성립하지 않는다.** 90분의 근거는 "주행 최악 40분 + 복귀·업로드 여유 = 한 작업 최대 50분"이다.

⚠️ **배포 순서는 기기가 먼저다.** 서버가 먼저 90분을 실어 보내면 기기가 범위 밖으로 보고 80초로 되돌려 **늘리려던 것이 7.5배 짧아진다.** 서버는 코드 천장만 열어둔 상태이고, 기기 반영 확인 후 **env 한 줄**(`KVS_MAPPING_RELAY_MAX_DURATION_MS=5400000`)만 올리면 재빌드 없이 켜진다.

## 4. API 계약

### 4-1. 관제 웹 → `skix-security`: 맵핑 전용 KVS 세션 3종

```
POST   /security/v1/devices/{serial}/kvs/mapping-sessions              (Idempotency-Key 헤더 필수)
POST   /security/v1/devices/{serial}/kvs/mapping-sessions/{sessionId}/close
GET    /security/v1/devices/{serial}/kvs/mapping-sessions/{sessionId}
```

요청·응답 형태는 기존 `kvs/sessions`와 같다. 다른 점은 셋이다.

- **용도가 경로로 결정된다.** 클라이언트가 `purpose`를 보내지 않는다. 그래서 일반 화면에서 맵핑 권한을 요청할 수 있는 공격면이 존재하지 않는다.
- **프로바이더를 자사 AWS로 강제한다.** 일반 라이브뷰의 `provider` 설정과 무관하다.
- **구독 검증(`@SubscriptionRequired`)을 붙이지 않는다.** 자사 인프라를 쓰는 관제 대리 작업이고, **설치 시점처럼 구독 전에 맵을 만드는 것이 정상 시나리오**이기 때문이다. 어드민 게이트(`CONTROL_ROBOT` 권한)는 컨트롤러가 직접 세운다. 수명주기 3개 전부를 이 네임스페이스에 둔 이유는 create만 우회하면 "세션은 만들 수 있는데 종료·조회는 못 하는" 모순이 되고 relay 주기 재연결(close→create)까지 막히기 때문이다.

### 4-2. 관제 웹 → `backend-api-main`: 맵핑 작업 API 6종

`/api` 접두사 기준이다.

| 호출 | 경로 | 언제 |
|---|---|---|
| 시작 | `POST /control/robot/mapping-session/start` | body `{ serial, kvsSessionId }` |
| 완료 | `POST /control/robot/mapping-session/{id}/finish` | body `{ serial }`. **`ACTIVE`에서만** |
| 취소 | `POST /control/robot/mapping-session/{id}/cancel` | body `{ serial }` |
| 강제 종결 | `POST /control/robot/mapping-session/{id}/force-terminate` | body `{ serial, reason }` (reason 200자 이내). **운영자용 원장 정리 — 로봇에 명령이 나가지 않는다** |
| 상태 | `GET /control/robot/mapping-session/{id}/status?serial=...` | 진행 상태 폴링 |
| 활성 조회 | `GET /control/robot/mapping-session/active?serial=...` | 화면 재진입 시 이어하기 판단 |

**종료 계열은 모두 body에 `serial`이 필요하다.** id만으로 받지 않는다 — id가 연속값이라 관제 메뉴 권한만으로 다른 건물·다른 요원의 맵핑을 조작할 수 있기 때문이다.

응답은 기존 관제 API와 같은 형태다. HTTP 200 + envelope, 실패는 `data.result=false` + `DVRG` 코드.

**시작 응답(`data`)**

```jsonc
{ "result": true,
  "mappingSessionId": 12345,     // 이후 모든 호출의 {id}. STARTING 상태에서 이미 발급된다
  "correlationId": "uuid",
  "status": "STARTING",
  "mappingExpiresAt": "...",     // 권장 마감(경고용). 강제 종료 SLA가 아니다
  "presignedExpiresAt": "..." }
```

**상태 조회 응답(`data`)**

```jsonc
{ "result": true,
  "mappingSessionId": 12345, "serial": "...", "status": "ACTIVE",
  "correlationId": "uuid", "kvsSessionId": "...",
  "mappingExpiresAt": "...", "presignedExpiresAt": "...",
  "terminationType": null, "terminationReason": null,
  "slamStatus": "In Progress",   // 기기 보고. null이면 시작 명령이 로봇에 닿지 않았다는 신호
  "convertCode": null, "convertMessage": null, "convertedImageCount": 0 }
```

**진행률·완성도 필드는 없다** — 기기가 제공하지 않는다. 요원이 영상으로 판단한다.

**세션 상태값**

| 값 | 뜻 |
|---|---|
| `STARTING` | 시작 명령 발행 후 기기 확인 대기 |
| `ACTIVE` | 기기가 맵핑 중임이 확인됨 (`In Progress` 최초 수신으로 승격) |
| `ENDING` | 종료 명령 발행 후 기기 회신 대기 |
| `ENDED` | 지도 등록·변환까지 완료 |
| `CANCELLED` | 취소로 종결 (지도 없음) |
| `FAILED` | 완료되지 못하고 종료 — **사유에 따라 지도 유무가 다르다** |

**`FAILED`의 `terminationType` 4종** (화면이 구분해야 하는 것)

| 값 | 무슨 일이 | 지도는 | 요원 안내 |
|---|---|---|---|
| `DISCONNECT` | 연결이 끊겨 로봇이 맵핑을 취소 | **없음** | 처음부터 다시 |
| `SLAM_FAILURE` | 로봇이 SLAM 실패 보고 | **없음** | 처음부터 다시 |
| `UPLOAD_FAILURE` | 지도는 만들어졌는데 업로드·등록만 실패 | **로봇에 남아 있을 수 있음** | 재시도 여지 있음 — 문의 안내 |
| `FORCE` | 운영자가 원장을 강제 정리 | 상황에 따라 다름 | `terminationReason` 표시 |

**`UPLOAD_FAILURE`를 나머지와 섞으면 안 된다.** 40분 주행이 끝나고 지도까지 완성된 뒤 마지막 업로드만 실패한 경우인데, "처음부터 다시"로 안내하면 회수 가능한 작업을 버리게 된다.

**오류 코드**

| 코드 | 언제 | 화면 대응 |
|---|---|---|
| `DVRG0048` | 이미 원격 맵핑 진행 중 | "이어하기" 안내 → active 조회로 |
| `DVRG0049` | 로봇이 스테이션 밖 | "충전 스테이션에 도킹 후 시작할 수 있습니다" |
| `DVRG0003` | 발행 실패 / 아직 시작 확인 전(`STARTING`에서 `finish` 호출) | 재시도 안내 |
| `DVRG0000` | 로봇/세션 정보를 찾을 수 없음 | 일반 오류 |
| `DVRG0041` | 입력값 위반(serial 누락, reason 길이 초과 등) | 일반 오류 |

전원·배터리·바이탈사인·동작 상태 게이트는 **기존 관제 제어와 같은 코드를 그대로 쓴다.** 시작 허용 동작 상태는 `READY`·`CHARGING`·`DOCKING`·`STREAMING` 넷이다(관제 흐름이 KVS 세션을 먼저 열기 때문에 시작 시점 로봇은 이미 `STREAMING`인 경우가 정상이다).

### 4-3. 서버 → 기기: MQTT 전문

```
skmg/security/{serial}/v1/command/kvsSessionStart
{ "request": { ..., "controlPurpose": "REMOTE_MAPPING" | "LIVE_VIEW" } }

skmg/airbot/{serial}/v1/command/mapping
{ "request": { "slamCommand": "start", "slamType": "MANUAL", "pgmUrl": ..., "yamlUrl": ... } }
                                                        ← 원격 표식 없음. 기존과 동일한 모양
```

| 토픽 | 원격 맵핑 판정에 쓰나 | 역할 |
|---|---|---|
| `kvsSessionStart`의 `controlPurpose` | **유일한 판정 근거(SSOT)** | 조그 허용 · PUI 화면 억제 · 세션 종료 시 정리 |
| `mapping` (`slamCommand` start/end) | 안 씀 | SLAM 엔진 시작·종료 명령(기존 파이프라인 재활용) |

일반 세션에도 `LIVE_VIEW`를 **명시적으로** 싣는다 — 기기가 "미수신"과 "일반 라이브뷰"를 구분할 필요가 없게 하려고.

종료 명령은 둘로 갈린다.

| 요원 조작 | 서버가 보내는 것 | 기기에 기대하는 동작 |
|---|---|---|
| "맵핑 완료" | `comeback` (`missionFinYn: false`) | 스테이션 복귀 → 도착 시 지도 저장 → 업로드 |
| "취소" | 맵핑 종료 (`slamCommand: end`) | 지도 폐기 |

## 5. 되돌리면 안 되는 설계 결정

"더 단순해 보이게 바꾸면 사고가 나는" 것만 남겼다.

| # | 결정 | 바꾸면 생기는 일 |
|---|---|---|
| 1 | **맵핑 흐름에서 도킹 해제(undock)를 호출하지 않는다.** 맵핑 전용 undock 엔드포인트는 만들었다가 **삭제**했다(`20be6b8`) | 도킹 해제는 곧 "수동제어 시작"이라 로봇이 맵핑 상태를 이탈하고 **만들던 지도를 버린다.** 맵핑 시작 전문만 보내면 로봇이 스스로 언도킹하므로 명령 자체가 불필요하다. 관제 웹이 라이브뷰용 undock을 맵핑에서 호출해도 404다 |
| 2 | **원격 맵핑 판정은 `controlPurpose` 단 하나(SSOT).** 맵핑 전문에는 원격 표식(`source`)을 싣지 않는다 — 한 번 넣었다가 **제거**했다(`3f48f772`) | 판정 근거가 두 토픽에 흩어지면 도착 순서·부분 유실이 상태를 가른다. 세션이 항상 선행하는 것은 구조로 보장된다(관제 웹 시작 버튼이 DataChannel OPEN에서만 활성). 세션 없이 맵핑 시작만 도착하면 **기존 앱 맵핑으로 동작**해 PUI 화면이 뜨고 조그는 안 열린다 — fail-safe 방향이다 |
| 3 | **조그 권한은 세션 단위이고 확정 시점은 "세션 수락 성공"이다.** 로봇 상태나 작업 속성으로 대체 금지 | 맵핑 중 로봇은 동작 모드를 `NORMAL`로 보고하므로 **로봇 상태 기준이면 조그가 영영 안 열린다.** 작업 기준으로 열면 맵핑용 세션이 죽은 뒤 **일반 세션이 권한을 물려받는다.** 시작 요청 수신 시점에 저장하면 거부된 세션의 권한이 남는다 |
| 4 | **PUI 화면 억제는 "세션 실시간"이 아니라 "맵핑 시작 시점의 작업 래치"로 판단하고, 맵핑 종료(업로드/취소)까지 유지한다** | 실시간 세션 참조로 하면 **복귀 중 세션이 죽는 순간 억제가 풀리고**, 맵핑 진행 콜백이 런처로 나가며, 화면 없는 런처가 맵핑 정지를 재발행해 **완주한 지도가 저장 직전에 파괴된다.** 조그(세션과 함께 죽어야 함)와 화면 억제(맵핑과 함께 죽어야 함)는 수명이 다르다 — 같은 값을 보되 참조 방식이 갈린다 |
| 5 | **`ACTIVE` 승격은 기기의 `In Progress`(WOST0001) 최초 수신으로만 한다.** MQTT 발행 성공으로 승격하지 않는다 | MQTT는 qos 0이라 발행이 도달 증명이 아니다. `Started` 이벤트는 DeviceAgent 호출 **전에** 발행되므로 증거로 부적격이다. `finish`를 `ACTIVE`에서만 허용하는 것도 같은 이유 — 시작되지도 않은 맵핑을 "완료"시킬 수 없다 |
| 6 | **업로드 등록 여부 판별은 평문 SELECT가 아니라 CAS 4분기로 한다** | SELECT는 `finish` CAS와 직렬화되지 않고(REPEATABLE READ), `active_flag=1` 필터 조회는 **종결된 원격 세션을 "앱 발"과 구별하지 못해 무감독 지도가 등록된다**(강제 종결 후 늦은 업로드, `FAILED` 후 재전달, 구세션 재전달이 전부 실재 경로다). 분기는 A: `ENDING(FINISH)`→`ENDED` 등록 / B: `ENDING(CANCEL)`→`CANCELLED` 미등록 / C: `STARTING`·`ACTIVE`→`FAILED(DISCONNECT)` 미등록(방어) / D: 0건 → 미등록 + WARN |
| 7 | **등록과 상태 전이는 같은 트랜잭션이다.** 시작 3행(`remote_mapping_session`·`history_control`·`history_map`)도 하나의 트랜잭션으로 **발행 이전에** 커밋한다 | `history_map`이 없으면 기기가 올린 맵을 완료 처리가 조용히 폐기한다(로그만 남고 끝난다) — 완주한 맵이 영구 유실된다. `remote_mapping_session`이 없으면 `uk_rms_serial_active` 동시성 게이트가 안 걸려 중복 SLAM0001이 가능해진다. 선커밋 빈을 별도로 둔 것은 **같은 서비스 안에서 자기 메서드를 호출하면 `@Transactional` 프록시를 우회**하기 때문이다 |
| 8 | **취소 보고(`response/mapping{result:false, message:"SLAM Cancelled"}`)가 업로드 실패로 선점되지 않게 message로 라우팅한다** | 기기의 취소 경로는 이 메시지를 `SLAM_STATUS Cancelled` 이벤트보다 **먼저** 발행한다(발행 순서 실물 확인). 구분 없이 앞의 것을 `UPLOAD_FAILURE`로 종결하면 뒤의 취소가 no-op이 되어 **`DISCONNECT` 분류가 도달 불가**가 된다. 철자는 기기가 `Cancelled`, 서버 기존 매핑표가 `Canceled`라 **두 철자 모두 매핑**해 둔다 |
| 9 | **`ENDING`도 활성 세션 가드 대상으로 유지한다** | 풀면 맵핑 중인 로봇에 **두 번째 SLAM0001**이 허용된다. 강제 종결 API가 `ENDING`을 허용 상태에 넣은 것은 원장 정리용이고 로봇에 명령을 보내지 않는다 |
| 10 | **relay 상한은 서버가 먼저 올리지 않는다.** 코드 천장(90분)만 열고 wire 기본값은 600초로 유지 | 기기가 범위 밖 값을 받으면 기본값 80초로 되돌려 **오히려 7.5배 짧아진다.** 코드 배포만으로 wire 값이 바뀌면 기기 반영 전 배포가 곧 사고가 된다. 되돌리기는 재빌드 없이 env 한 줄이다 |
| 11 | **원격 맵핑 KVS 네임스페이스에 구독 검증을 붙이지 않는다** | 설치 시점처럼 **구독 전에 맵을 만드는 것이 정상 시나리오**다. create만 우회하고 close/GET에 남기면 "만들 수는 있는데 끄지 못하는" 모순이 되고 relay 주기 재연결(close→create)이 막힌다 |
| 12 | **`REMOTE_MAPPING_START_ALLOWED_STATES`를 공용 command-이름 switch에 넣지 않는다** | 그 switch는 `/control/robot/clean`이 **클라이언트 body의 command 값**을 그대로 넘겨 호출하며 default가 거절하는 화이트리스트다. 여기에 case를 추가하면 무관한 청정 엔드포인트가 `command="mappingStart"`를 통과시켜 청정 토픽에 알 수 없는 명령을 발행한다 |
| 13 | **신규 런타임 로그에 `serial`·`loginId`·`topic`을 남기지 않는다(backend-api-main 한정).** `sessionId`·`correlationId`만 남긴다 | 이 저장소의 dev 런타임 로그는 그 세 값이 0건인 것이 정책이다. **`skix-security`는 반대로 serial 로그가 29개 파일의 관례**라 그대로 둔다 — 저장소별로 다르다 |
| 14 | **원장에 "활성 시도 UNIQUE"를 두는 것이 여기서는 맞다** | 형제 테이블인 구독 신청 원장(`oasys_membership_apply_attempt`)은 일부러 UNIQUE를 안 두는데, **차이는 "종결을 눌러줄 사람이 있느냐"** 다. 원격 맵핑은 관제 UI의 강제 종결 API로 요원이 풀 수 있어 영구 잠김이 생기지 않는다 |

## 6. 타 팀에 요청한 내용 (요청서 3종 핵심)

기기·프론트·AMR 코드는 직접 수정하지 않았다. 아래가 각 담당자에게 전달한 요청의 핵심이다. 형식은 지시서가 아니라 **"문제 + 제안 + 검토 요청"** 이고, 인수자의 역할은 이 내용이 실제 구현과 맞는지 확인하는 것이다. 실제 구현 상태는 §2-4에 정리했다.

### 6-1. AMR 담당 — 코드 변경 요청 0건, 전제 확인 + 실측

**전제 3가지를 확인해 달라고 했다.**

1. 수동 맵핑 상태에서 속도 명령이 들어오면 AMR이 그냥 처리하는가(조그를 막는 곳이 AMR에는 없는가)
2. 맵핑 시작만 보내면 스테이션에서 알아서 빠져나오는가 — 도킹 해제를 따로 보내지 않아도 되는가(오히려 보내면 지도가 버려지는가)
3. 지도 저장 트리거가 "복귀 도착"이고, 맵핑 취소로 끝나면 저장하지 않는가

**실측 4건을 부탁했다.** A: 복귀→도착→저장→업로드가 실제로 이어지는지 / B: 수동 맵핑 상태에서 속도 명령 시 **실제로 바퀴가 도는지** / C: 조그 명령이 끊겼을 때 **몇 초 만에 정지하는지**(데드맨) / D: 장애물·keepout 정지 시 상위로 통지가 올라오는지(콜드부팅 직후와 수동제어를 거친 뒤 두 조건에서).

**회신 결과 (2026-08-19) — 전건 완료**

| | 결과 |
|---|---|
| 전제 (1) | **✖ 틀렸다.** AMR이 **라이브뷰(수동제어) 상태에서만 조그 입력을 처리**하고 있었다. AMR 담당이 **수동 맵핑에서도 속도 명령을 처리하도록 수정**했고 바퀴가 도는 것까지 확인. → **AMR 펌웨어가 배포 대상에 추가됐다** |
| 전제 (2) | ✔ 확인 |
| 전제 (3) | ✔ **둘 다 확인** — 취소는 저장 없음, 저장은 도착 트리거 |
| 실측 A | ✔ 복귀→도착→저장→업로드→변환→**자동 맵 분할**까지 확인 |
| 실측 B | ✔ 수정 후 바퀴 회전 확인 |
| 실측 C | ✔ **데드맨 1~2초**(속도에 따라). 맵핑 주행은 저속이고 요원이 영상으로 감독하므로 **수용 확정** |
| 실측 D | ✔ **통지가 올라오지 않는다** — 수동 맵핑 중 장애물·금지구역 에러코드가 정의돼 있지 않다. 에러코드 정의 + 개발이 별도로 필요해 **확대 시점 백로그로 수용** |

또한 "세션이 끊기면 기기가 맵핑 취소 후 스테이션 복귀를 지시한다"는 정책과 "맵핑 중 RF 리모컨이 열려 있는 것"에 대한 의견을 물었고, 둘 다 수용됐다(RF는 내부 인원 대상이라 공지로 감수).

### 6-2. 기기 담당 (`packages-mr7` + `liveliew`) — 6건

> 두 저장소를 한 담당자가 맡고 있어 요청서를 하나로 합쳤다. 합치니 조그 경로가 세 산출물(DeviceAgent·LiveView·SDK)에 걸친 하나의 사슬로 읽힌다 — 나눠져 있을 땐 받는 쪽이 조립해야 했다.

| | 요청 | 성격 |
|---|---|---|
| **①** | **원격 맵핑 세션에서는 맵핑 중에도 조그가 통과해야 한다** | 이게 되어야 나머지를 실기로 검증할 수 있다 |
| **②** | **PUI 맵핑 화면 미표시 + 억제를 맵핑 종료까지 유지(래치)** | **지도 보호 — 요청의 핵심** |
| **③** | 세션 종료 시 맵핑 취소 + 스테이션 복귀 | 합의 확인 (복귀 호출 활성화 여부만) |
| **④** | 복귀 구간 세션 부수효과 가드 | **권장** — 없어도 기능은 돈다 |
| **⑤** | relay 지속 상한 600초 → **90분(5,400,000)** | 값 요청 하나. **실사용 가능 시점을 정하는 항목** |
| **⑥** | 현장 안내 문구 분기 | 마지막에 붙여도 됨 |

**① 조그** — 지켜져야 하는 것 셋: (i) **일반 라이브뷰 조그는 지금 그대로**(조건을 더하는 것이지 바꾸는 게 아니다) (ii) **원격 맵핑 목적 세션에서만** 맵핑 중 조그 허용("맵핑 중이면 허용"으로 열면 고객이 PUI로 맵핑할 때 일반 라이브뷰에서도 열린다) (iii) 세션이 끝나면 **그 권한도 함께 사라진다.** 로봇 상태로는 판단할 수 없다(맵핑 중 `NORMAL` 보고). 전달 경로에 AIDL과 프리빌트 AAR이 끼어 있어 **확장 방식(인자 추가 vs 새 메서드)과 세 산출물 동시 배포 여부는 담당자 판단에 맡기되, 어느 쪽인지는 알려달라**고 했다(릴리스 계획이 갈린다).

**② PUI 화면 억제** — 함정을 공유했다: 출하 런처가 **맵핑 화면이 없는 상태에서 맵핑 진행 콜백을 받으면 맵핑 정지를 재발행**한다. 그래서 "화면을 억제"가 아니라 **"화면 쪽으로 가는 신호 자체를 보내지 않는" 방향**이어야 한다. 그리고 **억제 판정을 "지금 세션이 살아 있는가"로 실시간 판단하면 안 된다** — 복귀 중 세션이 끊기면 억제가 풀려 40분 작업이 저장 직전에 사라진다. **맵핑 시작 시점에 원격 세션이었는지를 래치로 기억하고 맵핑 종료까지 유지**해 달라고 요청했다.

**③ 세션 종료 = 맵핑 종료** — 짧은 단절(유예 안에 재연결)은 이어가고, **그 외 세션 종료는 사유 불문 맵핑 취소.** 예외를 두지 않는다("맵핑은 도는데 요원 화면은 없는 상태"를 정상 흐름에 만들지 않기 위해). 취소는 **기존 `MapCancelled` 경로로 발행**해 달라고 했다 — SLAM 엔진만 직접 멈추면 서버에 아무 신호가 안 와 원장이 "진행 중"으로 남는다. 취소 판정을 **DeviceAgent 내부 맵핑 플래그가 아니라 로봇 상태로** 하면 복귀 구간이 자동 제외된다는 것도 함께 공유했다(복귀 중 로봇 상태는 `RETURN_CHARGER`인데 지도 저장 조건은 SLAM 노드 생존을 보기 때문). 현행 코드의 맵핑 종료 분기에서 **복귀 호출이 주석 처리**되어 있어 그대로면 "취소 후 정지"가 된다는 점도 지적했다.

**④ 복귀 구간 가드(권장)** — KVS 세션이 시작될 때 기기가 **진행 중이던 동작을 정리**하고 off-station이면 수동모드로 전환하는 부수효과가 있다. 복귀 중에 걸리면 복귀가 끊겨 도착·저장이 없어진다. 관제 화면 쪽은 "복귀 중 재연결 금지" 규칙으로 막지만 **고객 앱 라이브뷰가 열리는 경우는 못 막으므로**, ②의 래치가 참인 동안 두 부수효과를 건너뛰어 달라고 했다. **로봇 상태(복귀 중인가)로 판단하지 말 것** — 스케줄 복귀·앱 발 복귀까지 동작이 바뀌어 기존 라이브뷰에 영향이 간다.

**⑤ relay 90분** — "천장만 올리는 것"이고 실제 값은 세션마다 서버가 싣는다. 일반 라이브뷰는 계속 80초가 나가 동작이 그대로다. **배포는 기기가 먼저**임을 명시했다. 피어 유실 유예 5초는 기기 판단을 존중해 유지하기로 했다.

**⑥ 안내 문구** — 현행("현재 스트리밍 중입니다 / 하이나무 앱과 연결되어 있으며. 음성 소통이 가능합니다.")은 원격 맵핑에서 사실과 다르다. 제안: **"로봇이 원격으로 지도를 만들고 있습니다 / 관제센터에서 조작 중이며 카메라 영상이 전송됩니다. 로봇의 이동을 막지 말아 주세요."** 현장 인원의 실제 의문 셋(왜 움직이나 / 카메라가 켜져 있나 / 막아도 되나)에만 답한다. "점검 중" 같은 완곡어는 고장 수리로 읽혀 오해를 부른다. **실시간 맵 미리보기는 넣지 말 것** — 그리려면 ②에서 막는 그 신호를 흘려야 한다.

**요청 순서**: ① 조그 → ② 화면·래치 → ③ 세션 종료 시 취소·복귀 → ④ 복귀 가드 → ⑥ 문구. ⑤ relay는 독립이라 병행 가능하되 **실사용에는 이것이 먼저 반영돼야 한다.**

### 6-3. 관제 프론트 담당 (`frontend-web-backoffice`) — 7건

기존 KVS 뷰어(영상·데이터채널·조이스틱·세션 발급) 위에 얹는 형태로 요청했다.

| | 요청 | 핵심 |
|---|---|---|
| D-1 | 맵핑 전용 세션 경로 사용 | `kvs/sessions` → `kvs/mapping-sessions`. 형태 동일 |
| D-2 | 맵핑 작업 API 연동 | start / finish / cancel / status / active (§4-2) |
| D-3 | **조그 활성화 기준이 라이브뷰와 다르다** | 로봇 모드를 보지 말고 **세션 상태 + DataChannel OPEN**으로 판단. 맵핑 중엔 `NORMAL`이 와서 기존 기준으론 영영 안 열린다. ⚠️ **기존 라이브뷰 기준은 그대로 둘 것** — 공용 조건에서 모드 검사를 빼면 라이브뷰에서 도킹 중인 로봇에도 조그가 열린다 |
| D-4 | 종료 버튼 2개 | "맵핑 완료"(`ACTIVE`에서만) / "취소"(항상). "완료"가 처음 몇 초간 비활성인 것은 서버가 기기 시작 신호를 받은 뒤에만 허용하기 때문(통상 10초 내외, 그동안 조그는 열려 있다) |
| D-5 | 종료 전 로봇 먼저 정지 | **종료 API가 나가기 전에 정지 명령이 전송되고 이후 조그 입력이 더 나가지 않을 것**. 구현 순서는 맡김 |
| D-6 | 맵핑 흐름에서 도킹 해제 호출 금지 | 호출하면 만들던 지도가 버려진다. 서버 엔드포인트도 제거했으므로 호출해도 404 |
| D-7 | **단절 UI + 세션 보전 3종** | 아래 |

**D-7 세션 보전 3종** — (i) **이탈 방지**: 새로고침·탭 닫기·뒤로가기에 확인 대화상자(`beforeunload`). 재연결 복구가 되든 안 되든 1차 방어다. (ii) **페이지를 떠날 때 세션 종료 API를 호출하지 말 것** — 명시적으로 닫으면 5초 유예조차 없어지고 재연결 경로도 막힌다. 그냥 두면 로봇이 5초를 기다려준다. (iii) **세션이 완전히 끝난 뒤 자동 재발급을 반복하지 말 것** — 새로 발급받아도 그건 새 작업이라 맵핑이 이어지지 않는다.

**D-7 복귀 구간 규칙 (가장 중요)** — "맵핑 완료" 후 로봇이 복귀하는 몇 분 동안 지도는 아직 저장 전이다. 이 구간에 **세션을 먼저 닫지도, 끊겼더라도 다시 열지도 말 것.** 재연결하면 기기가 진행 중이던 동작을 정리하면서 복귀가 끊기고 40분 작업이 저장 직전에 사라진다. 재연결로 얻는 것은 영상뿐이고(복귀 중엔 조그가 어차피 잠긴다) 복귀는 스케줄 복귀와 같은 일상 동작이다. **진행 표시는 상태 조회 폴링으로**(`ENDING` → `ENDED`면 완료), **세션 종료는 `ENDED` 확인 후.** 요원이 화면을 떠나는 것은 막지 않아도 된다(관제 업무 방해) — 다만 **복귀 중인 로봇 화면에 다시 들어왔을 때 KVS 세션을 자동으로 열지 말 것.** `active` 조회로 `ENDING`을 확인하면 영상 없이 진행 상태만 보여주는 화면으로 들어가면 된다.

**시작 버튼 조건** — DataChannel OPEN **+ 로봇이 스테이션에 도킹**. 스테이션 밖에서 시작하는 경우를 아예 만들지 않는 것이 설계 전제다. 최종 판정은 서버가 하므로(폴링 시차가 있다) 버튼 비활성화는 요원 편의용으로만 쓰고 **판정은 서버 응답 코드로** 받는 편이 안전하다.

**화면에 표시할 수 없는 것 3가지도 미리 공유했다** — 맵핑 진행률·완성도, 조그 실패 여부(기기가 항상 성공을 반환한다), 장애물·keepout 정지 사유.

## 7. 배포 방법

### 7-1. ★ 배포 전 차단 이슈 (P0) — 둘 다 확인 전 배포 금지

**P0-① `security.kvs_session_history.purpose` ALTER를 이미지보다 먼저 적용한다.**

`insertClaimed`가 `purpose` 컬럼을 무조건 나열하는데, 그 경로는 맵핑 전용이 아니라 **모든 KVS 세션 생성의 공통 경로**다. 컬럼 없이 새 이미지가 뜨면 `Unknown column 'purpose'`가 전파되어 **고객 앱 라이브뷰까지 전량 실패**한다. **부팅은 성공하고 런타임에 터지므로 헬스체크로도 안 걸린다.**

```sql
-- 확인 (환경별 1회)
SHOW COLUMNS FROM `security`.`kvs_session_history` LIKE 'purpose';

-- 없으면 (무중단 additive ALTER)
ALTER TABLE `security`.`kvs_session_history`
    ADD COLUMN `purpose` varchar(32) NULL
        COMMENT '세션 용도 - NULL이면 일반 라이브뷰, REMOTE_MAPPING이면 관제 원격 맵핑(자사 AWS 강제 + relay 무제한)'
    AFTER `admin_login_id`;
```

역순(DDL 먼저, 구 이미지 유지)은 안전하다 — 구 이미지는 새 컬럼을 모르는 채 기존 동작을 그대로 한다. 되돌릴 일이 생기면 이미지만 롤백하면 된다.

**P0-② 배포 전 세 환경 태스크 정의의 `KVS_RELAY_MAX_DURATION_MS` 실값을 확인한다.**

이번 변경으로 **라이브뷰 relay 값도 기기 수락 범위(10초~90분)로 부팅 검증**을 받게 됐다. 범위 밖 값이 설정돼 있으면 **부팅이 실패**한다. ECS 롤링이라 구 리비전이 계속 서비스하므로 장애로 보이지는 않지만 배포가 나가지 않는다.

- **미설정이면 안전하다** — 코드 기본값 80,000이 범위 안이다.
- 설정돼 있으면 값이 `10000` ~ `5400000` 안인지 확인한다.
- `KVS_MAPPING_RELAY_MAX_DURATION_MS`도 같은 검증을 받는다. **600,000을 넘기면 부팅 WARN이 남는다**(기기 미반영 상태에서 올렸다는 경고). 기기 반영 확인 전에는 올리지 않는다.

### 7-2. 순서

```
1. DB DDL                ← 반드시 이미지보다 먼저 (P0-①)
   ① security.kvs_session_history.purpose ALTER
   ② remote_mapping_session 테이블 (이미 있으면 생략 — §2-3)
2. skix-security 배포    ← ①의 짝
3. backend-api-main 배포 ← ②의 짝
4. 관제 프론트 / 기기 3종 / AMR 펌웨어   ← 별도 담당자
```

①↔②는 서로 독립이라 순서가 상관없고, **각각의 짝(①-2, ②-3)만 지키면 된다.** 2와 3 사이에는 배포 순서 제약이 없다 — 두 서버 사이에 직접 호출이 없고 관제 웹이 각각을 부른다.

**운영계는 `backend-api-main` main 승격이 선행돼야 한다**(§2-1). `skix-security` main 승격 시 §2-1의 선별 반영 주의사항을 반드시 확인할 것.

### 7-3. 배포 후 검증

```sql
-- 1) 컬럼·테이블 존재 (P0-① 사후 확인)
SHOW COLUMNS FROM `security`.`kvs_session_history` LIKE 'purpose';
SHOW CREATE TABLE `remote_mapping_session`;

-- 2) 생성 컬럼이 의도대로 도는지 — serial당 활성 세션 1개를 보장하는 장치다
INSERT INTO `remote_mapping_session`
  (serial, building_id, status, admin_login_id, mapping_expires_at)
  VALUES ('DDL-CHECK', 1, 'ACTIVE', 'ddl-check', NOW());
SELECT id, status, active_flag FROM `remote_mapping_session` WHERE serial='DDL-CHECK';
  -- active_flag = 1 이어야 한다
UPDATE `remote_mapping_session` SET status='ENDED' WHERE serial='DDL-CHECK';
SELECT id, status, active_flag FROM `remote_mapping_session` WHERE serial='DDL-CHECK';
  -- active_flag = NULL 이어야 한다 (종결되면 다음 맵핑이 열린다)
DELETE FROM `remote_mapping_session` WHERE serial='DDL-CHECK';
```

**기존 경로 회귀가 이 배포의 핵심 검증 지점이다.**

| 확인 | 왜 |
|---|---|
| **일반 라이브뷰 세션 생성** (앱에서 실제 영상 연결) | `purpose` 컬럼이 공통 경로에 끼어들었다. 여기가 깨지면 P0-①이다 |
| **일반 라이브뷰 조그** | 조그 게이트에 OR 항이 추가됐다. 기존 조건이 그대로인지 |
| **앱 발 SLAM 맵핑** 한 건 전체 | 맵 등록 지점(`ResponseDeviceService.mapping()`)에 CAS 분기가 추가됐다. 원장에 행이 없으면 기존 경로로 등록되어야 한다(분기 ①) |
| 기존 관제 제어(청정·복귀 등) | 시작 조건 게이트를 공용 코드에 위임했다 |
| 맵핑 세션 생성 → `kvs_session_history.purpose = 'REMOTE_MAPPING'` 기록 확인 | 신규 경로 스모크 |
| 맵핑 API 6종이 `DVRG` 코드를 정상 반환 | 신규 경로 스모크 |

### 7-4. 롤백

- **애플리케이션**: 이전 이미지로 되돌린다. 신규 API만 추가된 배포라 기존 기능 영향 없음.
- **DB**: **컬럼·테이블을 되돌리지 않는다.** 구 이미지는 둘 다 모르는 채 기존 동작을 그대로 하고, 맵핑 시도 기록은 조사 자료가 된다.
- **relay 값**: env 한 줄을 되돌리면 된다(재빌드 불필요).

## 9. 운영 중 자주 만날 상황

### 9-1. 조회 쿼리

```sql
-- 특정 로봇의 최근 맵핑 이력
SELECT id, status, termination_type, termination_reason, terminated_by,
       admin_login_id, correlation_id, kvs_session_id, create_date, update_date
  FROM remote_mapping_session
 WHERE serial = '<serial>'
 ORDER BY id DESC LIMIT 10;

-- 지금 활성인 세션 전부 (고아 세션 점검)
SELECT id, serial, status, admin_login_id, create_date, mapping_expires_at
  FROM remote_mapping_session
 WHERE active_flag = 1
 ORDER BY create_date;

-- KVS 세션이 맵핑용으로 발급됐는지
SELECT id, serial, purpose, admin_login_id, create_date
  FROM security.kvs_session_history
 WHERE serial = '<serial>' ORDER BY id DESC LIMIT 5;
```

### 9-2. 상황별 대응

| 상황 | 확인·대응 |
|---|---|
| "맵핑 시작했는데 로봇이 안 움직여요" | 상태 조회의 **`slamStatus`가 계속 `null`이면 시작 명령이 로봇에 닿지 않은 것**이다(MQTT qos 0). `cancel`로 회수하고 재시작 |
| "조그가 안 돼요" | 네 계층이 다 맞아야 열린다 — 관제 화면(세션 상태 + DataChannel OPEN) / LiveView / DeviceAgent(세션 목적 + 로봇 물리 상태) / AMR 펌웨어. **기기 3종·AMR 중 하나라도 미배포면 안 열린다**(§8-2). `kvs_session_history.purpose`가 `REMOTE_MAPPING`인지부터 본다 |
| "완료를 눌렀는데 버튼이 비활성이에요" | `ACTIVE` 승격 전이다. 승격은 기기의 진행 신호 최초 수신 시점이고 통상 10초 내외 걸린다. 그동안 조그는 열려 있다 |
| **`STARTING`·`ACTIVE`·`ENDING` 잔존 (고아 세션)** | §9-3 런북 |
| `FAILED` + `DISCONNECT` | 연결이 끊겨 로봇이 맵핑을 취소했다. **지도는 없다.** 로봇은 스테이션으로 복귀한다. 처음부터 다시 |
| `FAILED` + `UPLOAD_FAILURE` | **지도가 로봇에 남아 있을 수 있다.** "처음부터 다시"라고 안내하지 말 것 |
| 맵핑 중 로봇 화면에 맵핑 화면이 뜬다 | PUI 콜백 게이트(요청 ②)가 미반영이거나 래치가 풀린 것이다. **첫 콜백에 런처가 맵핑을 자동 취소할 수 있으므로 즉시 확인 대상**이다. 로그 단서: `"Received mapping data after STOP MAPPING"` |
| relay 경유 통합 테스트 중 10분에 끊긴다 | **기기 상한이 600초인 상태에서는 정상이다**(§3-4). 90분 반영 후에 다시 본다 |
| 서버 로그 키워드 | `remote mapping started` / `promoted to ACTIVE` / `finish requested` / `cancel requested` / `cancel republished` / `force terminated` / `upload discarded (cancelled)` / `upload not registered (disconnected)` / `upload not registered (already terminal)` / `session converged` |

### 9-3. 수동 복구 런북 (고아 세션)

```
1. 활성 세션 확인   GET /control/robot/mapping-session/active?serial=...
2. 기기 상태 확인   status 응답의 slamStatus + 영상·현장으로 실제 맵핑 여부 판단
3. 맵핑 중이면      cancel 재호출 — 단, STARTING·ACTIVE 에서만
4. 맵핑 아니면      force-terminate 로 FAILED 확정 (사유 필수, 200자 이내)
```

⚠️ **`ENDING(FINISH)`에는 `cancel`을 쓰지 않는다.** `cancel`의 허용 상태에 `ENDING`이 포함돼 있어 호출하면 `termination_type`이 FINISH → CANCEL로 뒤집히고, **뒤늦게 도착한 완주 지도가 CAS 분기 B로 떨어져 폐기된다.** `ENDING`의 회수는 강제 종결 API로 한다.

⚠️ **start 후 약 10초(로봇이 실제로 맵핑을 도는 상태에 들기 전) 구간의 단절은 기기가 스스로 멈추지 않는다.** 로봇이 아직 언도킹 중이라 취소 조건이 거짓이기 때문이다. 이 구간의 고아 세션은 `cancel`로 회수한다. 감독 없는 맵핑이 시작되는 유일한 구간이고, 스테이션 시작 원칙 덕에 약 10초로 좁혀져 **수용하기로 확정**한 항목이다.

⚠️ **기기에서 맵핑이 끝났다는 증거 없이 강제 종결하지 않는다.** 활성 가드를 풀면 맵핑 중인 로봇에 두 번째 SLAM0001이 허용된다. **강제 종결은 원장 정리 전용이며 로봇에 명령을 보내지 않는다.**

### 9-4. 구조적으로 수용한 것 (문의가 들어와도 "의도"다)

- **세션 종료 = 작업 종료.** 유예 5초를 넘긴 어떤 단절도 그때까지의 지도를 폐기한다. 부분 지도 회수 경로는 없다.
- **PUI 고지는 KVS 안내 문구뿐.** 맵핑 전용 화면·진행 표시가 없고, 세션이 닫히면 안내 화면도 내려간다.
- **로봇 화면에서 맵핑을 멈출 수단이 없다.** 원격 취소가 유일하다 — 지나가던 사람이 무심코 눌러 40분 작업이 날아가는 쪽을 더 위험하다고 봤다.
- **맵핑 중 RF 리모컨이 열려 있다.** 원격 조그와 현장 리모컨이 동시에 열릴 수 있다. 내부 인원 대상이라 공지로 감수한다.
- **단절 후 복귀 구간은 안내 화면이 내려간 상태**라 무고지 자율 주행이다(스케줄 복귀와 같은 동작이라 수용).
- **원격 맵핑 세션이 열려 있는 동안 앱 발 맵핑이 시작되면 기기가 원격으로 오분류한다**(화면 억제 + 조그 허용). 판정을 `controlPurpose` 하나로 통일하면서 남은 유일한 케이스이고, 내부 cohort·요원 감독 전제로 수용했다.

## 부록 B. DDL 전문 (개발계 기준)

아래는 개발계에 적용한 원문이다. **검증계·운영계는 스키마명만 다르다** — dev는 `airbotdev`, stg·prd는 `benjamin`이다(dev의 `application-dev.yml` jdbc-url이 `.../airbotdev`이고, 매퍼가 스키마 접두사 없이 테이블명만 쓰므로 **접속 스키마에 생성**되어야 한다). §2-3에 적었듯 stg·prd에는 이미 적용돼 있는 것으로 보이므로 **적용 전 존재 여부부터 확인**한다.

```sql
-- =============================================================================
-- 관제 원격 맵핑 — 개발계(dev) DDL
--
-- ⚠️ 배포 순서: 이 SQL을 애플리케이션 이미지보다 **먼저** 적용한다.
--    ① → skix-security 배포   ② → backend-api-main 배포
--    ①↔②는 서로 독립이라 순서가 상관없고, 각각의 짝만 지키면 된다.
--
-- ⚠️ 역순(DDL 먼저, 구 이미지 유지)은 안전하다 — 구 이미지는 새 컬럼/테이블을
--    모르는 채로 기존 동작을 그대로 한다. 되돌릴 일이 생기면 이미지만 롤백하면 된다.
-- =============================================================================


-- -----------------------------------------------------------------------------
-- ① security DB — kvs_session_history 에 purpose 컬럼 추가
--
-- ★ 이것이 두 변경 중 위험한 쪽이다.
--   insertClaimed 가 purpose 를 무조건 나열하는데, 그 경로는 맵핑 전용이 아니라
--   **모든 KVS 세션 생성의 공통 경로**다. 컬럼 없이 새 이미지가 뜨면
--   Unknown column 'purpose' 가 전파되어 **고객 앱 라이브뷰까지 전량 실패**한다.
--   부팅은 성공하고 런타임에 터지므로 헬스체크로도 안 걸린다.
--
-- 무중단 additive ALTER (환경당 1회)
-- -----------------------------------------------------------------------------

ALTER TABLE `security`.`kvs_session_history`
    ADD COLUMN `purpose` varchar(32) NULL
        COMMENT '세션 용도 - NULL이면 일반 라이브뷰, REMOTE_MAPPING이면 관제 원격 맵핑(자사 AWS 강제 + relay 무제한)'
    AFTER `admin_login_id`;

-- 확인
-- SHOW COLUMNS FROM `security`.`kvs_session_history` LIKE 'purpose';


-- -----------------------------------------------------------------------------
-- ② airbotdev DB — remote_mapping_session 테이블 신규 생성
--
-- ⚠️ dev 의 스키마명은 `airbotdev` 다 (stg·prd 는 `benjamin`).
--    application-dev.yml 의 jdbc-url 이 .../airbotdev 이고, 매퍼가 스키마 접두사
--    없이 테이블명만 쓰므로 **접속 스키마에 생성**되어야 한다.
--
-- 신규 테이블이라 기존 경로에 영향이 없다 — 없으면 원격 맵핑 API 만 실패하고
-- 라이브뷰·앱 맵핑·기존 관제는 그대로 돈다.
--
-- prod.sql / stg.sql 의 정규화 DDL 과 동일하며, DROP 은 넣지 않았다.
-- -----------------------------------------------------------------------------

CREATE TABLE IF NOT EXISTS `airbotdev`.`remote_mapping_session` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '일련번호',
  `serial` varchar(50) NOT NULL COMMENT '제품일련번호',
  `building_id` bigint NOT NULL COMMENT '건물아이디 - serial에서 서버 해석(클라이언트 입력 불허). NULL이면 완료 처리가 맵 등록 대상을 잃어 맵이 유실되므로 NOT NULL',
  `correlation_id` varchar(50) DEFAULT NULL COMMENT 'SLAM 제어 correlationId - history_control/history_map과 연결',
  `kvs_session_id` varchar(36) DEFAULT NULL COMMENT 'skix-security KVS 세션 UUID - 감사 및 재진입 복구 시 close 대상',
  `status` varchar(20) NOT NULL COMMENT 'STARTING/ACTIVE/ENDING/ENDED/CANCELLED/FAILED. ACTIVE는 기기의 진행 신호 최초 수신으로 승격한다 - MQTT 발행 성공은 기기가 시작했다는 증명이 아니므로 발행 시점에는 승격하지 않는다',
  `admin_login_id` varchar(20) NOT NULL COMMENT '수행 관제 요원 - history_control.login_id와 같은 폭',
  `mapping_expires_at` datetime NOT NULL COMMENT '운영상 권장 마감 - 강제종료 SLA가 아니며 관제 화면이 경고를 표시한다',
  `presigned_expires_at` datetime DEFAULT NULL COMMENT '맵 업로드 presigned URL 실효 만료 - 마감 판단 근거',
  `termination_type` varchar(20) DEFAULT NULL COMMENT '종료 분류 FINISH/CANCEL/DISCONNECT/FORCE/SLAM_FAILURE/UPLOAD_FAILURE - ENDING 전이 시 확정하며 맵 업로드 도착 시 등록 여부를 가른다(FINISH만 등록). UPLOAD_FAILURE는 지도가 로봇에 남아 재시도 여지가 있는 경우다',
  `termination_correlation_id` varchar(50) DEFAULT NULL COMMENT '종료 명령(복귀/취소)의 correlationId - 시작 키와 분리 보존한다. 기기 회신이 어느 키로 오는지 확정 전이라 둘 다 보관',
  `cancel_republished` tinyint(1) NOT NULL DEFAULT '0' COMMENT '취소 재발행 표식 - 취소 종료 중 진행 신호를 받으면 취소를 1회만 재발행하기 위한 잠금. 없으면 신호 주기마다 무한 발행된다',
  `termination_reason` varchar(200) DEFAULT NULL COMMENT '종료 사유 - 강제 종결은 필수 입력, 단절 종료는 서버가 기록',
  `terminated_by` varchar(20) DEFAULT NULL COMMENT '종료 수행자 로그인 아이디 - 강제 종결 감사용. admin_login_id와 같은 폭',
  `active_flag` tinyint GENERATED ALWAYS AS (if((`status` in (_utf8mb4'STARTING',_utf8mb4'ACTIVE',_utf8mb4'ENDING')),1,NULL)) VIRTUAL COMMENT '활성 세션 표식 - 종결 상태에서 NULL이 되어 UNIQUE 중복을 허용한다',
  `create_date` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '생성일시',
  `update_date` datetime DEFAULT NULL COMMENT '수정일시',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_rms_serial_active` (`serial`,`active_flag`),
  KEY `idx_rms_correlation` (`correlation_id`),
  KEY `idx_rms_serial_create` (`serial`,`create_date` DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='관제원격맵핑세션';
```

## 부록 C. 설계를 강제한 코드 사실

밖에서 읽어 확인한 것들이다. 설계 결정을 다시 검토할 때 근거를 찾는 시간을 줄이려고 남긴다. **파일·줄 번호는 2026-08 시점 기준이라 지금은 밀렸을 수 있다.**

| 계층 | 사실 |
|---|---|
| AMR | `ONSTATION` → `UNDOCKING` → `MANUAL_MAPPING`으로 **자동 언도킹**한다 (`state_manager.cpp`) |
| AMR | `MANUAL_MAPPING` → `MANUAL_CONTROL` 전이가 허용된다 = **도킹 해제가 지도 파괴 경로**다 (`state_manager.cpp`) |
| AMR | 지도 저장 조건은 **로봇 상태가 아니라 SLAM 노드 상태**를 본다 — `ARRIVED_GOAL` + `NODE_STATUS::MANUAL_MAPPING` → `map_saver()` (`return_charger.cpp`). 복귀 중 로봇 상태는 `RETURN_CHARGER`로 바뀌므로, **취소 판정을 로봇 상태로 하면 복귀 구간이 자동으로 제외**된다 |
| AMR | 맵핑 중 `publishRemoteBlock(false)` — **RF 리모컨이 열려 있다** (`manual_mapping.cpp`) |
| AMR | 취소는 저장하지 않는다 (`manual_mapping.cpp`) |
| DeviceAgent | `setKvsSessionActive(true)`의 부수효과 2개 — `stopAllAction`(복귀 중단)과 off-station 시 `changeAmrManualMode`(미저장 지도 소멸) (`StreamingManager.java`) |
| DeviceAgent | 지도 없는 로봇은 세션 시작이 거부된다(`"No MAP - Off Station"`). **완화를 요청하지 않았다** — 잃는 것이 감시뿐인데 precondition 완화는 위험 등급이 다르다 |
| DeviceAgent | 맵핑 플래그(`IS_STARTMAPPING`)는 **업로드까지 참**이라 복귀 중 취소를 발동시킨다 — 취소 판정에 쓰면 안 된다 |
| DeviceAgent | 맵핑 중에는 이동 관련 화면도 안 뜬다(이동 상태 콜백 조기 return). 이 플래그는 게이트 대상 콜백보다 **앞에서** 세팅되므로 콜백을 막아도 유지된다 → **맵핑 구간 내내 안내 화면이 유일한 화면**이 된다 |
| IotAgent | 맵핑 토픽은 DTO 선별 복사라 **미지 필드가 관통하지 않는다**. KVS 토픽은 JSON에서 직접 꺼내 읽어 **미지 필드에 안전**하다 — "이 저장소는 이렇다"가 아니라 **경로별로 다르므로 각각 확인해야 한다** |
| 런처 | **맵핑 화면이 없는데 맵핑 진행 콜백이 오면 맵핑 정지를 재발행**한다 — "화면만 안 띄우는" 접근은 첫 콜백에서 지도를 파괴한다. 이 자동 취소는 두 런처 버전 중 한쪽에만 있지만, **콜백 게이트는 양쪽 모두에서 안전**하므로 설계가 런처 버전에 의존하지 않는다 |
| 런처 | 맵핑 완료 콜백은 화면 부재 시 조용히 무시된다 — 게이트 불필요 |
| LiveView | `RELAY_TIME_LIMIT_MAX_MS` 600초 / 피어 유실 유예 5초 / **범위 밖 값이면 기본값 80초로 되돌린다** (`KvsSessionManager.kt`) |
| LiveView | **재-offer를 받으면 세션을 유지한 채 PeerConnection만 재구축**한다 — 유예 5초는 수동 대기가 아니라 **재협상 창**이고, 탭 새로고침도 5초 안에 붙으면 "짧은 단절"에 해당한다 |
| LiveView | 안내 화면의 텍스트 2줄이 리소스로 고정이고 화면까지 세션 정보가 전달되는 배선이 없다 — 문구 분기에는 extra 추가 + 전달 + 문자열 2쌍(ko/en)이 필요하다 |
| 서버(skix) | `KvsProperties`의 `DEVICE_RELAY_MAX_MS`(90분 천장) / wire 기본값 600초 / 초과 시 부팅 WARN — 전부 테스트로 고정돼 있다 |
| 서버(api-main) | 맵 등록 지점은 `ResponseDeviceService.mapping()`의 `createBuildingMap()` 호출부 **하나**다. `mapUpload()`는 앱 전용 경로라 correlationId가 세션 키와 겹칠 수 없어 가드가 불필요하다(확인 완료) |
| 서버(api-main) | 공용 복귀 API의 허용 상태 목록은 **넓히지 않았다** — 공용 계약 변경은 앱 경로 회귀 위험이라, 원격 맵핑 서비스가 소유권 검증 후 명령을 직접 발행하는 전용 경로를 뒀다 |
