# [공통] 코드 규약·로그·시크릿·협업 방식

| 항목 | 내용 |
|---|---|
| **문서 성격** | 특정 기능이 아니라 4개 저장소에 걸쳐 적용해 온 **공통 규약과 일하는 방식**을 모은 문서 |

## 0. 세 줄 요약

1. 로그·감사기록·시크릿에 관한 규칙은 문서가 아니라 **코드에 상수 클래스·주석으로 박아 두었다** — `LogBodyPolicy`, `LogMasking`, `AuditLog` 세 클래스를 보면 규약 전체가 나온다.
2. 핵심 발상은 하나다. **"정상적으로 없는 값"과 "있어야 하는데 없는 값(=결함)"을 항상 다른 표기로 남긴다.** 이 원칙이 로그 마커·감사로그 예외·시크릿 fail-closed 설계에 공통으로 깔려 있다.
3. 브랜치는 `feature → dev → stg → main` 단방향 승격이 원칙이지만, **운영 미배포 커밋은 승격에서 의도적으로 빠질 수 있다**(skix-security `main`이 실례). 이걸 모르고 `dev`를 통째로 머지하면 빠져 있던 위험 코드가 조상으로 딸려 들어온다.

## 1. 용어

| 용어 | 뜻 |
|---|---|
| **로그 센티널(sentinel)** | 값이 없는 이유를 구분하기 위해 로그에 남기는 고정 문자열. 예: `[REDACTED:PII]`, `[ABSENT]`, `[NOT_CAPTURED]` |
| **REDACTED** | 값이 있었지만 **정책상** 남기지 않았다는 표시. 이유 코드를 콜론 뒤에 붙인다(`[REDACTED:PII]`) |
| **ABSENT / EMPTY** (skix-medcare) | `ABSENT`=필드 자체가 없었음, `EMPTY`=필드는 왔는데 빈 값이었음. 둘 다 상대(또는 우리 자신)의 계약 위반을 의심할 신호다 |
| **NOT_CAPTURED** | 본문이 실제로 있었는데 로깅 필터가 그 시점에 캐시하지 못한 경우. 값이 "원래 없음"이 아니라 "포착 실패"임을 구분한다 |
| **접속기록(감사로그)** | 개인정보 안전성 확보조치 기준 제8조가 요구하는 "누가·언제·누구의 정보를·무엇을 했는지" 로그. 2년 보관·월 1회 점검 대상이며, 위 로그 센티널 규약과 **표기 방식이 다르다**(§2-3) |
| **SSM Parameter Store** | AWS Systems Manager의 키-값 저장소. 시크릿 원본을 여기 두고, 애플리케이션은 값이 아니라 파라미터 경로만 안다 |
| **fail-closed** | 시크릿·설정이 없거나 형식이 틀리면 **기동을 막거나 요청을 차단**하는 설계. 반대는 fail-open(누락 시 평문·기본값으로 조용히 동작) |
| **`--no-ff` 머지** | `git merge --no-ff`. 빨리 감기(fast-forward) 없이 항상 머지 커밋을 남긴다. feature 브랜치가 어디서 dev에 들어왔는지 이력에 남기기 위해 쓴다 |
| **선별 반영(선별 승격)** | 하위 브랜치의 커밋 전부가 아니라 **일부만** 골라 상위 브랜치에 올리는 것. `git merge`를 그대로 쓰면 제외한 커밋까지 조상으로 딸려 오므로 별도 기법(cherry-pick, 특정 머지 커밋만 골라 머지)이 필요하다 |
| **계약 테스트(contract test)** | 우리 코드가 아니라 **외부 시스템과 주고받는 전문(필드명·구조·고정값)**이 맞는지 고정하는 테스트. 우리 로직이 맞아도 필드명 하나가 틀리면 상대가 조용히 거절할 수 있어 별도로 둔다 |
| **변이 테스트(mutation test) 방식 점검** | 정식 변이 테스트 도구를 쓰지 않고, **일부러 결함을 주입한 뒤 기존 테스트가 실패하는지 직접 확인**하는 검증 습관. "테스트가 있다"와 "테스트가 그 결함을 잡는다"는 다른 얘기라서 쓴다 |

## 2. 로그 마커 규약 (3저장소 공통)

### 2-1. 핵심 원칙

**빈 자리를 결함 신호로 예약한다.** 정상적인 미기록이 전부 정해진 마커를 거치게 해 두면, 아무 마커도 없이 그냥 비어 있는 자리는 자동으로 "버그"가 된다 — 별도 모니터링 없이 결함이 스스로 드러난다. 이 규약 이전에는 "저장 로직이 고장났다"와 "원래 값이 없었다"가 구별되지 않아 로그만 보고는 감사 필터가 죽었는지조차 알 수 없었다.

`skix-security`·`skix-medcare`·`skix-openapi` 세 저장소에 **같은 형태**로 적용되어 있다(2026-08-13 확정). 형태를 다르게 두면 규약이 아니라 저장소별 습관이 되므로, 신규 저장소나 신규 필드에 적용할 때도 아래 어휘를 그대로 재사용한다.

| 상태 | 표기 | 저장소 |
|---|---|---|
| 값 자체가 없었음 | DB 컬럼은 `null`, 로그 라인은 `[ABSENT]` | DB 적재형은 null, 로그 라인형(medcare)은 `[ABSENT]` |
| 필드는 왔는데 빈 값 | `[EMPTY]` | skix-medcare |
| 있었지만 포착 실패 | `[NOT_CAPTURED]` | skix-security (skix-medcare는 WebFlux라 캡처 지점 자체가 없어 아직 미사용, 도입 시 같은 이름 예약) |
| 정책상 미기록 | `[REDACTED:사유]` | 3저장소 공통 |
| 마스킹 | `010****5432` | 3저장소 공통 |

사유 코드는 `PIN`(기기 PIN 평문) · `PII`(이름·전화번호·주소 등 개인정보) · `CREDENTIAL`(자격증명·presigned URL·공개키) 이 3저장소 공통이고, **skix-medcare만 `PHI`를 추가**로 쓴다(PHR 원문·의료 질의·답변·신고 문구 — 이 저장소의 주된 민감정보이며 법적 취급이 다르다). skix-medcare는 여기에 `EXTERNAL_BODY`(외부 응답 원문 — 내용을 통제할 수 없는 값)도 둔다.

### 2-2. 실제 구현

구현은 저장소마다 **상수 클래스 한 곳**에 모여 있다. 규약을 확인하거나 새 사유 코드를 추가할 때 이 파일 하나만 보면 된다.

**`skix-security/src/main/java/com/skix/security/common/utils/LogBodyPolicy.java`** — API·MQTT 이력 테이블은 **본문을 DB 컬럼에 그대로 적재**하므로, `null`이 "값 없음"으로 쓸 수 있는 실제 값이다. 별도 `body_policy` 컬럼을 두지 않고 컬럼 안에 센티널 문자열을 넣는 방식을 택했다 — `WHERE body LIKE '[REDACTED:%'`로 기존 조회를 그대로 확장할 수 있고, 과거에 사유 없이 `[REDACTED]`로만 저장된 행도 같은 LIKE 조건에 걸린다.

```java
/** 사유 없이 저장된 과거 데이터도 LIKE '[REDACTED%' 로 함께 조회되도록 접두사를 유지한다. */
private static final String REDACTED_PREFIX = "[REDACTED:";

public static final String NOT_CAPTURED = "[NOT_CAPTURED]";
public static final String PIN = "PIN";
public static final String PII = "PII";
public static final String CREDENTIAL = "CREDENTIAL";

public static String redacted(String reason) {
    return REDACTED_PREFIX + reason + "]";
}
```

이 클래스는 `RequestLoggingFilter`(인바운드)·`OutboundApiLogInterceptor`(아웃바운드) 양쪽에서 쓰인다. 예를 들어 `RequestLoggingFilter`는 경로별로 사유를 판정해서 본문 대신 사유를 저장한다.

```java
// RequestLoggingFilter.java
private String sensitiveRequestReason(String uri) {
    if (uri == null) return null;
    if (uri.contains(PIN_PATH_SEGMENT)) return LogBodyPolicy.PIN;
    if (uri.contains(KVS_PATH_SEGMENT)) return LogBodyPolicy.CREDENTIAL;
    if (uri.startsWith(INTERNAL_PATH_PREFIX) && uri.contains(DIRECT_MEMBERSHIP_PATH_SEGMENT)) {
        return LogBodyPolicy.PII;
    }
    return null;
}
```

같은 파일이 `[NOT_CAPTURED]`가 필요한 이유도 주석으로 남겨 두었다: `ContentCachingRequestWrapper.getContentAsByteArray()`는 **핸들러가 본문을 읽은 뒤에만** 채워진다. 인증 필터에서 401로 끊기면 본문이 실제로 왔어도(`Content-Length > 0`) 캐시는 빈 배열이라 `null`로 저장되어 버린다. 그래서 "본문 없음"과 "본문은 왔는데 못 잡음"을 코드로 구분한다.

```java
byte[] cached = wrappedRequest.getContentAsByteArray();
if (cached.length == 0 && request.getContentLengthLong() > 0) {
    // 인증 필터에서 끊겼거나 핸들러가 본문을 읽지 않아 래퍼가 채워지지 않은 경우.
    return LogBodyPolicy.NOT_CAPTURED;
}
```

**`skix-medcare/src/main/java/com/skix/medcare/config/LogMasking.java`** — 여기는 DB가 아니라 **로그 라인만** 다루므로 전부 문자열이고, `null`이라는 "값 자체가 없다"는 의미로 쓸 자리가 없다. 그래서 "없음"까지도 마커(`[ABSENT]`)가 필요하다.

```java
public static final String ABSENT = "[ABSENT]";
public static final String EMPTY  = "[EMPTY]";

public static final String PHI = "PHI";
public static final String PII = "PII";
public static final String CREDENTIAL = "CREDENTIAL";
public static final String EXTERNAL_BODY = "EXTERNAL_BODY";

public static String redacted(String reason) {
    return "[REDACTED:" + reason + "]";
}
```

같은 파일 안 `maskLoginId`가 값이 없는 경우를 실제로 어떻게 가르는지 보여준다.

```java
public static String maskLoginId(String loginId) {
    if (loginId == null) {
        return ABSENT;
    }
    if (loginId.isEmpty()) {
        // 예전에는 "" 를 그대로 돌려줘 로그에 `user: ` 로 아무것도 남지 않았다.
        // 그러면 '값이 빈 문자열이었다'와 '포맷 인자가 통째로 빠졌다'가 구별되지 않는다.
        return EMPTY;
    }
    ...
}
```

**`skix-openapi`**는 `AuditLogFilter`(이름은 audit이지만 실제로는 인바운드 API 로그 필터) 안에 같은 발상의 `REDACTED` 상수를 둔다.

```java
/**
 * 본문을 일부러 저장하지 않았다는 표시.
 * 본문이 실제로 없어 null인 경우와 반드시 구별돼야 한다 —
 * 둘 다 null이면 감사 기록이 비어 있을 때 그게 정상인지 고장인지 알 수 없다.
 */
static final String REDACTED = "[REDACTED]";
```

세 저장소를 관통하는 같은 발상의 이전 사례로 `skix-medcare`의 `ExternalApiException.responseBodyLength` — 본문 내용 대신 **길이만** 남겨서 "응답이 비어 있었다"와 "응답은 있었지만 안 남겼다"를 구별한다. `ConversationMapper`의 `length=` 로그도 같은 패턴이다.

### 2-3. 감사로그(접속기록)는 이 규약에서 제외되는 문서화된 예외

**감사·접속기록 로그는 위 규약을 쓰지 않는다.** 값이 없을 때 이유를 가리지 않고 전부 `-`로 남긴다. 이건 누락이 아니라 의도적인 예외다.

이유는 `skix-medcare/src/main/java/com/skix/medcare/config/AuditLog.java`의 주석에 그대로 박아 두었다: 접속기록은 2년 보관 대상이고 CloudWatch 구독 필터가 이 로그를 골라 S3(Object Lock)로 보내 월 1회 점검에 쓴다. 지금 센티널을 바꾸면 과거 데이터와 신규 데이터의 표기가 갈리고, `subject != '-'` 같은 **기존 점검 조건이 조용히 깨진다.** 표기를 통일하려면 로그 규약이 아니라 보관·점검 절차와 함께 다뤄야 하는 별건이라 손대지 않았다.

```java
public final class AuditLog {
    private static final Logger log = LoggerFactory.getLogger("AUDIT");  // 전용 로거 이름

    // 관제가 X-Acting-Admin 을 보내지 않은 경우. 내부 API 는 공유 키 인증이라 헤더가 없으면
    // '누가'를 특정할 수 없다 — 빈 값으로 흘리지 않고 이 값으로 드러낸다.
    public static final String UNIDENTIFIED_ACTOR = "UNIDENTIFIED";
    ...
}
```

다만 "행위자를 왜 모르는지"는 접속기록 안에서도 두 값으로 구분한다: `UNAUTHENTICATED`(인증 자체가 실패해 주장을 믿을 수 없음)와 `UNIDENTIFIED`(인증은 통과했으나 행위자 헤더가 없음). 조치가 다르기 때문이다. `InternalApiAuditFilter.resolveActor()`가 응답 상태(401/403)로 이 둘을 가른다.

앱 로그의 마커가 감사 포맷으로 새어드는 통로가 있는지도 코드로 확인해 두었다. `skix-medcare`는 `InternalApiController`가 `log/list` 조회의 `subject`를 `maskLoginId`로 만들어 감사 로그에 넘기는 자리 **하나뿐**이고, 그 자리의 `loginId`는 `@NotBlank` 검증을 통과해야만 컨트롤러에 도달하므로 `[ABSENT]`/`[EMPTY]`가 감사 로그에 섞일 수 없다. **이 검증(`@NotBlank`)을 제거하면 두 마커 체계가 섞이므로, 손대기 전에 반드시 이 사실을 다시 확인할 것.**

접속기록에는 로그 위조 방지 처리도 들어 있다. 값 일부(쿼리의 `authSub` 등)는 인증 전 요청에서 그대로 오므로, 개행을 그대로 두면 공격자가 줄바꿈으로 **위조된 감사 라인 한 줄을 통째로 심을 수 있다.** 그래서 `AuditLog.sanitize()`가 개행을 제거하고 길이도 200자로 자른다(2년 보관·법적 증빙 대상이라 가짜 한 줄이 기록 전체의 신뢰를 무너뜨리기 때문).

내부 API 호출 감사는 컨트롤러마다 호출을 넣는 방식이 아니라 **필터**(`InternalApiAuditFilter`, skix-medcare)로 걸었다. 컨트롤러가 늘 때마다 사람이 감사 호출을 기억해야 하는 구조면 언젠가 빠지기 때문이다. 이 필터는 `doFinally`로 완료·오류·**취소**(ALB 타임아웃·클라이언트 이탈)까지 전부 받는다 — `doOnSuccess`/`doOnError`만 쓰면 취소 시 기록이 사라지는데, 그 사이 DB 조회는 이미 일어났을 수 있어 "정보주체 기록을 읽고도 접속기록이 없는" 상태가 생긴다.

## 3. PII·토큰 로그 금지 원칙

### 3-1. 헤더는 화이트리스트가 아니라 "아예 남기지 않기"로 귀결됐다

`skix-medcare`의 `RequestLoggingFilter`는 한 줄 요청·응답 로그만 남기고 **헤더 값은 어떤 형태로도 찍지 않는다.** 이전에는 민감 헤더 6종(`authorization`, `idtoken`, `x-api-key`, `x-internal-api-key`, `cookie`, `set-cookie`)을 블랙리스트로 가리고 나머지를 전부 남기는 방식이었는데, 그 구조를 다음 이유로 폐기했다(코드 주석 그대로 옮김).

- 블랙리스트는 "지금 안전"만 보장하고 "앞으로 안전"을 보장하지 않는다 — 목록에 없는 새 헤더는 기본이 노출이다.
- 실제로 `X-Forwarded-For`(접속자 IP)·`User-Agent`(단말 지문)는 민감한데 한 번도 가린 적이 없었다.
- 인증 헤더가 하나 늘 때마다 사람이 목록을 갱신해야 하는 구조라, 언젠가 빠뜨린다.
- 장애 분류에 헤더 값이 필요한 적이 없었다 — method·path·파라미터 **이름**과 응답 상태·소요시간으로 충분하다.

필요해지면 블랙리스트를 되살리지 말고 **남길 헤더를 화이트리스트로 명시**하는 쪽으로 간다는 방향까지 주석에 못박아 두었다. 같은 이유로 내부 API 감사(`InternalApiAuditFilter`)는 쿼리 파라미터 전체가 아니라 통제된 이름(`EFFECT_PARAMS = List.of("apply", "limit")`)만 화이트리스트로 남긴다 — 쿼리 전체를 실으면 검색어 같은 개인정보가 감사 로그로 샌다.

`skix-security`의 `RequestLoggingFilter`는 DB 적재형이라 접근이 다르다. 헤더 자체를 남기지 않는 대신, **경로 단위로 본문 전체를 `[REDACTED:사유]`로 대체**한다(§2-2의 `sensitiveRequestReason`). KVS 세션 응답처럼 뷰어 자격증명이 실리는 응답도 `isSensitiveResponse(uri)`로 걸러 본문 자체를 저장하지 않는다.

### 3-2. 아웃바운드 로그의 마스킹은 "경로 단위"로 더 세밀하다

`skix-security/src/main/java/com/skix/security/infra/http/OutboundApiLogInterceptor.java`는 대상(target) 전체를 가리는 방식과, **한 대상 안에서 특정 경로의 응답만** 가리는 방식을 함께 쓴다.

```java
/**
 * 경로 단위 응답 본문 미저장 규칙.
 *
 * PLATFORM 은 스케줄·계약·영역명처럼 장애 분석에 본문이 필요한 호출이 대부분이라
 * 통째로 가릴 수 없는데, check-member 응답만은 전화번호를 담는다.
 *
 * 이 응답의 loginId 는 전화번호다. 토큰에서 PII 를 걷어내면서 사용자 해석을
 * 이 응답으로 옮겼는데, 그대로 저장하면 매 인가 호출마다 전화번호가 로그 DB 로 옮겨간다 —
 * 유출면을 없앤 게 아니라 이동시킨 셈이 된다.
 */
private static final List<Map.Entry<Pattern, String>> RESPONSE_BODY_REDACTIONS = List.of(
    Map.entry(Pattern.compile("/api/internal/security/check-member"), LogBodyPolicy.PII)
);
```

이 주석이 지적하는 함정 — "토큰에서 PII를 걷어내고 다른 응답으로 옮겼더니 그 응답이 새 유출면이 됐다" — 은 규모가 큰 리팩토링(예: 토큰에서 개인정보 제거) 뒤에 특히 반복되는 패턴이다. 값을 어디서 걷어내든 **그 값이 도착하는 다음 자리를 반드시 같이 확인**해야 한다.

`skix-openapi`의 `AuditLogFilter`는 아예 경로+메서드 조합(`Set<String>` route)으로 요청/응답 각각 다른 규칙을 둔다. 흥미로운 결정은 **실패 응답은 가리지 않는다**는 것 — 자격증명은 성공 응답에만 실리고, 장애 조사에 정작 필요한 건 실패했을 때의 본문이기 때문이다.

```java
private static final Set<String> REDACT_RESPONSE_ROUTES = Set.of(
    "POST /v1/auth/token",                      // 액세스 토큰 전문
    "POST /v1/developer/credentials",           // Secret Key 평문 — 이 응답 이후 재조회 불가
    "POST /v1/developer/credentials/rotate",    // 위와 동일
    "POST /v1/webhooks"                         // 웹훅 서명용 secret — 1회만 반환
);

private String resolveResponseBody(String route, int status, String capturedBody) {
    if (status < 400 && REDACT_RESPONSE_ROUTES.contains(route)) return REDACTED;
    return truncate(capturedBody, BODY_STORE_LIMIT);
}
```

같은 필터가 본문 캡처 크기 상한을 둔 이유도 남겨 뒀다 — 상한이 없으면 응답 전체를 버퍼링해 큰 응답이 몰릴 때 힙을 잠식하고, `MaxRAMPercentage=70` + `ExitOnOutOfMemoryError` 조합에서는 OOM이 곧 컨테이너 종료로 이어진다. 신규 아웃바운드/인바운드 로깅 지점을 추가할 때 이 상한 패턴을 그대로 따른다.

### 3-3. 예외 메시지에 외부 응답 본문을 붙이지 않는다

`skix-medcare/src/main/java/com/skix/medcare/domain/exception/ExternalApiException.java`는 **응답 body를 절대 싣지 않는다.** 상대(PHR, 케이론 등)가 내용을 정하는 값이라 우리가 통제할 수 없고, 실제로 PHR은 실명·생년월일·전화번호를, 케이론은 사용자 질의를 되돌려준다. 처음에는 500자로 잘라서 저장했었는데 소용이 없었다 — 실명·생년월일·전화번호·의료 질의는 전부 500자보다 짧아서 그대로 남았다. **길이 제한은 '긴 값'을 막을 뿐 '민감한 값'을 막지 못한다.**

이 클래스는 `cause`를 받는 생성자를 아예 두지 않는다. 외부 응답을 파싱하다 난 예외는 응답 원문을 메시지에 그대로 담고 있어서, `cause`로 달면 스택트레이스로 그대로 새어나간다 — 2026-08-04에 PHR·케이론·플랫폼 세 어댑터에서 전부 실측으로 확인된 문제였다. 대신 상태·호출 종류·**응답 본문 길이**만 구조화해서 남긴다.

```java
protected static String describe(String system, String operation, int httpStatus, int responseBodyLength) {
    return system + " API call failed - op=" + operation
            + ", status=" + httpStatus + ", bodyLength=" + responseBodyLength;
}

// 상태 없이 실패한 경우(연결 거부·타임아웃·TLS 오류·2xx 역직렬화 실패)
// 원인 예외의 cause 는 보존하지 않고 타입만 남긴다 — 역직렬화 실패 메시지에
// Jackson 이 파싱하려던 원문이 그대로 담겨 있어서다.
protected static String describeWithoutStatus(String system, String operation, String traceId, String causeType) {
    ...
}
```

새로운 외부 연동을 추가할 때 예외 클래스를 새로 만들지 말고 이 클래스를 상속해서 같은 규칙(본문 미포함, cause 미보존, 메타데이터만)을 그대로 따른다.

### 3-4. 식별자 마스킹

로그인 ID(전화번호로 폴백되는 값)는 `010****5678` 형태로 마스킹한다(`LogMasking.maskLoginId`, 앞 3자·뒤 4자만 남김). `sub`로 바꾸지 않고 마스킹을 택한 이유가 코드 주석에 있다 — `PhrService`·`PlatformApiAdapter`·`InternalApiController`는 `loginId`가 유일한 키라 `sub`를 가져올 수 없고, 절반만 `sub`로 바꾸면 한 요청의 로그를 이어붙일 수 없게 된다.

`backend-api-main`은 신규 3종과 같은 통합 필터가 없는 레거시 구조라 마스킹이 유틸 함수 단위로 흩어져 있다. `StringUtil.maskPhoneNumber` / `maskId` / `maskKoreanName` / `emailMasking`이 존재하며, 로그에 개인정보를 남기는 곳(`VitalSignCreateMeasurementService`, `UserService`, `MemberService`)이 개별적으로 이 함수를 호출해야 한다 — **필터 한 곳이 강제하지 않으므로, 새 로그 라인을 추가할 때 마스킹 호출을 빠뜨리기 쉬운 구조라는 점을 인지하고 리뷰에서 챙길 것.**

## 4. 시크릿 취급

### 4-1. 세 가지 원칙

`skix-security`·`skix-medcare`·`skix-openapi` 세 저장소는 **"저장소에 값을 두지 않고, 런타임에 주입하며, 없으면 기동을 막는다"**로 표준화되어 있다.

| 통제 항목 | 구현 방식 |
|---|---|
| 시크릿 외부화 | AWS SSM Parameter Store → ECS Task Definition 환경변수 주입 |
| Fail-closed | 키 미설정 시 **기동 실패** 또는 **전 요청 차단** |
| 정적 자격증명 배제 | ECS Task Role(기본 자격증명 체인) / STS 단기 자격증명. 장기 IAM 액세스 키를 애플리케이션이 보유하지 않는다 |
| 로컬 개발용 값 | 저장소 밖 파일(`.env`류) + `.gitignore` + `.example` 템플릿만 커밋 |

설정 파일(`application-ecs.yml` 등)은 실제 값이 아니라 플레이스홀더만 선언한다.

```yaml
# skix-medcare/src/main/resources/application-ecs.yml
cheiron:
  api:
    api-key: ${CHEIRON_API_KEY}
spring:
  r2dbc:
    password: ${SPRING_R2DBC_PASSWORD}
```

`dev`/`stg`/`prd`는 **같은 프로필(`application-ecs.yml`)을 공유**하고 값만 환경별 Task Definition에서 달라진다. 설정 파일 안에 환경별 실값이 분기되어 있지 않으므로, 개발 환경 자격증명으로 운영 환경에 접근할 수 있는 경로가 코드상 존재하지 않는다.

### 4-2. Fail-closed 검증의 실제 코드

키가 없거나 형식이 틀리면 **조용히 넘어가지 않고 기동을 막는다.** `skix-medcare/src/main/java/com/skix/medcare/config/ColumnCryptoConfig.java`:

```java
// 아는 값만 받는다. 모르는 값을 평문 모드로 흘리면 `COLUMN_CRYPTO_MODE=KMS` 같은 오타 하나가
// 기동은 성공시키면서 전 행을 평문으로 저장한다 — fail-closed 를 무력화하는 가장 흔한 경로다.
if (!"kms".equals(mode)) {
    throw new IllegalStateException("column.crypto.mode 는 kms 또는 off 여야 한다(대소문자 구분): " + mode);
}
// kms 모드에 키가 없으면 기동을 막는다 — 평문 저장으로 조용히 뜨는 것이 최악이다(fail-closed).
if (keyArn == null || !keyArn.startsWith("arn:aws:kms:")) {
    throw new IllegalStateException("column.crypto.mode=kms 인데 key-arn 이 KMS ARN 이 아니다: " + keyArn);
}
```

내부 API 키가 없을 때도 마찬가지다(`InternalApiKeyAuthFilter`): 키가 비어 있으면 `/medcare/v1/internal/**` 전 경로를 401로 차단하고, 검증은 상수 시간 비교(`MessageDigest.isEqual`)를 써서 타이밍 공격으로 키를 한 바이트씩 추측하는 경로도 막는다.

로컬 개발용 시크릿 분리 파일도 **누락 시 즉시 실패**하도록 만들었다. `skix-security/src/main/resources/application-localhost.yml`:

```yaml
spring:
  # 로컬 시크릿은 저장소에 두지 않는다. 최초 1회 아래를 복사해 값을 채운다.
  #   cp config/local-secrets.yml.example config/local-secrets.yml
  # optional: 을 붙이지 않은 것은 의도적이다 — 파일이 없으면 "그 파일이 없다"고
  # 즉시 실패하는 편이, 키가 비어 엉뚱한 지점에서 죽는 것보다 낫다.
  config:
    import: file:./config/local-secrets.yml
```

`config/local-secrets.yml`은 `.gitignore`에 등록되어 있고(`config/local-secrets.yml` 제외, `config/local-secrets.yml.example`만 허용), RSA 키쌍·DB 계정·OASYS 계정·KVS lease-secret·admin JWT secret 등 로컬 전용이 아닌 값들이 여기로 분리되어 있다. `spring.datasource.password: 1234` 같은 진짜 로컬 전용 값(외부에서 의미 없는 값)만 yml에 리터럴로 남긴다.

### 4-3. yml과 SSM의 우선순위 함정 (실제로 겪은 문제)

**Spring의 `spring.config.import`로 들어오는 값(SSM 등)은 일반 프로필 yml 리터럴보다 우선순위가 낮다.** 같은 키가 양쪽에 있으면 **SSM 값이 조용히 무시되고 yml에 박힌 값이 이긴다.** 이 함정은 실제로 `backend-api-main`의 `application.yml`에 방지 조치로 남아 있다.

```yaml
# backend-api-main/src/main/resources/application.yml
app:
  internal:
    api-key: ${app.myHealthCare.api.api-key:}
    # 검증 강제 여부. 여기 공통은 안전한 기본값(false)만 두고, 환경별 값은 각 프로필 yml 에서 정한다.
    # SSM 에 넣지 않는다 — 민감정보가 아니고, 무엇보다 spring.config.import 로 들어오는 값은
    # 이 파일보다 우선순위가 낮아 여기 박힌 false 에 덮여 조용히 무시된다.
    enforce-api-key: false
```

**교훈**: 어떤 설정값의 "진짜 소스"가 SSM인지 yml인지 헷갈리면, 값을 SSM에만 두지 말고 **그 값이 실제로 yml 어디에도 리터럴로 박혀 있지 않은지부터 확인**한다. 특히 boolean 플래그·on/off 스위치류는 안전한 기본값을 프로필 공통 yml에 박아 두는 습관이 있으므로 더 걸리기 쉽다.

### 4-4. 비밀이 아닌 값은 SSM에 올리지 않는다

호스트명·URL·리전 같은 값은 **비밀이 아니므로** SSM으로 옮기지 않고 프로필별 yml 리터럴로 둔다. 예를 들어 `skix-security/src/main/resources/application-localhost.yml`의 `oasys-api.base-url`, `kms-server.base-url`, `aws.iot.endpoint` 등은 전부 yml에 평문으로 있고, 계정·비밀번호·키 종류만 `config/local-secrets.yml`로 분리되어 있다. 비밀도 아닌 값까지 SSM으로 옮기면 파라미터 수만 늘고 배포 시 조회 지연·권한 관리 대상만 늘어난다 — **"환경마다 다른 값"과 "비밀 값"은 다른 축이며, SSM으로 옮기는 기준은 후자다.**

### 4-5. backend-api-main은 다른 전환 단계에 있다

`backend-api-main`은 위 표준이 서기 전에 만들어진 레거시 서비스이고, 실행 환경도 ECS가 아니라 **EC2**라 Task Definition 주입 방식을 그대로 쓸 수 없다. 지금은 프로필별 설정 파일(`src/main/resources-{local,stag,prod,vdi}`)에 자격증명이 있고, 빌드 시 `-Pprofile=<env>`로 해당 디렉터리가 리소스로 선택되면서 **설정값이 빌드 산출물에 그대로 포함**되는 구조다.

전환 목표는 신규 3종과 같은 형태(SSM 원본 → 런타임 로드 → 설정 파일은 `${VAR}` 플레이스홀더)이며, `spring-cloud-aws-starter-parameter-store` 의존성은 이미 추가되어 있다(`spring.config.import` 연동 전까지는 비활성 상태). 조치 순서는 ①대상 시크릿 전수 식별 및 재발급(기존 값 폐기) ②SSM(SecureString) 등록, 경로 체계는 `/<서비스>/<env>/*`로 신규 3종과 통일 ③EC2 인스턴스 프로파일에 해당 경로로 한정된 최소 권한 부여 ④`spring.config.import` 연동 ⑤설정 파일의 실제 값을 플레이스홀더로 치환 ⑥형상관리 이력 정리다. 인수자가 이 전환을 이어받는다면 **③번 권한 범위를 서비스별 경로로 한정하는 것**이 핵심이다 — 범위를 넓게 주면 EC2 하나가 털렸을 때 다른 서비스 시크릿까지 노출된다.

이미 확인된 함정: **로컬(local)·검증계(stag)·운영계(prod) 설정 파일에 동일한 시크릿 값이 다수 들어 있었다**(외부 API 키 여러 종, 앱 무결성 검증 키, 관리자 JWT 시크릿 등). 즉 로컬 개발 환경 설정 파일 안에 운영에서 유효한 시크릿이 있는 상태였다. 재발급 작업을 이어받을 때는 "환경별로 값이 다르다"고 가정하지 말고 **저장소 전체에서 값 자체를 대조**해서 어디까지 같은 값을 쓰고 있는지부터 확인한다.

## 5. 브랜치·커밋 규칙

### 5-1. 커밋 메시지 머리말

모든 저장소가 대괄호 머리말 관례를 쓴다. 4개 저장소 커밋 메시지의 실제 분포(전체 이력 기준):

| 머리말 | skix-security | skix-medcare | skix-openapi | backend-api-main |
|---|---|---|---|---|
| `[feat]` | 115 | 42 | 36 | 100 |
| `[fix]` | 82 | 101 | 42 | 111 |
| `[chore]` | 24 | 30 | 13 | 15 |
| `[refactor]` | 6 | 17 | 3 | 20 |
| `[docs]` | 8 | 22 | 27 | 1 |
| `[test]` | 1 | 9 | 3 | 7 |
| `[revert]` | 1 | 0 | 0 | 1 |
| 기타(`perf`/`security`/`bugfix`) | 2 | 10 | 4 | 2 |

의미는 다음과 같다.

- `[feat]` — 새 동작 추가.
- `[fix]` — 결함 수정.
- `[chore]` — 코드 동작에 영향 없는 작업(설정값 변경, 브랜치 승격 커밋 자체, 플래그 on/off).
- `[refactor]` — 동작 변화 없는 구조 개선.
- `[revert]` — 이전 커밋을 되돌림. 예시(`skix-security` `8779f61`): "[revert] ECS 수동 배포 흐름 유지" — 되돌린 이유를 메시지에 남겨서, 나중에 "왜 되돌렸는지" 찾으려고 커밋을 거슬러 올라가지 않게 한다.
- 메시지 본문은 "무엇을 바꿨는지"보다 **"왜 이 형태로 했는지"**를 담는 경우가 많다. 예: `[fix] OASYS 호출의 자동 재시도를 끄고, 오류 경로의 상태 분류·마스킹을 바로잡는다` — 무엇(자동 재시도 OFF)과 왜(오류 경로 마스킹까지 함께 손봄)가 한 줄에 같이 들어간다.

가끔 머리말 없이 conventional commits 스타일(`fix(kvs): ...`, `docs(kvs): ...`)이 섞여 있는 구간도 있다(주로 원격 맵핑 세션 작업 시기). 새 커밋은 대괄호 스타일로 통일한다.

### 5-2. 브랜치 승격 흐름과 실제 커밋 형태

원칙은 **`feature/* → dev → stg → main` 단방향 승격**이다. 역방향(main→dev로 직접 반영, stg 건너뛰고 main 반영)은 쓰지 않는다.

**① feature → dev**: `--no-ff` 머지 커밋(부모 2개)으로 들어간다. 메시지는 기본형 `Merge branch 'feature/xxx' into dev`를 그대로 쓰는 경우가 대부분이다.

```
32a9913 Merge branch 'feature/oasys-direct-membership' into dev   (부모: 8c2d8fd, 36e3e91)
```

**② dev → stg**: 이전에는 기본형 `Merge branch 'dev' into stg`를 그대로 썼지만, 최근(2026-09 전후)은 **`[chore] dev → stg 승격 (날짜) — 요약`** 형태로 바꿔 무엇이 올라갔는지 메시지에서 바로 보이게 한다. 두 형태 모두 실제로는 부모가 2개인 머지 커밋이다(`git log --format='%P'`로 확인 가능).

```
04b28dc [chore] dev → stg 승격 (2026-09-14) — R045 ctrtClsNo 추가   (부모: b6b5653, 0fa25b5)
b6b5653 [chore] dev → stg 승격 (2026-09-08) — OASYS 자동 재시도·오류 마스킹
31d5d54 [chore] dev → stg 승격 (2026-09-03)
```

신규 승격 커밋을 만들 때는 이 형태(날짜 + 무엇이 올라갔는지 한 줄 요약)를 따른다 — 기본 머지 메시지만으로는 몇 달 뒤 "이 승격에 뭐가 포함됐는지"를 커밋을 다 열어봐야 알 수 있다.

**③ stg → main**: 지금까지는 기본형 `Merge branch 'stg' into 'main'`을 그대로 썼다.

```
f9485f9 Merge branch 'stg' into 'main'
43b89ff Merge branch 'stg' into 'main'
```

### 5-3. 선별 승격 — dev 전부를 main에 올리지 않는 경우

**dev에 있는 커밋이 전부 운영 배포 가능 상태는 아니다.** 백엔드(플랫폼) 쪽 운영 배포가 아직 안 끝난 변경을 dev에 먼저 반영해 두고, main 승격 때는 **그 커밋만 빼고** 올리는 경우가 실제로 있다.

실례: `skix-security`의 `main`은 2026-08-31 시점에 dev의 다음 2개 커밋을 의도적으로 제외한 상태다.

- `b1b148b` `[refactor]` 토큰에서 loginId 클레임 의존 제거
- `cf5f56b` `[fix]` check-member 응답을 아웃바운드 로그에 저장하지 않는다

제외 이유는 **코드 결함이 아니라 연동 대상(플랫폼) 쪽 운영 배포가 아직 끝나지 않아서**다. 그쪽이 운영에 나가면 그때 승격한다. 2026-09-22 재확인 결과 지금도 두 커밋 다 main 조상에 없다(아래 검증 방법 참고).

**dev를 통째로 `git merge`하면 안 되는 이유**: 일반 머지는 대상 브랜치의 전체 이력을 조상으로 끌어오므로, 제외해 둔 2개 커밋이 그 순간 main에 들어와 버린다. 이 상황에서 실제로 쓴 방법은 (a) 함께 반영해도 되는 머지 커밋만 골라서 머지하고, (b) 제외 대상과 섞여 있는 커밋(PIN 이력 등)은 `cherry-pick -x`로 따로 옮기는 것이었다.

이 방식의 부작용: **cherry-pick한 커밋은 dev와 main에서 해시가 다르다.** 실측(2026-09-22):

```bash
git merge-base --is-ancestor 955ba0a origin/dev   # PIN 이력 커밋(dev쪽 해시) → YES
git merge-base --is-ancestor f19e9d7 origin/main  # 같은 내용, main쪽 해시(cherry-pick 결과) → YES
git merge-base --is-ancestor 955ba0a origin/main  # dev쪽 해시로 main을 찾으면 → NO (당연함, 해시가 다름)
```

**다음에 dev를 통째로 승격할 일이 생기면**, git이 "같은 내용을 양쪽에서 서로 다른 커밋으로" 보게 되므로 그 사이 같은 줄이 다시 바뀌면 충돌이 난다. 이때 "충돌 = 중복 적용"이 아니라 **정상 상황**이니 당황하지 말고 내용 기준으로 해소한다.

**선별 승격이 실제로 반영됐는지 확인하는 방법** — 문서에 적힌 커밋 해시를 믿지 말고 항상 아래로 재확인한다.

```bash
git merge-base --is-ancestor <제외해야 할 커밋 해시> origin/main
# 종료 코드 0 = 반영됨(문제), 1 = 미반영(의도대로)
```

`git log`나 과거 문서에서 본 해시로 `grep`하는 방식은 **rebase나 cherry-pick을 거치면 해시가 바뀌어 신뢰할 수 없다.** 항상 `merge-base --is-ancestor`로 조상 관계 자체를 물어야 한다.

### 5-4. 커밋 단위 원칙

- 리뷰·롤백 단위를 커밋으로 잡는다. `[fix]` 커밋 하나가 "자동 재시도 OFF + 오류 상태 분류 + 마스킹"처럼 여러 변경을 담기도 하지만, 이는 **하나의 원인(OASYS 이중 접수 위험)에서 나온 연관 조치**이기 때문이지 무분별하게 묶은 것이 아니다. 서로 다른 원인의 변경은 커밋을 분리한다.
- 되돌릴 때는 `git revert`로 새 커밋을 만들거나, 미push 상태면 `reset`으로 정리하고 이유를 다음 커밋 메시지나 PR 설명에 남긴다. `main`처럼 이미 배포된 브랜치에서는 `--force` 류를 쓰지 않는다.

## 6. 전제 검증 원칙

**변경의 전제가 되는 사실 — 인프라 구성요소의 존재 여부, "실측했다"는 수치, 외부 시스템의 동작 — 은 반드시 실물(배포 정의 파일, 형제 프로젝트 설정, 라이브 DB 실행, 실제 API 응답)로 확인한 뒤 진행한다.** 이 원칙은 두 번의 구체적인 사고를 겪은 뒤 명문화됐다.

**사고 1 — 존재하지 않는 수집기를 전제로 한 작업.** 관측 지표 작업 중 Prometheus 수집기가 있다고 가정하고 actuator 지표 엔드포인트를 열었다가, 실제로는 이 조직의 표준이 CloudWatch(awslogs) 기반이라 그 수집기가 존재하지 않는다는 게 뒤늦게 드러나 커밋을 되돌렸다. 교훈: 관측·알람 작업 전에는 수집처가 실재하는지 **task definition이나 형제 프로젝트 설정으로 먼저 확인**한다.

**사고 2 — 재현 불가능한 "실측"을 근거로 코드와 문서를 고쳤다.** "특정 검색 방식은 항상 0건이 나온다"는 주장을 실측 결과로 믿고 그 전제로 커밋을 만들었을 뿐 아니라, 코드 주석과 문서에 **허위 수치까지 구체적으로(소수점까지)** 남겼다. 이후 감사 과정에서 동일한 스키마·버전으로 재현해 보니 그 주장이 틀렸다는 게 드러났고, 해당 커밋을 전부 철회했다. 교훈: **"실측 결과 X"라고 쓰기 전에, 그 자리에서 재현 가능한 명령과 출력을 함께 남긴다.** 재현 명령이 없는 실측 주장은 애초에 쓰지 않는다.

**세 번째 함정 — 한 환경에서 본 에러를 다른 환경에 일반화.** 탈퇴 처리 중 특정 컬럼이 `NOT NULL`이라 예외가 나는 문제를 조사할 때, `db-schema` 저장소의 DDL 파일 세 개(dev/stg/prd용) 전부가 `DEFAULT NULL`로 되어 있어 "설정상 문제 없음"으로 보였다. 그런데 **실제 운영 중인 DB는 개발계만 `NOT NULL`이고 검증계·운영계는 `nullable`이었다** — 개발계는 예외로 시끄럽게 터졌고, 검증계·운영계는 조용히 NULL을 기록하고 있었다. 스키마 정의 파일과 실제 스키마가 어긋난 사례다. 교훈: **환경 간 스키마 drift가 실재한다.** 재현이 안 되면 로직을 더 파기 전에 `SHOW CREATE TABLE`을 각 환경에서 직접 확인하는 것이 먼저다. 로컬 맥에서는 DB에 직결할 수 없으므로 이 확인은 VDI(사내 가상 데스크톱)에서 해야 한다.

**네 번째 함정 — 확인 범위를 넓혀 보니 전제가 절반만 맞았던 사례.** 내부 API에 별도 인증이 필요 없다는 판단을 "API Gateway가 그 경로를 라우팅하지 않는다"는 근거로 내렸는데, 그 근거는 **앱 API 전용 호스트(`app-api-*`)만 확인한 결과**였다. 나중에 별도 조사에서 웹뷰 프론트가 쓰는 호스트(`report-*.namuhx.com`)는 API Gateway를 거치지 않고 `/api/**`를 백엔드로 통째 프록시한다는 사실이 드러났고, 그 경로로는 같은 내부 API가 **무인증으로 열려 있었다.** "인프라로 막혀 있다"는 판단은 그 인프라 구성 전체(모든 진입 호스트)를 확인한 뒤에만 내릴 수 있다는 교훈이다.

**적용 규칙 요약**

- 보안 기본값(401 등)이 작업에 방해가 된다고 느껴지면, 우회하기 전에 **그 작업 자체가 정말 필요한지**부터 의심한다.
- 로컬에서 DB를 직접 열어 검증할 때는 문자 인코딩 옵션을 명시하고(`--default-character-set=utf8mb4` 등), **출력 없음(=0건)과 오류를 혼동하지 않는다.**
- "저장소 설정 파일이 이렇게 되어 있다"는 "실제로 이렇게 동작한다"의 증거가 아니다. 특히 스키마·인프라 설정 파일은 실물과 어긋날 수 있다는 전제로 다룬다.
- 인프라 구성(라우팅, 게이트웨이 등)을 근거로 보안 판단을 내릴 때는 **진입 가능한 경로 전체**를 확인했는지 스스로 물어본다. 하나의 호스트·하나의 환경만 확인하고 "막혀 있다"고 단정하지 않는다.

## 7. 타 팀·협력사 요청서 작성 방식

앱·프론트·협력사에 작업을 요청하는 문서는 **지시서가 아니라 "문제 + 제안 + 검토 요청" 형식**으로 쓴다. 처음에는 before/after diff와 금지 조항 위주의 엄격한 지시서 형태로 썼다가 "너무 삭막하다"는 피드백을 받고 바꿨다.

바탕에 깔린 태도: 요청을 받는 쪽을 **판단력 있는 동료**로 대한다. 조사 과정에서 확인한 함정이나 배경 정보는 유지하되, "이렇게 하라"는 명령이 아니라 **참고 정보/도움말**로 전달한다. 검토해서 더 나은 방법이 있으면 그쪽으로 가도 되는 관계로 둔다. 방향이 크게 갈릴 수 있는 항목만 "착수 전에 공유해 달라"고 명시적으로 요청한다.

### 7-1. 템플릿 구조

```
# <대상팀> 공유 — <무엇을 왜 바꾸는지 한 줄>

> (선택) 이번 요청의 범위를 한 문단으로 좁힌다. 무엇을 포함하고 무엇을 빼는지,
> 아직 정해지지 않아 이번에 못 다루는 것이 있으면 여기서 미리 밝힌다.

## 배경 — 왜 바꾸려 하는지

지금 상태를 문제로 짚는다. 가능하면 **수치나 관찰된 사실**로(예: "검증계 2주 실측 결과
성공 건의 70%가 10초를 넘었다"). "왜 지금 하는가"도 짧게 — 타이밍 근거가 있으면 설득력이
붙는다(예: "아직 운영 미출시라 지금이 형태를 바꾸기 가장 싼 시점이다").

기존 동작 중 **바뀌지 않는 부분**을 먼저 명시한다. 받는 쪽이 영향 범위를 가장 먼저 궁금해하기
때문이다.

## 바뀌는 것 없음 / 새로 생기는 것

간단한 다이어그램이나 표로 "기존 흐름"과 "신규/변경 흐름"을 나란히 보여준다.

# A. 우리(서버) 쪽이 제공하거나 바꾸는 것

각 API·필드 변경마다:

1. **무엇이 바뀌는가** — 요청/응답 형태를 실제 JSON·HTTP 스펙으로 보여준다(설명글보다 예시가
   빠르다).
2. **왜 이 형태로 했는가** — 특히 "왜 새 필드를 안 만들고 기존 필드를 생략하는가", "왜 이
   값을 서버가 정하고 클라이언트가 판단하지 않게 했는가" 같은 결정은 이유를 붙인다. 이유
   없이 결과만 주면 상대가 자기 판단으로 다르게 구현할 여지가 생긴다.
3. **플랫폼별로 확인해야 할 지점**이 다르면 각각 짚어준다. 한쪽은 구조가 이미 맞아서 트리거
   지점만 옮기면 되고, 다른 쪽은 실질적인 재작업이 필요한 경우가 흔하다 — 작업량이 다르다는
   것 자체가 유용한 정보다.

## B. <대상팀>에서 필요한 것

1. 항목별로 **문제 상황(위치·영향) → 제안하는 해결 방향 → 참고할 함정**의 순서로 쓴다.
2. 코드 위치를 안다면 파일·라인까지 구체적으로 짚어준다(`[FileName.kt:123]` 형태). 조사도
   안 하고 "확인해 주세요"라고만 하면 받는 쪽이 처음부터 다시 찾아야 한다.
3. **"왜 안전한 기존 설정을 재사용하면 안 되는가"** 같은, 자칫 넘어가기 쉬운 위험은 굵게
   강조하고 이유를 붙인다.
4. 가장 중요하고 놓치기 쉬운 항목(예: "접수됨과 완료를 반드시 분리해야 한다")은 별도 소제목을
   달아 다른 항목보다 눈에 띄게 한다.
5. 판단을 위임할 부분은 위임한다("기존 화면을 고쳐 쓰실지 새로 만드실지는 판단에 맡기겠습니다.
   다만 기존 화면 설정을 그대로 쓰지는 않았으면 합니다").
6. 실패 코드·에러 케이스가 있으면 표로 정리하고, **각 실패가 실제로 어디로 이어져야 하는지**
   (재시도 지점이 어디인지, 화면 전환이 필요한지)까지 명시한다. "에러 코드가 내려간다"만
   전달하면 받는 쪽이 잘못된 화면으로 연결하기 쉽다.
7. 잘 보이지 않는 리스크(예: "알림을 꺼둔 사용자는 이 채널로 결과를 영영 못 받는다",
   "전경 상태에서는 푸시가 기본적으로 안 보일 수 있다")는 별도로 짚어서, 요청받은 사람이
   "이 경우까지 내가 책임져야 하는구나"를 놓치지 않게 한다.
```

### 7-2. 쓸 때 주의할 점

- **조사 없이 요청하지 않는다.** 요청서를 쓰기 전에 상대 저장소(앱·프론트)의 실제 코드를 먼저 읽고, 어느 파일·어느 줄이 이번 변경과 관련 있는지 파악한 뒤에 쓴다. 이 조사가 없으면 요청서가 지시서보다 못한 "막연한 부탁"이 된다.
- **결정한 이유를 감추지 않는다.** "이렇게 해주세요"만 있고 "왜"가 없으면, 받는 쪽이 다르게 구현했을 때 리뷰에서 다시 설득해야 한다. 이유를 먼저 주면 그 자리에서 판단할 수 있다.
- **위험은 눈에 띄게, 그러나 명령조로 쓰지 않는다.** 굵게 강조하거나 별도 소제목을 쓰되 "~해야 합니다" 대신 "~해 주셨으면 합니다", "~는 확인이 필요합니다" 톤을 유지한다.
- **작업량 차이를 숨기지 않는다.** 두 플랫폼(iOS/Android) 작업량이 다르면 그대로 말한다. 균등하게 나온 것처럼 포장하면 일정 협의가 꼬인다.
- **범위를 좁힌 이유를 먼저 밝힌다.** 이번 요청에서 뺀 것(예: 로딩 화면 UI)이 있다면 왜 뺐는지, 그런데도 반드시 같이 가야 하는 항목(예: 상태 분리)은 무엇인지 서두에서 갈라 둔다. 안 그러면 "왜 이건 안 하냐"는 질문이 항목마다 따로 들어온다.

## 8. 테스트 관례

### 8-1. 변이 테스트 방식 점검 — "테스트가 있다"와 "테스트가 결함을 잡는다"는 다르다

새 테스트를 작성한 뒤, 정식 mutation testing 도구 없이도 **일부러 결함을 주입해서 테스트가 실제로 실패하는지 직접 확인**하는 습관을 쓴다. 테스트 커버리지가 있어도 assertion이 느슨하면 결함이 있는 채로 통과해 버리는데, 이 방식은 그런 "무늬만 테스트"를 걸러낸다.

실제로 이 방식으로 확인한 사례(OASYS 직접 구독 신청 작업, 2026-09-07 기준 backend-api-main 467건·skix-security 450건 테스트 전량 통과 상태에서):

- **SafeKey 필드명을 옛 이름(`skmSfky`)으로 되돌려 봤을 때** — 테스트가 깨지는지 확인. 계약 테스트(§8-2)의 `SafeKey는_safeKey_필드명으로_직렬화된다`가 이 회귀를 잡는다.
- **요금제 값이 없을 때 기본값을 채우도록 코드를 바꿔 봤을 때** — 테스트가 깨지는지 확인. "알 수 없는 요금제는 거절하고 기본값을 채우지 않는다"는 결정을 검증하는 테스트가 있어야 이 변이가 잡힌다.
- **조건부 UPDATE에 반대 컬럼(SafeKey 갱신 SQL에 `icst_no`)을 끼워 넣어 봤을 때** — 테스트가 깨지는지 확인. `UserMapperOasysUpdateXmlTest`가 생성된 SQL 문자열에 `icst_no =`가 **없어야 한다**는 것까지 단정해서 이 실수를 잡는다.

```java
// backend-api-main/src/test/java/.../UserMapperOasysUpdateXmlTest.java
@Test
void SafeKey_갱신은_skm_sfky_만_건드리고_비어있을_때만_쓴다() {
    String sql = sqlOf("updateSafeKeyIfMissing", Map.of("loginId", "01011110001", "skmSfky", "K"));
    assertThat(sql).contains("SET skm_sfky =");
    // icst_no 가 SET 절에 끼면 기존 통합고객번호가 날아간다. 이 단정이 이 테스트의 핵심이다.
    assertThat(sql).doesNotContain("icst_no =");
    assertThat(sql).contains("skm_sfky IS NULL");
}
```

새 테스트를 리뷰할 때 "이 테스트를 통과시키기 위한 가장 게으른 잘못된 구현을 상상할 수 있는가? 그 구현으로 바꾸면 정말 이 테스트가 깨지는가"를 스스로 묻는다. 특히 값이 여러 개 오가는 자리(생성자 인자 순서, SQL의 SET절)는 **"둘이 서로의 자리에 들어가지 않았는지 교차로 확인하는 assertion"**을 넣는다.

### 8-2. 계약 테스트 — 외부 전문의 키를 코드로 고정한다

외부 시스템(OASYS 등)과 주고받는 전문은 **필드명 하나, 고정값 하나가 틀려도 우리 로직은 멀쩡한 채로 상대가 조용히 거절하거나 잘못 처리할 수 있다.** 이 클래스의 실패는 개발계의 화이트리스트 스텁 경로에서는 드러나지 않는다(스텁은 실제 전문을 만들지 않고 바로 성공 응답을 준다). 그래서 전문의 필드 구성·필드명·고정값을 코드로 고정하는 전용 테스트를 둔다.

`skix-security/src/test/java/.../OasysDirectMembershipRequestContractTest.java`:

```java
/**
 * R045 appType=1 요청 전문 계약 — OASYS 회신(2026-09-07) 기준.
 *
 * 필드명 하나가 어긋나면 OASYS 가 조용히 거절하거나 SafeKey 없이 접수될 수 있는데,
 * 그 실패는 개발계 화이트리스트 스텁에서는 드러나지 않는다(스텁이 요청을 보지 않는다).
 * 전문 이름을 코드로 고정해 두는 유일한 지점이다.
 */
@Test
void SafeKey는_safeKey_필드명으로_직렬화된다() throws Exception {
    JsonNode data = serialize(saveData()).get("saveData");
    assertThat(data.get("safeKey").asText()).isEqualTo(SAFE_KEY);
    // R002 응답 필드명(skmSfky)을 그대로 쓰던 임시 구현으로의 회귀 방어
    assertThat(data.has("skmSfky")).isFalse();
}

@Test
void 전문_키_구성이_고정된다() throws Exception {
    JsonNode json = serialize(saveData());
    assertThat(json.fieldNames()).toIterable()
            .containsExactlyInAnyOrder("interfaceid", "saveData");
    assertThat(json.get("saveData").fieldNames()).toIterable()
            .containsExactlyInAnyOrder("appType", "icstNo", "ctrtNo", "prdtQcrsNo", "gdsCd", "ctrtClsNo", "safeKey");
}
```

이런 테스트는 두 계층으로 나눠 두는 것이 안전하다.

1. **DTO 직접 조립 계약 테스트** — 위 예시처럼 요청 객체를 직접 만들어 직렬화 결과를 검사한다. 전문 스펙 자체를 문서 대신 코드로 고정한다.
2. **와이어 테스트(실제 조립부 경유)** — DTO를 직접 만들지 않고, **실제 프로덕션 코드(HTTP 클라이언트)가 조립한 요청 본문**을 가로채 검사한다(`OasysDirectMembershipWireTest`, `MockRestServiceServer` 사용). `@AllArgsConstructor` 인자 순서가 어긋나 두 필드가 자리를 바꿔치는 것 같은 실수는 1번 방식(DTO를 그 순서 그대로 다시 만듦)으로는 못 잡고, 2번 방식만 잡는다.

새 외부 연동을 추가할 때는 최소한 "필드 구성이 스펙과 정확히 일치한다"(초과 필드도 실패), "고정값이 다른 조건에서도 항상 같은 값으로 나간다", "toString 등 어디에도 민감값이 새지 않는다" 세 가지는 계약 테스트로 고정한다.
