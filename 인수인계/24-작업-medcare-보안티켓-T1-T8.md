## 0. 세 줄 요약

1. AI 건강 상담 서비스 `skix-medcare`의 개인정보 보안성검토 대응을 티켓 T1~T10으로 나눠 진행했고, **코드 작업은 전부 끝나 dev·stg·main 세 브랜치에 반영돼 있다.** 남은 것은 코드가 아니라 **확정·인프라·협의**다.
2. 핵심은 네 가지다 — 건강보험 진료·투약 이력(PHR) **저장 암호화**(T1), 목적 없이 쌓이던 질문·답변 원문 사본 **테이블 파기**(T2), 소유자 키를 전화번호에서 Cognito `sub`로 바꾸고 **전화번호 컬럼을 세 환경에서 DROP**(T5), 그리고 **파기 두 경로**(보유기간 배치 + 사용자 단위 전체 파기)와 **접속기록**(T8).
3. 남은 일은 **보유기간 수치 확정**(확정 전까지 자동 파기가 꺼져 있다), **접속기록 인프라**(CloudWatch→S3 Object Lock 2년, RDS 감사 로깅, 월 1회 점검), **내부 NLB 평문 HTTP 구간 TLS**(T10, 미착수) 세 가지다.

## 1. 배경

### 1-1. 용어

| 용어 | 뜻 |
|---|---|
| **skix-medcare** | AI 건강 상담 서비스(제품명 My Healthcare) 백엔드. Java 21 / Spring Boot 3.4.2 **WebFlux** / Spring Data **R2DBC** / MySQL 8. ECS에 배포한다 |
| **PHR** | Personal Health Record. 여기서는 **건강보험공단에서 스크래핑해 온 진료·투약 이력 원본 JSON**을 말한다. 민감정보(건강정보)다 |
| **PHI** | 건강 관련 개인정보 일반. 이 문서에서는 PHR 원본 + 의료 질의·답변 + 신고 문구를 묶어 가리킨다 |
| **케이론** | 대화 처리를 위탁한 외부 시스템(`skix.phnyx.ai`). **법적으로 수탁자**이고, 대화 원본은 저쪽에 있으며 우리 `kmeta_*` 테이블은 그 사본이다 |
| **kmeta_\*** | 케이론 대화를 내재화해 저장한 우리 테이블군(`kmeta_streams` + 자식 6개 + 검색 인덱스 `kmeta_conversation_search`) |
| **loginId** | 사용자의 **휴대폰번호**. Cognito `custom:login_id`, 없으면 `phone_number`에서 `+82`→`0` 치환해 얻는다 |
| **sub** | Cognito가 계정에 부여한 불투명 UUID. 그 자체로 가명화 효과가 있다 |
| **auth_sub** | 위 `sub`를 담는 DB 컬럼 이름(테이블마다 `CUSTOMER_IF_PHR_AUTH_SUB`, `folder_auth_sub` 등으로 다르다) |
| **Platform** | `backend-api-main`. 회원·기기·구독을 맡는 본체 백엔드. medcare에게는 사용자 신원 조회처이자 탈퇴 통보처다 |
| **관제** | 백오피스(운영자 화면). medcare의 `/medcare/v1/internal/**` 을 호출한다 |
| **envelope 암호화** | 행마다 KMS에서 새 데이터키를 받아(AES-256) 그 키로 값을 암호화하고, **감싼 데이터키를 암호문과 함께 저장**하는 방식. 평문 마스터키가 우리 프로세스에 남지 않고, 키 로테이션 시 기존 암호문 재암호화가 필요 없다 |
| **AAD / EncryptionContext** | 암호문을 특정 행에 묶는 부가 인증 데이터. 다른 행에 복사한 암호문은 복호화가 실패한다 |
| **취급자 / 정보주체** | 개인정보보호법 용어. 취급자는 관제·운영자, 정보주체는 서비스 사용자 본인 |
| **안전성 확보조치 제8조** | 개인정보의 안전성 확보조치 기준 제8조(접속기록의 보관 및 점검). 민감정보 처리시스템은 **2년 보관 · 월 1회 점검 · 위·변조 방지**가 따라붙는다 |

### 1-2. 문제

보안성검토 착수 시점(2026-08-06)에 실측한 결과는 아래와 같았다. 전부 "설정을 조이면 되는" 종류가 아니라 저장 구조 자체의 문제였다.

| # | 문제 | 왜 문제인가 |
|---|---|---|
| 1 | PHR 원본(`customer_if_phr_data.CUSTOMER_IF_PHR_DATA`)이 **평문 mediumtext** | 이 저장소에서 가장 민감한 데이터인데 DB를 읽을 수 있으면 그대로 읽힌다 |
| 2 | `customer_if_log_text`에 **질문 원문 JSON과 답변 전문(최대 256KB)이 쌓이고 있었고, 읽는 코드가 어디에도 없었다** | 목적 없는 PHI 사본. 타임스탬프 컬럼조차 없어 기간 기반 파기도 불가능했다 |
| 3 | **휴대폰번호가 5개 테이블에 평문 저장** | 고유식별정보는 아니지만 식별성이 높다. 덤으로 번호를 바꾸면 그 사용자 데이터가 고아가 됐다 |
| 4 | **파기 경로가 통째로 없었다** — 회원 탈퇴 연계 파기, 사용량 로그 파기, 신고 파기 전부 | 보유기간이 지나도, 사용자가 탈퇴해도 데이터가 남는다 |
| 5 | **접속기록이 없었다** | 취급자가 남의 건강정보를 조회·파기해도 흔적이 없다. 법정 요건 미충족 |
| 6 | DB 연결이 TLS로 붙는다는 **보장이 없었다** | r2dbc-mysql 기본값 `PREFERRED`는 협상 실패 시 **오류 없이 평문으로 떨어진다** |
| 7 | 내부 구간(Platform→medcare, medcare→PHR 스크래퍼)이 **평문 HTTP** | NLB를 거치는 사내망이지만 전송구간 암호화 요건은 충족하지 않는다 |

### 1-3. 티켓 구성

한 브랜치(`feature/security-review-hardening`)에 티켓별 커밋을 쌓았다. **배포는 한 번인데 앞뒤로 순서가 강제되는 작업이 흩어져 있다**는 것이 이 작업의 가장 큰 함정이다(§8).

| 티켓 | 내용 | 결과 |
|---|---|---|
| T1 | PHR 원본 KMS envelope 암호화 + 레거시 평문 마이그레이션 | 완료 |
| T2 | 사용량 로그의 질문·답변 원문 저장 중단 + 기존 테이블 파기 | 완료 |
| T3 | 데이터 맵 · 보유기간 · 파기정책 문서화 | 문서 완료 / **보유기간 수치 미확정** |
| T4 | Flyway 도입 | **보류 결정**(§4-4) |
| T5 | 소유자 키 loginId → Cognito sub 단독 전환 + 백필 + 전화번호 컬럼 DROP | **완결**(별도 후속 티켓이 있다, §4-3) |
| T6 | 보유기간 경과 배치 파기 + 사용자 단위 전체 파기(탈퇴·파기요구) | 완료 / **자동 파기는 꺼둔 상태** |
| T7 | 대화 내용 저장 암호화 | **범위 재산정 후 신고 테이블만 암호화**, 나머지는 근거 남기고 보류 |
| T8 | 개인정보 접속기록 | 앱 코드 완료 / **인프라 미완** |
| T9 | DB 연결 TLS 강제 | 완료 |
| T10 | 내부 NLB TLS 종단 | **미착수**(인프라팀) |

## 3. 전체 그림

```
[앱]  IdToken(Cognito)
   │
   ├─▶ skix-medcare  (ECS / WebFlux / R2DBC)
   │        │
   │        ├─ 채팅 ──▶ 케이론(수탁사)  ── 대화 원본 ──┐
   │        │            └ 내재화 배치 ─▶ kmeta_* (사본, 평문·검색 대상)
   │        │
   │        ├─ PHR ──▶ PHR 스크래퍼(내부 NLB :8030, 평문 HTTP ← T10 대상)
   │        │            └ customer_if_phr_data.CUSTOMER_IF_PHR_DATA  **ENC1: 암호문(T1)**
   │        │
   │        ├─ 신고 ──▶ customer_chat_report.report_question/answer/text  **ENC1: 암호문(T7)**
   │        │
   │        └─ 사용량 ─▶ customer_if_log (토큰수·시각만. 원문 저장 중단 T2)
   │
   └─▶ backend-api-main (Platform)
            ├─ 관제 사용량 로그 조회 ─▶ medcare POST /internal/log/list  (전화번호 계약 유지)
            └─ 회원 탈퇴 ────────────▶ medcare POST /internal/users/purge?authSub=&apply=true
                                        (Cognito 삭제 **전에** 호출 — 사후엔 sub 해석 불가)

[감사]  모든 /medcare/v1/internal/** 호출 → InternalApiAuditFilter → 전용 로거 "AUDIT" 한 줄
        파기 3종(USER_DATA_PURGE / RETENTION_PURGE / PHR_PURGE) → 서비스에서 결과와 함께 기록
```

암호화·파기·기록의 경계를 한 줄로 요약하면 이렇다.

- **암호화한 것**: PHR 원본, 신고 테이블(질문·답변·신고 사유). 둘 다 검색 대상이 아니고 읽는 빈도가 낮다.
- **암호화하지 않은 것**: 대화 본문(`kmeta_*`, `customer_folder_chat`). 검색 인덱스가 평문이어야 검색이 성립하므로 원본만 암호화하면 **보호 효과 없이 지연만 는다**(§6의 5번).
- **기간으로 지우는 것**: 사용량 로그, 신고, PHR 데이터. **대화는 기간으로 지우지 않는다** — 정책이 "사용자 삭제 시까지"다.
- **사용자 단위로 지우는 것**: 대화(케이론 먼저)·폴더·PHR·사용량 로그·평가. 신고만 분쟁 대비로 보존한다.

## 4. 티켓별 상세

### 4-1. T1 — PHR 원본 KMS envelope 암호화

**무엇을.** `customer_if_phr_data.CUSTOMER_IF_PHR_DATA`(건강보험공단 스크래핑 원본 JSON 전문)를 암호문으로 저장한다.

**왜.** 이 저장소에서 가장 민감한 데이터이고, 평문 `mediumtext`였다. 민감정보(건강정보)는 저장 암호화가 요건이다.

**어떻게.**

- 포맷 `ENC1:b64(감싼 데이터키):b64(iv):b64(AES-256-GCM 암호문)`. **컬럼 타입은 그대로**다(base64라 약 1.4배).
- 행마다 KMS `GenerateDataKey`(AES_256)로 **새 데이터키**를 받는다. 마스터키 평문이 프로세스에 남지 않는다.
- 행 바인딩: KMS `EncryptionContext = {table, rowKey}`, GCM AAD = `table:rowKey`. PHR은 `customer_if_phr_data:{phrId}`. **다른 행에 암호문을 복사해 넣으면 복호화가 실패한다.**
- `rowKey`로 `phrId`(인증행 FK)를 골랐다. **`loginId`를 쓰지 않은 이유는 T5에서 `sub`로 바뀔 값이라서다** — AAD로 썼다면 T5 실행 순간 기존 암호문이 전부 복호화 불가가 된다.
- 조회 시 레거시 평문 행은 `ENC1:` 접두사가 없어 그대로 통과한다(무중단 전환).
- 복호화 호출에 `keyId`를 명시한다(키 스왑 방어). EncryptionContext는 CloudTrail에 남아 감사 단서가 된다.
- 설정 `column.crypto.mode` = `kms`(ecs 기본) / `off`(localhost 기본). **kms 모드에서 키 ARN이 없거나 비정상이면 기동 실패(fail-closed).**
- AWS SDK `KmsAsyncClient` + netty-nio를 쓴다. WebFlux 이벤트 루프를 막지 않기 위해서다.

**검증.** 신규 적재 후 `SELECT LEFT(CUSTOMER_IF_PHR_DATA, 5)`가 `ENC1:`인지, 앱 `GET /phr/data`가 정상 응답하는지. 레거시 마이그레이션 API로 잔여 0까지 소진(3환경 완료). 마이그레이션 도구는 소진 후 코드에서 제거했다(`c62a004`).

**남은 것.** 없다. 다만 **KMS 키를 절대 삭제하지 말 것**(삭제 대기도 금지) — 키가 사라지면 전 데이터가 복구 불가다. 키 정책에 `DenyKeyDeletion`(Principal `*`로 `ScheduleKeyDeletion`·`DeleteImportedKeyMaterial` Deny)을 넣어 구조로 막아뒀다.

### 4-2. T2 — 사용량 로그의 원문 저장 중단

**무엇을.** `customer_if_log_text` 테이블에 쌓던 질문 원문 JSON(`customer_if_query`)과 답변 전문(`customer_if_text`, 최대 256KB) 저장을 없애고, 기존 행은 테이블째 파기했다.

**왜.** 실측 결과 이 테이블은 **쓰기 전용**이었다. skix-medcare와 형제 프로젝트 어디에도 읽는 코드가 없었고, 리포지토리는 `ReactiveCrudRepository` 기본 메서드뿐이었다. 같은 내용이 `kmeta_chat_inputs.query` / `kmeta_chats.response`에 이미 있다(대화 조회의 정본). 타임스탬프 컬럼이 없어 기간 파기도 불가능했다. **목적 없이 쌓이기만 하던 PHI 사본**이다.

**어떻게.**

- `ChatService.persistUsageLog`가 `customer_if_log`(토큰 수·시각·strid)만 남긴다. `LogService.createText`·`CustomerIfLogText` 엔티티·`CustomerIfLogTextRepository`를 삭제했다.
- `StreamChatAggregator`의 답변 원문 누적(`fullText`, 256KB 상한)을 제거했다. **부수 효과로 동시 스트림당 최대 256KB 힙 점유가 사라진다.**
- 요청 로그 JSON 생성(`buildRequestLog`)도 제거해 질문 원문이 애초에 메모리에 직렬화되지 않게 했다.
- 회귀 방어 테스트 `ChatStreamTerminationTest.사용량_로그에_질문과_답변_원문이_실리지_않는다`.
- 기존 행은 **RENAME → DROP**(SQL은 부록 B-1). **백업을 뜨지 않는다** — 백업은 파기 대상 PHI를 다른 곳에 한 벌 더 남기는 것이다. 파기 사실(일시·실행자·대상)만 기록으로 남긴다.

**순서 제약(중요).** 이 테이블은 **사용자 단위 파기(T6) 대상이 아니다.** 소유자 조건 DELETE를 코드에 넣으면 문서대로 DROP한 직후부터 모든 사용자 파기가 `1146 table doesn't exist`로 실패한다. 그래서 테이블 전체 파기로 처리하고, **탈퇴 연계 파기를 가동하기 전에** 끝내는 것으로 순서를 고정했다(§8-1의 ④-4). 끝내지 않으면 탈퇴한 사용자의 질문·답변 원문이 남은 채 "파기 완료"가 기록된다.

**검증.** 배포 후 채팅 정상 동작, `customer_if_log` 토큰 집계 정상(앱의 한도 표시), 신규 `customer_if_log_text` 행이 생기지 않음. 3환경 DROP 완료.

**남은 것.** 없다. 참고로 `customer_if_log.customer_if_token_usage_text`는 **남는다** — 케이론이 통보한 token_usage INFO 청크라 답변 내용이 아니고, 한도 산정 근거라 보존이 필요하다.

### 4-3. T5 — 소유자 키 loginId → Cognito sub (보안 관점 요약 + 컬럼 DROP 완결)

> 이 티켓의 소유자 키 전환은 뒤에 이어진 소유자 키 통합 작업으로 계속된다. **여기서는 보안성검토 관점의 결론과 T5 완결(전화번호 컬럼 DROP + 백필 코드 제거)만 정리한다.** 다만 인수자가 이 문서만으로 판단·실행할 수 있도록 DDL·백필 SQL 전문은 부록 B-2에 그대로 실었다.

**무엇을.** 5개 테이블(`customer_if_phr`, `customer_if_phr_data`, `customer_folders`, `customer_folder_chat`, `customer_if_log`)의 소유자 키를 휴대폰번호에서 Cognito `sub`로 바꾸고, **전화번호 컬럼을 세 환경 모두 DROP**했다.

**왜(보안 관점).** 휴대폰번호가 5개 테이블에 평문으로 있었다. `sub`는 불투명 UUID라 그 자체로 가명화 효과가 있고, 이미 절반의 테이블과 케이론 연동(`X-API-UID`)이 sub 기준이라 일관성도 회복된다. 부수 효과로 전화번호 변경 시 데이터가 고아가 되는 문제가 사라진다.

**어떻게(핵심 결정 두 가지).**

1. **전환기 폴백을 쓰지 않았다.** `auth_sub = :sub OR (auth_sub IS NULL AND login_id = :loginId)` 같은 임시 조건절을 두지 않는 대신 **순서가 계약**이다 — 백필이 배포보다 먼저 끝나야 한다. 배포된 코드는 `auth_sub`로만 조회하므로 그 값이 빈 행은 **사용자에게 보이지 않는다**(데이터는 그대로 있고 조회만 안 된다).
2. **소유를 증명할 수 없는 행은 자동 귀속하지 않는다.** 방어가 세 겹이다.
   - SQL 백필의 `HAVING COUNT(DISTINCT auth_sub) = 1` — 한 번호에 sub가 둘이면(번호 재사용) 매핑에서 제외.
   - 로그의 sub와 Platform이 알려주는 '지금 이 번호의 계정 sub'가 다르면 제외.
   - **계정 생성 시각보다 오래된 행은 UPDATE가 건드리지 않는다.**

   세 번째가 왜 필요한가 — `COUNT(DISTINCT sub)=1`은 "이 번호로 로그를 남긴 sub가 하나"라는 뜻이지 "번호가 재사용되지 않았다"는 뜻이 아니다. **이전 소유자가 채팅 없이 PHR·폴더만 남겼으면 로그에 아무 흔적이 없고, 그 행이 지금 계정에 붙는다.** 남의 건강정보가 붙는 사고다.

**완결(2026-08-11).**

- 세 환경 모두 잔여 0 확인 후 전화번호 컬럼 DROP 실행(SQL은 부록 B-3).
- 백필 도구 코드 제거 — `520d660`. `OwnerKeyBackfillService`·`OwnerKeyBackfillRepository`·`POST /internal/owner-key/backfill`·`CustomerIfLogRepository.findOwnerKeyPairs`·`customer_if_log_text` 스키마 파일 삭제, DDL 주석 정합화, 데이터 맵 갱신(-642줄).
- **단 `countRowsMissingAuthSub`는 `OwnerlessRowCountRepository`로 옮겨 보존했다.** `auth_sub`만 참조해 컬럼 DROP과 무관하고, 사용자 파기의 '미배정 잔여 경고' 안전장치다. **지우면 안 된다.**

**앱 영향 — 수정 불필요로 확정(2026-08-11).** 응답에서 제거된 필드는 폴더 DTO 4개(`folderLoginId`/`chatLoginId`/`createLoginId`/`updateLoginId`)뿐이다. iOS의 `FolderResponseDTO.folderLoginId`만 non-optional `String`이라 폴더 **생성(POST)·이름변경(PUT)** 응답 디코딩이 깨졌다(목록은 별도 DTO라 멀쩡 → "폴더는 보이는데 생성만 안 됨"으로 나타난다). Swift는 키 누락과 null을 **둘 다** 던지므로 null로는 해결되지 않아 **서버가 빈 문자열을 주도록** 했다(`343af51`). iOS·Android 모두 이 필드 사용처가 0건이라 동작 변화는 없다. **이건 부채다 — iOS가 옵셔널로 바꾸면 서버의 빈 문자열 자리표시자를 제거한다.**

**여기서 얻은 일반 교훈**: 서버가 응답 필드를 **뺄** 때만 클라이언트가 깨진다. 전수 대조 대신 `git diff`로 제거된 필드만 좁히는 편이 빠르고 정확하다.

**남은 것.** T5 자체는 없다. 관제 `POST /internal/log/list`의 **전화번호 요청 계약은 유지**되고(서버가 Platform API로 sub를 해석, 응답의 `loginId`는 요청값 에코) 이 계약은 바꾸지 않는다.

### 4-4. T3 · T4 — 데이터 맵과 스키마 마이그레이션

**T3(데이터 맵).** 테이블 × (보유 항목·분류·식별키·목적·암호화·읽는 코드 유무·파기 경로·보유기간) 전수 인벤토리를 저장소 안(`docs/data-map.md`)에 만들었다. **스키마와 함께 버전 관리해야 정확도가 유지되므로 별도 위키가 아니라 저장소에 뒀고, 스키마를 바꾸면 같은 MR에서 갱신하는 것이 규칙이다.**

실측으로 확인한 것: 고유식별정보(주민번호 등) 컬럼은 **없다.** loginId 평문 보유는 5개 테이블(T5로 해소). 파기 경로 3종이 전부 부재(T6으로 해소).

### 4-5. T6 — 파기 두 경로

파기 경로는 성격이 다른 **두 갈래**이고 섞으면 안 된다.

#### (가) 보유기간 경과 배치 파기

**대상은 세 테이블뿐이다.**

| 테이블 | 목적 | 기본 보유기간 | 기준 컬럼 | 환경변수 |
|---|---|---|---|---|
| `customer_if_log` | 채팅 한도 산정 | 365일 | `customer_if_create_date` | `RETENTION_USAGE_LOG_DAYS` |
| `customer_chat_report` | 신고 처리·분쟁 대비 | 1095일 | `create_date` | `RETENTION_CHAT_REPORT_DAYS` |
| `customer_if_phr_data` | PHR 제공 | 365일 | `create_date` | `RETENTION_PHR_DAYS` + **전용 게이트** |

**대화와 PHR 인증행은 대상이 아니다.** 보유 정책이 "사용자 삭제 시까지"라 기간으로 지우면 사용자가 지우지 않은 데이터가 사라진다. 이 사실을 테스트(`대화와_PHR은_파기_대상이_아니다`)로 고정해 뒀다.

**안전장치 — 전부 의도된 기본값이다.**

1. `retention.auto-purge=false`가 기본. 정기 배치는 존재하지만 아무것도 지우지 않는다. **보유기간이 아직 제안값이라, 확정 전에 자동으로 도는 것이 가장 위험하다.**
2. 내부 API는 **모의 실행이 기본**(`apply=false`) — 대상 건수만 보고한다.
3. 삭제 상한 `batch-limit` 기본 5000 — 첫 실행에서 거대한 삭제 트랜잭션이 생기지 않는다. 잔여 0까지 반복 호출한다.
4. 보유기간 `@Positive` 검증 — 0이나 음수를 넣으면 **기동이 실패**한다(전량 삭제 방지).
5. 기준은 **날짜 경계(자정)** — 같은 날 두 번 돌려도 대상이 같아 파기 기록을 사후에 재현할 수 있다.
6. 파기 기록은 **테이블별로 실행 직후** 남긴다(뒤에서 실패해도 앞의 삭제가 기록에서 사라지지 않게).

> **⚠️ 두 플래그는 축이 다르다. 여기서 사고가 난다.**
>
> - `RETENTION_AUTO_PURGE`는 **정기 실행 여부만** 정한다. **`false`여도 내부 API로 `apply=true`를 부르면 사용량 로그·신고는 지워진다.** 스케줄러 스위치지 안전장치가 아니다.
> - `RETENTION_PHR_PURGE_ENABLED`는 **PHR 전용 게이트**다. `apply=true`여도 이 값이 `false`면 PHR은 건드리지 않는다. 이 플래그를 따로 둔 이유는 **기존 API의 영향 범위가 조용히 넓어지는 것**을 막기 위해서다 — 사용량 로그를 정리하려던 운영자가 보유기간 미확정 PHR까지 지우게 되면 안 된다.
> - 비활성 테이블은 **API 응답과 배치 요약 로그 양쪽에** 표시된다(스케줄러는 컨트롤러를 안 거치므로 한쪽만으로는 부족하다).

설정(전부 `application-ecs.yml`, 태스크 정의에 없으면 아래 기본값):

```yaml
retention:
  usage-log-days:      ${RETENTION_USAGE_LOG_DAYS:365}
  chat-report-days:    ${RETENTION_CHAT_REPORT_DAYS:1095}
  phr-days:            ${RETENTION_PHR_DAYS:365}
  batch-limit:         ${RETENTION_BATCH_LIMIT:5000}
  auto-purge:          ${RETENTION_AUTO_PURGE:false}
  phr-purge-enabled:   ${RETENTION_PHR_PURGE_ENABLED:false}
  purge-cron:          ${RETENTION_PURGE_CRON:0 30 4 * * *}   # 04:30 KST, 드리프트 점검(04:00) 뒤
```

파기 배치는 케이론을 호출하지 않고 변환 배치와 테이블도 겹치지 않아 공용 `BatchExecutionLock`을 쓰지 않는다. 자기 실행끼리만 겹치지 않게 전용 가드를 둔다.

#### (나) 사용자 단위 전체 파기 — 탈퇴·파기요구

**회원 탈퇴 통보와 정보주체의 파기 요구가 같은 API를 쓴다.**

| 대상 | 처리 |
|---|---|
| 케이론(수탁자)의 대화 원본 | **먼저** 삭제 — 대화별 순차 호출 |
| `kmeta_streams` | 삭제(자식 6테이블 + 검색 인덱스는 FK CASCADE) |
| `kmeta_conversation_search` | **명시 삭제.** FK가 나중에 추가된 제약이라 기존 환경에는 없을 수 있고, 없으면 대화 전문이 그대로 남는다 |
| `customer_folder_chat` → `customer_folders` | 순서대로 삭제 |
| `customer_if_phr`, `customer_if_phr_data` | 삭제 |
| `customer_if_log`, `customer_chat_rating` | 삭제 |
| `customer_chat_report` | **보존** — 분쟁 대비(개인정보보호법 제21조 예외). 보고에 "보존 N건"으로 드러낸다 |

**설계상 중요한 세 가지.**

1. **키는 Cognito sub 하나다.** 전화번호를 받지 않는다 — 저장이 전부 sub 기준(T5)이고, **탈퇴 시점에는 Platform에서 계정이 사라져 전화번호를 sub로 해석할 수 없다.** 그래서 호출자가 탈퇴 처리 **전에** sub를 확보해 넘겨야 한다.
2. **케이론 삭제가 먼저다.** 대화 원본은 수탁자에게 있고 `kmeta_*`는 사본이다. 로컬을 먼저 지우면 **어떤 대화를 케이론에서 지워야 하는지 알 방법이 사라진다.** 케이론 삭제가 하나라도 실패하면 로컬을 건드리지 않고 실패로 끝낸다. 재시도하면 남은 것부터 이어서 지운다. **부분 성공을 '파기 완료'로 기록하면 감사 기록이 실제 상태와 어긋난다.**
3. **케이론 대화 목록은 열거를 모두 끝낸 뒤에 삭제한다.** 오프셋 페이지네이션으로 열거하면서 동시에 삭제하면 뒤 페이지가 앞으로 당겨져 건너뛴다 — 검토에서 실제로 잡힌 결함이다(250건 중 100~199번이 조회조차 되지 않았다). **목록을 변경하면서 오프셋 페이지네이션을 하면 안 된다.**

#### (다) 탈퇴 연계 — `backend-api-main` 측 (`b2138c78`)

medcare가 받는 쪽을 만들어도 **Platform이 부르지 않으면 아무 일도 일어나지 않는다.** 그래서 호출 측도 직접 구현했다.

- `UserService.deleteUser`에서 **Cognito 삭제 전에** `MyHealthCareService.purgeUserData(sub)`를 호출한다.
- **한 `loginId`에 Cognito 계정이 여러 개일 수 있다**(`getUserAccountListByLoginId`가 List를 반환한다). 토큰의 sub 하나로는 부족해 **계정 목록 전체를 순회**하고, 토큰 sub는 목록 누락 대비 폴백으로 함께 넣는다(`LinkedHashSet`으로 중복 제거).
- **실패 정책**: 탈퇴는 계속 진행하고 **sub를 포함한 ERROR 로그**를 남긴다(기존 OASYS 연동과 같은 정책). medcare 파기는 행 단위 멱등이라 그 sub로 같은 API를 재호출하면 남은 것부터 이어서 지워진다 — **ERROR 로그의 sub가 곧 재시도 수단이다.**
- 파기 호출의 `X-Acting-Admin`은 **`platform-withdrawal` 고정**이다. 관리자 조작이 아니라 본인 요청에 따른 시스템 호출이므로 사용자 전화번호를 medcare 접속기록의 행위자로 남기지 않는다.
- 부수 변경: `log/list` 호출의 `X-Acting-Admin`이 고정값 `"admin"`이었는데 `jwtTokenUtil.getLoginId()`의 실제 관제 관리자 값으로 바꿨다(해석 실패 시 기존값 폴백). **접속기록의 '누가'를 특정하기 위한 변경**이다.

**검증.** 테스트 계정으로 모의 실행 → 건수 확인 → `apply=true` → 로그에서 "사용자 파기 완료 - user: …, 케이론 대화 N건, 로컬 M행" 확인 → 재실행 시 0행/0건(멱등) 확인 → 케이론에서도 사라졌는지 확인.

**남은 것.** ⑴ **보유기간 확정**(확정 전까지 `RETENTION_AUTO_PURGE=false` 유지). ⑵ 확정 후 수동 첫 소진 → `RETENTION_AUTO_PURGE=true` 배포. ⑶ `backend-api-main` 탈퇴 연계의 **stg·prd 배포 확인**(main 미반영). ⑷ 신고 테이블 보존이 정책상 맞는지 법무 확인.

### 4-6. T7 — 대화 내용 암호화 (범위 재산정)

**결론 먼저.** 원래 범위는 "대화 원본(`kmeta_chats`, `kmeta_chat_inputs`, `customer_chat_report`) 암호화 + `customer_folder_chat` 참조화"였다. 착수 전 실측 결과 **`customer_chat_report`만 실익이 있어 그것만 암호화했고, 나머지는 근거를 남기고 보류한다.**

| 대상 | 결정 | 근거 |
|---|---|---|
| `customer_chat_report.report_question` / `report_answer` / `report_text` | **암호화 완료** | 대화가 지워지고 사용자가 탈퇴해도 남는 **유일한 대화 사본**(분쟁 대비 3년). 검색 대상이 아니고 읽는 코드가 없어 지연 영향 0. 신고는 저빈도라 KMS 비용도 무시할 수준 |
| `kmeta_chats.response`, `kmeta_chat_inputs.query` | **보류** | 아래 |
| `customer_folder_chat.chat_question` / `chat_answer` | **보류** | 대화 삭제·탈퇴 시 함께 사라져 수명이 짧고, 폴더 목록은 사용자가 자주 여는 경로라 행마다 KMS 복호화가 붙는다. 참조화는 앱이 값을 보내는 구조라 앱 변경을 동반한다 |
| `kmeta_conversation_search.content_text` | **평문 유지(확정)** | 검색 기능과 원리적으로 상충 |

**왜 kmeta 원본 암호화를 보류하는가.** `kmeta_conversation_search.content_text`가 **같은 대화의 질문·답변을 전부 이어붙인 평문 사본**이다. 검색(ngram FULLTEXT + 1자 LIKE 폴백)이 성립하려면 이 컬럼은 평문이어야 한다. 그 상태에서 원본만 암호화하면 **DB를 읽을 수 있는 공격자는 그냥 `content_text`를 읽으면 된다.** 위험은 그대로인데 비용만 는다 — 대화 상세 조회가 턴마다 KMS 복호화를 타므로 20턴 대화면 20회다.

**blind index는 대안이 아니다.** HMAC 파생 컬럼은 동등 비교 전용이라 부분 일치(ngram·1자 LIKE)를 지원하지 못한다. 2-gram 토큰 인덱스로 우회해도 ⑴ 결정적 HMAC의 빈도 분석 취약, ⑵ 1자 검색 불가, ⑶ 응답 스니펫(매치 앞뒤 40/80자) 생성에 어차피 원문이 필요하다.

**재검토 조건은 하나다 — 검색 인덱스가 평문이 아니게 되는 때**(검색 요구 완화, 전용 검색엔진 분리, blind index 대체). 그 전까지 대화 내용의 실질 통제는 소유자 스코프 강제(적용 완료), 보유기간·파기(T6), 접속기록(T8), 전송구간 암호화(T9·T10)가 맡는다.

**무엇이 바뀌었나(코드).**

- T1에서 PHR 전용으로 만든 암호화 모듈을 **컬럼 단위로 일반화**했다. `PhrCryptoPort` → `ColumnCryptoPort`, `encrypt(값, table, rowKey)` / `decrypt(값, table, rowKey)`. 어댑터도 `KmsColumnCryptoAdapter` / `NoopColumnCryptoAdapter`로 개명.
- 설정 `phr.crypto.*` → `column.crypto.*`, 환경변수 `PHR_CRYPTO_MODE` → `COLUMN_CRYPTO_MODE`, `PHR_KMS_KEY_ARN` → **`MEDCARE_KMS_KEY_ARN`**. **T1이 아직 배포 전이라 기존 암호문이 없었던 것이 이 개명이 안전했던 이유다.**
- **신고의 행 바인딩 키는 `(신고자 sub, 앱이 만든 요청 UUID)`** 다. `report_id`는 INSERT 후에야 정해져 쓸 수 없고, 이 쌍은 유니크 키라 INSERT 전에 확정되며 이후 바뀌지 않는다.
- **신고 사유(`report_text`)도 암호화 대상**이다. "짧은 문구라 대화 내용이 아니다"는 안전의 근거가 아니다 — 사용자 자유 입력이라 200자 안에 병명·투약 이력이 얼마든지 들어간다. 봉투를 담으려고 컬럼을 `varchar(200)` → `text`로 넓혔다(**배포 전 DDL 선행 조건**, 부록 B-4).
- **KMS 키는 환경당 하나**를 PHR 원본과 신고 3컬럼이 공유한다(EncryptionContext로 구분).

**주의 — 나중에 사고가 날 지점.** 신고 테이블은 **읽는 코드가 없다**(medcare·형제 프로젝트 전수 확인). 관제가 나중에 신고 조회 화면을 만들면 **복호화 경로를 함께 만들어야 한다.** DB를 직접 조회하면 암호문만 보인다. 이 사실을 관제 팀에 미리 알려야 한다.

**수용한 잔여 위험.** 암호화 여부를 `ENC1:` 접두사로 판정한다. 레거시 평문 값이 마침 `ENC1:`로 시작하면 마이그레이션이 그 컬럼을 건너뛰면서 완료로 집계한다. 사용자가 그 문자열을 그대로 입력해야 성립하고 영향은 그 행 하나가 복호화되지 않는 것뿐이라, 일회성 배치가 훑는 유한한 기존 행을 위해 두 테이블에 `crypto_version` 컬럼을 더하지 않기로 했다. 마이그레이션 후 잔여 0 확인으로 갈음했다(3환경 완료).

### 4-7. T8 — 개인정보 접속기록

**무엇을.** 취급자(관제)의 내부 API 접근과 파기 실행을 전용 로거 `AUDIT`에 고정 형식 한 줄로 남긴다.

**왜.** 안전성 확보조치 기준 제8조가 요구한다 — 계정, 접속일시, 접속지 정보, 처리한 정보주체 정보, 수행업무. 민감정보 처리시스템이므로 **2년 보관 · 월 1회 점검 · 위·변조 방지**가 따라붙는다. 착수 전에는 기록 자체가 없었다.

**범위 — 취급자 접근만.** 정보주체 본인이 자기 데이터를 보는 것은 취급자 접근이 아니므로 기록하지 않는다. 남기면 감사 로그가 트래픽만큼 불어나 **정작 봐야 할 관제 접근이 묻힌다.** 이 결정을 테스트(`일반_사용자_API는_접속기록_대상이_아니다`)로 고정했다.

**기록 형식.**

```
action=POST /medcare/v1/internal/users/purge?apply=true actorType=ADMIN actor=admin-42 subject=sub-1111 result=200 ip=10.0.0.5
```

| 키 | 의미 | 요건 대응 |
|---|---|---|
| `action` | 메서드 + 경로, 또는 배치 이름 | 수행업무 |
| `actorType` | `ADMIN`(관제) / `USER`(정보주체) / `SYSTEM`(배치) | 계정 구분 |
| `actor` | `X-Acting-Admin` 값. 없으면 `UNIDENTIFIED`, **인증 실패(401·403)면 `UNAUTHENTICATED`** | 계정 |
| `subject` | 정보주체 sub(가명) 또는 마스킹 전화번호, 테이블 파기는 테이블명 | 처리한 정보주체 |
| `result` | HTTP 상태코드 또는 `ERROR:예외명`, 배치는 건수 | 결과 |
| `ip` | `X-Forwarded-For`의 **마지막** 항목 | 접속지 정보 |

로그 시각은 기존 패턴(`%d{yyyy-MM-dd HH:mm:ss.SSS}`)이 앞에 붙고, 패턴에 `%logger{36}`가 있어 **라인에 `AUDIT` 로거 이름이 포함된다**(CloudWatch 필터의 근거).

**기록 지점.**

- **모든 `/medcare/v1/internal/**` 호출** — `InternalApiAuditFilter`가 자동으로 남긴다. 컨트롤러마다 감사 호출을 넣지 않은 이유는 **누락 방지**다. 내부 API가 하나 늘 때마다 사람이 기억해야 하는 구조면 언젠가 빠진다. **인증 필터보다 앞에 있어 401/403도 남는다** — 실패한 접근 시도야말로 봐야 할 신호다.
- **관제 로그 조회(`/internal/log/list`)** — 정보주체가 본문에 있어 필터가 쿼리에서 채우지 못한다. 컨트롤러가 마스킹된 전화번호를 exchange 속성으로 넘기고 **필터가 한 줄로 합쳐** 남긴다. 따로 한 줄 더 남기던 방식은 결과·접속지 없는 반쪽 기록이 하나 더 생겨서 되돌렸다.
- **파기 3종** — `USER_DATA_PURGE`, `RETENTION_PURGE`, `PHR_PURGE`는 서비스에서 결과와 함께 기록한다.
- `AUDIT` 로거 레벨을 `INFO`로 **고정**했다 — 앱 로그 레벨(`LOG_LEVEL_APP`)을 낮춰도 접속기록은 남는다.

**신뢰 경계 — 요청이 주장하는 값과 우리가 관측한 값.** 필터가 인증보다 앞에 있어서 이 구분이 특히 중요하다.

| 값 | 출처 | 취급 |
|---|---|---|
| `actor` | `X-Acting-Admin` 헤더 | 요청이 **인증을 통과한 경우에만** 인정. 401·403이면 `UNAUTHENTICATED`로 적고 주장값은 버린다 — 그렇지 않으면 키 없는 외부 요청이 임의의 관리자 이름을 기록에 심을 수 있다 |
| `ip` | `X-Forwarded-For` | **마지막 항목**을 쓴다. ALB는 기존 헤더를 유지한 채 자기가 본 주소를 **뒤에 덧붙이므로 첫 항목은 요청자가 써 보낸 값**이다. 전제는 앞단 append 프록시가 ALB 하나라는 것 — 체인이 늘면 신뢰 홉 수를 함께 조정한다 |
| `subject` | 쿼리 `authSub` 또는 컨트롤러가 넘긴 마스킹 값 | 가명 식별자라 그대로 적되 **제어문자·U+2028/U+2029를 `_`로 치환하고 200자에서 자른다**(위조 라인 삽입 방지) |

인증된 호출에서도 `X-Acting-Admin`은 호출 측(`backend-api-main`)이 관제 토큰에서 뽑아 넣는 값이다. **그 신뢰는 내부 API 키 인증에서 온다** — medcare가 관리자 신원을 직접 검증하지는 않는다.

**값 없음 표기가 앱 로그와 다른 것은 의도적이다.** 앱 로그는 `[ABSENT]`/`[EMPTY]`/`[REDACTED:사유]`로 '없는 이유'를 구별하지만(§6의 10번), **접속기록은 전부 `-`로 남긴다.** 2년 보관 대상이고 CloudWatch 구독 필터가 S3로 분리해 월 1회 점검에 쓰이므로, 센티널을 바꾸면 과거 데이터와 신규 데이터의 표기가 갈리고 `subject != '-'` 같은 기존 점검 조건이 조용히 깨진다. 표기 통일은 로그 규약이 아니라 **보관·점검 절차와 함께 다룰 별건**이다.

**남은 취약점 — 행위자 식별.** 내부 API는 공유 시크릿(`X-Internal-Api-Key`) 하나로 인증한다. 서버는 "관제가 불렀다"까지만 알 수 있고 **어느 운영자인지는 `X-Acting-Admin`에 전적으로 의존한다.** 지금은 헤더가 없으면 `UNIDENTIFIED`로 남긴다("기록은 남았는데 아무도 책임지지 않는" 상태보다 낫다). 요건의 '계정'을 충족하려면 결국 관제가 모든 호출에 이 헤더를 보내야 한다. **전부 보내는 것이 확인되면 헤더 없는 호출을 400으로 거부하도록 조일 수 있다.** 지금 조이지 않은 것은 관제가 못 보내는 엔드포인트가 있으면 운영이 멈추기 때문이다.

**남은 것(전부 인프라·절차).** §9-1의 3·4·5번.

### 4-8. T9 · T10 — 전송구간

**T9(DB 연결 TLS) — 완료, 커밋 `ee8780b`.**

착수 시 가설은 "TLS 설정이 아예 없다"였는데 **실측 결과는 달랐다.** r2dbc-mysql의 기본값은 미지정이 아니라 `PREFERRED`다 — 서버가 지원하면 이미 TLS로 붙지만, **협상에 실패하면 오류 없이 조용히 평문으로 떨어진다.** 그래서 `spring.r2dbc.properties.sslMode=REQUIRED`로 강제했다(드라이버가 문자열을 `toUpperCase` 후 enum 파싱하는 것 확인).

```yaml
spring:
  r2dbc:
    properties:
      sslMode: ${DB_SSL_MODE:REQUIRED}
```

- **되돌리기 수단을 열어 뒀다** — 태스크 정의에 `DB_SSL_MODE=PREFERRED`를 넣으면 **재빌드 없이** 즉시 완화된다.
- **이 설정이 배포 시 드러난다** — TLS 협상이 안 되면 기동 시 연결이 실패한다. 배포가 곧 검증이다.
- `VERIFY_IDENTITY`(서버 인증서 검증)까지 올리려면 **RDS CA 번들 동봉이 선행 과제**다.
- 같은 문제가 형제 저장소 두 곳(`skix-security`, `skix-openapi`)에도 있었다. 그쪽은 JDBC(`hikari.data-source-properties.sslMode`)로 같은 조치를 해 3환경 배포까지 끝났다. **medcare는 원래부터 REQUIRED였고 나머지가 medcare를 본보기로 따라간 순서다.**

**T10(내부 NLB TLS) — 미착수, 인프라팀 협업.**

내부 호출이 전부 평문 HTTP다. 실측 근거는 아래 설정값이다.

| 구간 | 값 |
|---|---|
| Platform → medcare (dev) | `http://skmg-airbot-nlb-dev-…elb.amazonaws.com:8081` |
| Platform → medcare (stg) | `http://skmg-benjamin-stg-was-nlb-…elb.amazonaws.com:8081` |
| Platform → medcare (prd) | `http://skmg-benjamin-prd-was-nlb-…elb.amazonaws.com:8081` |
| medcare → PHR 스크래퍼 | `PHR_API_URL` — 세 환경 모두 같은 NLB의 `:8030`, 평문 HTTP |

이 구간에는 **내부 API 키와 파기 대상 sub, PHR 요청·응답이 흐른다.** NLB에 TLS 종단을 붙이는 것은 인프라팀 작업이고, 붙인 뒤 양쪽 저장소의 URL을 `https://`로 바꾸는 것이 우리 몫이다.

## 5. 내부 API와 설정

### 5-1. 내부 API (`/medcare/v1/internal/**`)

인증은 `X-Internal-Api-Key` 헤더(상수시간 비교, **미설정이면 전체 차단 = fail-closed**). 행위자를 남기려면 `X-Acting-Admin`을 함께 보낸다 — 없으면 접속기록에 `UNIDENTIFIED`로 찍힌다. 감사 기록은 필터가 자동으로 남기므로 호출 전 별도 기록은 필요 없다.

| 엔드포인트 | 호출자 | 용도 |
|---|---|---|
| `POST /log/list` | `backend-api-main`(관제) | 사용량 로그 조회. **전화번호 요청 계약 유지**, 서버가 sub로 해석 |
| `POST /users/purge?authSub=&apply=` | `backend-api-main`(탈퇴) | 사용자 단위 전체 파기 |
| `POST /retention/purge?apply=` | 운영자 수동 | 보유기간 경과 파기 |
| `POST /identity/backfill` | 스케줄러 + 수동 | 신원 레지스트리 백필(후속 티켓) |
| `GET /conversations/drift` | 스케줄러 + 수동 | 대화 적재 대사 |
| `POST /conversations/reconcile` | 스케줄러 + 수동 | 누락분만 재변환 |
| `POST /conversations/convertAll` | 수동 | 전체 재변환 |
| `POST /conversations/purge-stale?apply=&authSub=` | 수동 | 잔존 대화 정리 — **유지보수 배치 중 유일하게 되돌릴 수 없어 스케줄러에 걸지 않았다** |

**이미 제거된 것**: `POST /phr/encrypt-legacy`, `POST /chat-report/encrypt-legacy`. 3환경 소진을 마친 뒤 `c62a004`에서 지웠다(서비스 2·테스트 2·리포지토리 메서드 6·`ColumnCryptoPort.isActive()`까지 연쇄로 -417줄).

> **제거 기준이 "다 끝냈다"가 아니라 "다시 생길 수 없다"였다.** 평문 컬럼 모드를 로컬·테스트 프로필로 제한한 `e7c2f89`가 평문 재출현 경로를 막은 **뒤에야** 안전해졌다. 그 가드가 없으면 설정 실수 한 번으로 평문 행이 다시 생기고, 그때 소진 도구는 이미 없다.

> **나머지 7개를 남긴 이유.** `convertAll`·`drift`·`reconcile`·`purge-stale`은 저장소 문서 참조가 0건이었다. 평시 호출 0 + 문서 0이면 "마이그레이션 잔재"로 보이지만, 실제로는 **대화 내재화(INTERNAL) 라우팅의 유일한 복구 경로**다 — 적재가 어긋나면 예외가 아니라 **빈 목록**이 나가는 조용한 실패라서 자동으로는 드러나지 않는다. 그래서 지우는 대신 `docs/operations.md`를 새로 만들어 절차를 적었다. **문서 참조 0건은 삭제 근거가 아니라 문서화 부채의 신호다.**

### 5-2. 환경별 고정값

| 항목 | dev | stg | prd |
|---|---|---|---|
| AWS 계정 | 010928196421 | 087432099373 | 779846811758 |
| KMS 키 ID | `0b9a3183-…` | `002b9b62-…` | `748739aa-…` |
| 내부 API 키 | SSM `/skix-medcare/dev/INTERNAL_API_KEY` | SSM `/skix-medcare/stg/…` | SSM `/skix-medcare/prd/…` |
| 대화 라우팅 3종 | `INTERNAL` | `INTERNAL` | `INTERNAL` |

KMS 키는 전부 **대칭 · 연 1회 자동 로테이션 · ECS task role에 `kms:GenerateDataKey`+`kms:Decrypt`를 키 ARN 한정으로** 부여했다. envelope 방식이라 로테이션해도 기존 암호문 재암호화가 필요 없다.

**키 정책 작업 시 함정 두 가지.**

1. `put-key-policy`는 **병합이 아니라 전체 교체**다. 반드시 `get-key-policy` → append → 기존 `Allow`가 남았는지 확인 → `put` 순으로 한다. 이 순서를 어기면 기존 권한이 통째로 날아가고 앱이 기동하지 못한다.
2. `simulate-principal-policy`는 **IAM만 평가하고 키 정책은 반영하지 않는다.** `DenyKeyDeletion`이 실제로 먹는지는 dev에서 `schedule-key-deletion`을 직접 호출해 거부되는지 보는 방법밖에 없다(암호화 데이터가 없을 때만).

## 6. 되돌리면 안 되는 설계 결정

"더 단순해 보이게 바꾸면 사고가 나는" 것만 남겼다. 나머지 세부 결정은 코드 주석과 테스트가 지킨다.

| # | 결정 | 바꾸면 생기는 일 |
|---|---|---|
| 1 | **암호화 AAD/EncryptionContext는 `phrId`(데이터 행에 값으로 저장된 FK)다.** 소유자 키를 쓰지 않는다 | AAD를 조인이나 실시간 조회로 바꾸면 **과거 데이터 전부가 복호화 불가**가 된다. PHR 인증행 삭제가 무해한 근거도 이것 하나다 — AAD가 값으로 박혀 있으니 인증행이 사라져도 데이터 행은 열린다 |
| 2 | **`column.crypto.mode`는 `kms`와 `off` 외에는 기동 실패.** `off`는 localhost·test 프로필에서만 허용 | 원래는 `kms` 정확일치가 아니면 무조건 평문 어댑터였다. **`COLUMN_CRYPTO_MODE=KMS`(대문자) 하나가 기동에 성공하면서 전 행을 평문 저장한다** — 키 미설정을 막으려 세운 fail-closed를 설정값 한 글자가 우회했다. 기존 fail-closed는 `kms` 분기 **안**에만 있어 정작 평문으로 떨어지는 경로가 무방비였다 |
| 3 | **`spring.config.import`의 `optional:` 을 떼어 뒀다**(`.env` non-optional) | `optional:`이 있으면 배포에서 `SPRING_PROFILES_ACTIVE`가 누락돼도 기본 프로필로 조용히 뜬다. 뗀 덕분에 ⑴ 로컬은 `.env` 부재를 즉시 알리고 ⑵ **프로필 누락 배포가 기동 실패로 드러난다**(Dockerfile이 `gradlew/gradle/build.gradle/settings.gradle/src`만 COPY해 `.env`는 이미지에 구조적으로 없다). **함정: Spring 오류 메시지가 "or prefix it with 'optional:'"을 해결책으로 제안한다.** 그대로 따르면 방금 닫은 평문 기동 경로가 열린다 |
| 4 | **접속기록 필터는 인증 필터보다 앞에 두고, 인증 실패 요청의 `X-Acting-Admin`은 버린다** | 앞에 두는 것은 401/403을 남기기 위함이고(실패한 접근 시도가 봐야 할 신호다), 주장값을 버리는 것은 키 없는 외부 요청이 임의의 관리자 이름을 2년 보관 법적 증빙 로그에 심는 것을 막기 위함이다. **둘 중 하나만 하면 안 된다** |
| 5 | **접속기록 경로 판정은 인가와 동일한 PathPattern으로.** 원본 문자열 `startsWith`로 되돌리지 말 것 | 인가는 `pathMatchers`(디코딩 매칭)인데 감사만 원본 `startsWith`였을 때, `/medcare/v1/%69nternal/users/purge`가 **인증·라우팅을 통과해 파기까지 실행되면서 AUDIT 라인만 0줄**이었다(실서버 재현). **인가 경계와 감사 경계가 다른 매칭 규칙을 쓰면 그 틈이 곧 무기록 실행 경로가 된다** |
| 6 | **접속지는 `X-Forwarded-For`의 마지막 항목** | ALB는 기존 헤더를 유지한 채 뒤에 덧붙인다. 첫 항목은 **요청자가 써 보낸 값**이라 위조 가능하다 |
| 7 | **사용자 파기는 케이론(수탁자)을 먼저 지우고, 하나라도 실패하면 로컬을 건드리지 않는다** | 로컬이 어떤 대화를 케이론에서 지워야 하는지 알려주는 유일한 근거다. 순서를 뒤집으면 **무엇이 남았는지 알 방법이 사라진다.** 부분 성공을 '완료'로 기록하면 감사 기록이 실제와 어긋난다 |
| 8 | **파기 감사 기록은 트랜잭션 `.as(transactional)` 바깥에, 테이블별 실행 직후에** | 안에 두면 롤백돼도 '파기 완료'가 기록에 남는다. 건수는 결과 객체(`PersistResult`)로 밖에 꺼낸다. 테이블별로 즉시 기록하지 않으면 **앞 테이블을 지운 뒤 뒤 테이블이 실패했을 때 삭제 기록이 0줄**이 된다 |
| 9 | **`auto-purge=false`는 스케줄러만 끈다 — 안전장치가 아니다. PHR은 전용 플래그로 따로 잠근다** | 수동 `apply=true`는 이 설정과 무관하게 삭제한다. 새 파기 대상을 기존 체인에 그냥 넣으면 **기존 API의 영향 범위가 조용히 확대**된다. 비활성 여부는 `apply`와 **독립으로 계산**(`!enabled`)해야 한다 — `apply && !enabled`로 쓰면 모의 실행에서 "꺼져 있다"는 표시가 사라진다. 표시는 **응답과 배치 요약 로그 양쪽에**(스케줄러는 컨트롤러를 안 거친다) |
| 10 | **로그의 '값 없음'은 이유별로 구별한다.** 빈 자리·null을 **결함 신호로 예약** | 정상적인 미기록이 전부 마커(`[ABSENT]` 값 자체 없음 / `[EMPTY]` 필드는 왔으나 빈 값 / `[REDACTED:사유]` 정책상 미기록)를 거치면, **그냥 비어 있는 자리는 자동으로 버그가 된다** — 별도 모니터링 없이 결함이 스스로 드러난다. 사유 코드는 `PHI`·`PII`·`CREDENTIAL`·`EXTERNAL_BODY`이고 `PHI`는 medcare 전용이다. 구현은 `LogMasking` 한 곳에 모은다. **형태가 갈리면 규약이 아니라 각자의 습관이 된다** |
| 11 | **접속기록은 위 로그 규약의 문서화된 예외다**(값 없음은 전부 `-`) | 2년 보관 + CloudWatch 구독 필터 + 월 1회 점검에 쓰이는 기록이라, 센티널을 바꾸면 과거·신규 표기가 갈리고 `subject != '-'` 같은 점검 조건이 조용히 깨진다 |
| 12 | **백필은 전화번호가 같다는 사실만으로 과거 행을 계정에 붙이지 않는다** | 세 겹 방어(§4-3) 중 하나라도 빼면 **이전 소유자의 건강정보가 새 계정에 붙는다.** "값이 하나라 모호하지 않다"는 안전의 근거가 아니다 — **관측이 하나인 것과 사실이 하나인 것은 다르다** |
| 13 | **`OwnerlessRowCountRepository.countRowsMissingAuthSub`를 지우지 않는다** | 백필 도구를 제거하면서 함께 지우기 쉬운 자리인데, 이건 사용자 파기의 **'미배정 잔여 경고'** 안전장치다. `auth_sub`만 참조해 전화번호 컬럼 DROP과 무관하다 |
| 14 | **대화 목록을 지우면서 오프셋 페이지네이션 하지 않는다**(열거를 다 끝낸 뒤 삭제) | 뒤 페이지가 앞으로 당겨져 건너뛴다. 250건이면 100~199번이 조회조차 되지 않았다 |
| 15 | **`retention` 보유기간에 `@Positive`를 건다** | 0이나 음수가 들어오면 기준일이 미래가 되어 **전량 삭제**된다. 기동 실패로 막는 편이 낫다 |
| 16 | **파기 기준은 날짜 경계(자정)** | 같은 날 두 번 돌려도 대상이 같아야 파기 기록을 사후에 재현할 수 있다 |
| 17 | **`customer_if_log_text`는 소유자 단위 DELETE가 아니라 테이블 파기로 처리한다** | 코드에 소유자 DELETE를 넣으면 테이블 DROP 직후부터 **모든 사용자 파기가 1146으로 실패**한다 |

## 7. 타 팀에 요청한 내용

이 티켓들은 코드만으로 끝나지 않는다. 아래가 각 상대에게 전달한 요청의 핵심이고, 인수자는 이것을 이어받아 확정을 받는 역할이다.

### 7-1. 기획·법무 (가장 큰 병목)

1. **보유기간 수치 확정** — §4-4 표의 제안값. 특히 사용량 로그 365일이 맞는지(한도 산정만 보면 30일 창으로 충분하다. 분쟁·통계 목적이 따로 있는지), 신고 3년의 근거는 무엇인지.
2. **수탁사(케이론) 위탁계약서**, 서버 소재지 — **국외이전 여부**, 재위탁(LLM 제공자) 확인.
3. **PHR 스크래퍼 측의 데이터 보관 여부·기간.**
4. **민감정보(건강정보) 별도 동의 문구**가 요건을 충족하는지 — PHR 연동 동의 플로우.
5. **개인정보처리방침에 위탁·보유기간 반영.**
6. 사용자 파기 시 **신고 테이블 보존**이 정책상 맞는지(개인정보보호법 제21조 예외 적용 판단).

확정되면 저장소의 `docs/data-map.md` §4의 제안값을 확정값으로 바꾸고 `RETENTION_*` 환경변수를 맞춘다.

### 7-2. 관제 팀

1. **`X-Acting-Admin`을 모든 내부 API 호출에 보내는지** 엔드포인트별로 확인. 값이 관제 로그인 계정 식별자인지. 안 보내는 곳이 있으면 언제까지 보낼 수 있는지. 전부 확인되면 헤더 없는 호출을 400으로 거부하도록 조인다.
2. **신고 조회 화면을 만들 때 복호화 경로가 함께 필요하다.** DB를 직접 조회하면 암호문만 보인다. 이 사실을 **미리** 알려야 한다 — 화면을 다 만든 뒤에 알면 재작업이다.

### 7-3. 인프라팀

1. **CloudWatch 구독 필터 → Kinesis Data Firehose → S3**. 로그 그룹 `/ecs/skix-medcare-{env}`에서 `AUDIT` 로거 라인만 분리. 필터 패턴은 `"AUDIT"`(로그 패턴에 `%logger{36}`가 있어 라인에 로거 이름이 포함된다) 또는 `?"actorType=ADMIN" ?"actorType=SYSTEM"`.
2. **S3 버킷에 Object Lock(Compliance 모드, 2년)** — 위·변조 방지 요건. **버킷 생성 시에만 켤 수 있으므로 새 버킷이 필요하다.** 수명주기 2년 만료, SSE-KMS 암호화, 퍼블릭 액세스 차단.
3. **RDS 감사 로깅**(MariaDB Audit Plugin 또는 Aurora Advanced Auditing) → CloudWatch → 위 S3. 애플리케이션을 거치지 않는 DB 직접 접근은 앱이 기록할 수 없다. bastion·세션 매니저 로깅도 함께.
4. **내부 NLB TLS 종단**(T10) — §4-8의 4개 구간.

## 8. 배포 방법

> **⚠️ 이 티켓들은 한 브랜치라 배포는 한 번인데, 앞뒤로 순서가 강제되는 작업이 흩어져 있다.** 티켓 순서(T1 → T2 → …)로 따라가면 안 된다 — T1의 "배포"와 T5의 "배포"는 같은 한 번이고, T5의 SQL 백필은 그 배포보다 **먼저**여야 한다. 아래가 "언제"의 순서다.
>
> **이미 세 환경에서 한 번 완주한 절차다.** 인수자가 이 순서를 다시 쓸 일은 신규 환경 구축이나 유사 작업 때다. 개별 SQL은 부록 B에 전문이 있다.

환경마다 dev → stg → prd 순으로 전체를 반복한다.

### 8-1. 순서

**ⓐ 코드 반영**

| # | 작업 | 비고 |
|---|---|---|
| a-1 | 브랜치 push + MR(대상 `dev`) → 승격 `dev` → `stg` → `main`(`--no-ff`) | 머지 커밋 메시지 관례 `Merge branch 'X' into 'Y'` |
| a-2 | `dev`에서 빌드 → tar.bz2 → CloudShell → ECR | **CI가 없어 전부 수동.** 환경마다 AWS 계정이 다르다 |

> **`deploy/cloudshell-push.sh`는 브랜치를 보지 않는다.** 로컬 이미지 tar를 환경별 ECR로 밀 뿐이라 **배포와 브랜치 승격이 완전히 별개**다. 한 번 이것 때문에 배포를 먼저 하고 승격을 잊어 `stg`·`main`이 7커밋 뒤처진 채 운영계가 돌았다. 그 상태에서 `main` 기준으로 핫픽스를 따면 없는 코드로 시작해 **배포 순간 조용히 롤백된다.** **승격 먼저, 배포 나중.**

**⓪ 배포 전 — 하지 않으면 앱이 뜨지 않는다**

| # | 작업 | 왜 먼저인가 |
|---|---|---|
| 0-1 | **KMS 키 생성**(대칭, 환경당 1개) + ECS task role에 `kms:GenerateDataKey`,`kms:Decrypt` | `column.crypto.mode=kms`가 ecs 기본값이고 키가 없으면 **기동 실패(fail-closed)** |
| 0-2 | `deploy/task-definition-{env}.json`의 `MEDCARE_KMS_KEY_ARN` 자리표시자를 실제 ARN으로 교체 후 커밋 | 위와 동일 |

**① 배포 전 — DDL** (전부 가산 변경이라 구버전 코드와 공존한다)

| # | 작업 | 왜 먼저인가 | SQL |
|---|---|---|---|
| 1-1 | 소유자 키 컬럼(`*_auth_sub`) + 인덱스 + 기존 `login_id` NULL 허용 | 새 코드는 `auth_sub`로만 조회한다. 컬럼이 없으면 전부 실패 | 부록 B-2 |
| 1-2 | `customer_if_log`에 `idx_if_log_create_date` | 없으면 파기 배치가 매일 풀스캔 | 부록 B-5 |
| 1-3 | `customer_chat_report.report_text`를 `text`로 확장 | 신고 사유도 암호화 대상이라 `varchar(200)`에 봉투(base64)가 들어가지 않아 **저장이 실패**한다 | 부록 B-4 |

**② 배포 전 — 백필 (이 단계가 순서의 핵심)**

| # | 작업 | 왜 먼저인가 |
|---|---|---|
| 2-1 | **계정보다 오래된 행 사전 확인 쿼리** 실행(부록 B-6) | 나온 번호는 UPDATE 대상에서 빼고 수동 판단한다 |
| 2-2 | **SQL 백필**: `customer_if_log`의 (전화번호, sub) 쌍으로 5개 테이블 `auth_sub` 채우기(부록 B-2) | 배포된 코드는 `auth_sub`가 빈 행을 **보지 못한다.** 배포 전에 채워야 사용자에게 데이터가 사라져 보이지 않는다 |
| 2-3 | 테이블별 잔여 건수 확인(부록 B-7) | 잔여가 클수록 ③ 직후의 공백이 커진다. 크면 트래픽 적은 시간대를 고른다 |

**`HAVING COUNT(DISTINCT ...) = 1` 가드를 빼면 안 된다.**

**③ 배포**

- 앱 확인: 채팅 한도 표시 / 폴더 목록·담기 / 대화 삭제 / `GET /phr`·`GET /phr/data`·`DELETE /phr/delete` / 관제 사용량 로그 조회.
- **DB TLS가 여기서 드러난다** — `sslMode=REQUIRED`라 협상이 안 되면 기동 시 연결이 실패한다. 문제가 생기면 재빌드 없이 `DB_SSL_MODE=PREFERRED`로 낮춘다.

**④ 배포 직후 — 즉시**

| # | 작업 | 비고 |
|---|---|---|
| 4-1 | 잔여 소유자 백필 API 반복 | **미룰수록 그 사용자에게 데이터가 안 보인다.** ※ 이 도구는 T5 완결 후 코드에서 제거됐다(`520d660`). 신규 환경이라 백필이 필요하면 그 커밋을 되살려야 한다 |
| 4-2 | 레거시 평문 PHR 일괄 암호화 → 잔여 0 | ※ `c62a004`에서 제거됨. 위와 같다 |
| 4-3 | 레거시 평문 신고 일괄 암호화 → 잔여 0 | ①-3 DDL이 선행돼야 한다. ※ 위와 같다 |
| 4-4 | **`customer_if_log_text` 파기(RENAME → DROP)** | **탈퇴 파기를 가동하기 전에** 끝낸다(§4-2). **백업을 뜨지 않는다** |

4-1~4-3은 `apply` 없이 먼저 호출해 대상 건수를 확인한다. 전부 행 단위 멱등이라 반복 호출이 안전하다.

**⑤ 배포 후 — 시점 자유** → §9-1로 이관(아직 안 끝난 항목들이다).

**⑥ 마지막 — 되돌릴 수 없는 정리**

| # | 작업 | 전제 |
|---|---|---|
| 6-1 | 전화번호 컬럼 DROP(5개 테이블) + 구 인덱스 정리(부록 B-3) | **세 환경 모두 ④-1 잔여 0 확인 후.** 잔여는 번호중복·미해결·실패를 사람이 처리해야 0이 된다 — **저절로 도달하지 않는다** |
| 6-2 | 백필 코드 제거 | 6-1 이후 |

### 8-2. 순서를 어기면 생기는 일

| 어김 | 결과 |
|---|---|
| KMS 키 없이 배포 | **앱이 뜨지 않는다**(의도된 fail-closed) |
| `report_text` 확장 없이 배포 | 신규 **신고 저장이 실패**한다 |
| 백필 없이 배포 | `auth_sub`가 빈 행이 **사용자에게 보이지 않는다**(데이터는 그대로 있다) |
| `customer_if_log_text` 파기 전에 탈퇴 연계 가동 | 탈퇴한 사용자의 질문·답변 원문이 **남은 채 "파기 완료"가 기록**된다 |
| 잔여 0 전에 컬럼 DROP | 백필 도구가 못 돌아 **영영 채울 수 없다** |

### 8-3. 배포 후 검증 명령

```bash
BASE=https://<medcare 내부 호스트>     # 환경별 NLB. 로컬 맥에서는 닿지 않는다(VDI 필요)
KEY=<X-Internal-Api-Key>              # SSM /skix-medcare/{env}/INTERNAL_API_KEY
ADMIN=<확인용 식별자>

# 1) 보유기간 파기 — 모의 실행. 대상 건수와 "비활성 테이블" 표시를 본다
curl -s -X POST -H "X-Internal-Api-Key: $KEY" -H "X-Acting-Admin: $ADMIN" \
     "$BASE/medcare/v1/internal/retention/purge?apply=false"
#   기대: "보유기간 경과 N행 — apply=true 로 실행하세요. (customer_if_phr_data 는 비활성 — RETENTION_PHR_PURGE_ENABLED=false)"

# 2) 사용자 파기 — 테스트 계정으로 모의 실행
curl -s -X POST -H "X-Internal-Api-Key: $KEY" -H "X-Acting-Admin: $ADMIN" \
     "$BASE/medcare/v1/internal/users/purge?authSub=<테스트 sub>&apply=false"
#   기대: "파기 대상 N행(신고 M건은 보존) — apply=true 로 실행하세요."

# 3) 내부 API 키 없이 호출 — 401/403 이어야 한다. 200 이면 즉시 중단
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
     "$BASE/medcare/v1/internal/retention/purge"

# 4) 접속기록이 남는지 — 3)의 실패 호출도 AUDIT 한 줄로 남아야 한다.
#    CloudWatch Logs Insights (로그 그룹 /ecs/skix-medcare-{env}):
#      fields @timestamp, @message | filter @message like /AUDIT/ | sort @timestamp desc | limit 50
#    기대: 3) 에 대해 actor=UNAUTHENTICATED, result=401 또는 403
```

DB 쪽 검증(부록 B-8)은 신규 적재가 `ENC1:`로 저장되는지 확인하는 것이다.

### 8-4. 롤백

| 시점 | 가능 여부 |
|---|---|
| ①~② 후 | 그대로 두면 된다(가산 변경) |
| ③(배포) 후 | **깨끗한 롤백이 아니다.** 신규 행은 `auth_sub`만 있고 `login_id`가 NULL이라 구버전의 전화번호 조회에 안 잡히고, 신규 PHR·신고는 암호문이라 구버전이 파싱하지 못한다. 이미지를 되돌리는 것 자체는 되지만 그 사이 적재분은 사용자 재적재 또는 삭제가 필요하다(dev에서만 허용). **운영은 forward-fix로 대응한다** |
| ④ 후 | 위와 같다. 마이그레이션이 전 행을 암호문으로 바꾼 뒤라 구버전은 기존 데이터도 못 읽는다 |
| ⑥ 후 | **불가** |

롤백 가능성이 실제로 필요하면 방법은 이미지 되돌리기가 아니라 일정 기간 dual-write다(전화번호 컬럼 동시 기록 + 평문 병행 저장). **이 작업은 그 비용을 지지 않기로 하고 설계했다.**

DB 레벨 롤백은 **`customer_if_log_text` DROP과 전화번호 컬럼 DROP만 불가**이고, 나머지 DDL은 가산이라 되돌릴 일이 없다. KMS 키 삭제는 어떤 경우에도 금지다.

### 9-4. 접속기록 월 1회 점검 항목

절차를 만들 때 쓸 항목이다. 점검 결과를 문서로 남긴다(누가 언제 점검했고 무엇을 확인했는지).

- `actor=UNIDENTIFIED` 건수 — **0이어야 한다.** 0이 아니면 관제가 헤더를 안 보내는 경로가 있다는 뜻

- 파기(`USER_DATA_PURGE`, `RETENTION_PURGE`, `PHR_PURGE`) 실행 이력과 요청 대장 대조
- 비정상 시간대·비정상 IP 접근
- `result=4xx/5xx` 급증

| 상황 | 확인 방법 |
|---|---|
| **앱이 기동하지 않는다 (ECS 태스크가 계속 죽는다)** | 우선 세 가지를 본다. ⑴ `MEDCARE_KMS_KEY_ARN`이 비었거나 잘못됐다(fail-closed, **의도된 동작**) ⑵ `COLUMN_CRYPTO_MODE`가 `kms`/`off` 외의 값이다(대문자 `KMS` 포함) ⑶ DB TLS 협상 실패 — 임시 완화는 `DB_SSL_MODE=PREFERRED`. ⑷ `SPRING_PROFILES_ACTIVE` 누락도 기동 실패로 나타난다(의도된 동작) |
| "탈퇴했는데 데이터가 남아 있다" | `backend-api-main` 로그에서 `medcare 사용자 파기 실패 - sub: …`를 찾는다. **그 sub로 `POST /internal/users/purge?authSub=<sub>&apply=true`를 다시 부르면 남은 것부터 이어서 지워진다**(행 단위 멱등). 탈퇴 자체는 실패하지 않는 정책이라 이 로그가 유일한 단서다 |
| 사용자 파기가 500으로 실패 | 케이론 삭제가 하나라도 실패한 것이다. **로컬은 건드려지지 않았다.** 케이론 쪽이 복구되면 재호출한다 |
| 파기 응답에 "소유자 미배정 N행 존재" | 시스템 전체의 `auth_sub` 없는 행 수다. **이 사용자의 행이 그 안에 있다는 뜻은 아니다.** 백필이 미완인 환경에서만 나온다 |
| 보유기간 파기가 아무것도 안 지운다 | 정상이다. `RETENTION_AUTO_PURGE=false`가 기본이고 보유기간 확정 전까지 그대로 둔다. 수동 확인은 §8-3의 1번 |

| 관제 신고 조회가 암호문만 보인다 | 정상이다(§4-6). 복호화 경로를 만들어야 한다 |

| 접속기록에 `actor=UNAUTHENTICATED`가 보인다 | 인증에 실패한 요청이다. **주장한 관리자명은 버려졌다**(의도된 동작). 빈도가 높으면 조사 |
| 대화 목록·검색이 **빈 목록**으로 나온다 | 예외가 아니라 조용한 실패다. 라우팅이 `INTERNAL`인데 `kmeta_*` 적재가 어긋난 것 — `GET /internal/conversations/drift`로 `checkFailedUsers`·`missingInKmeta`·`missingSearchIndex`를 본다. 어긋나면 `reconcile`(누락분만) → `convertAll`(전체) 순 |
| PHR이 안 보인다 | `auth_sub`가 빈 행은 조회되지 않는다(데이터는 남아 있다). 신규 환경 구축 중이면 백필 미완을 의심한다 |
| 신규 PHR·신고가 암호화됐는지 | 부록 B-8 |
| 로그 키워드 | 접속기록 `AUDIT`, 파기 `USER_DATA_PURGE` / `RETENTION_PURGE` / `PHR_PURGE` |

### B-1. `customer_if_log_text` 파기 (T2, 되돌릴 수 없음)

### B-2. 소유자 키 컬럼 추가 + SQL 백필 (T5)

**DDL — 배포 전. 전부 가산 변경이라 구버전 코드와 공존한다.**

```sql
ALTER TABLE customer_if_phr
  ADD COLUMN CUSTOMER_IF_PHR_AUTH_SUB varchar(50) DEFAULT NULL AFTER CUSTOMER_IF_PHR_ID,
  ADD KEY idx_phr_auth_sub (CUSTOMER_IF_PHR_AUTH_SUB, CUSTOMER_IF_PHR_ID),
  MODIFY COLUMN CUSTOMER_IF_PHR_LOGIN_ID varchar(50) DEFAULT NULL;

ALTER TABLE customer_if_phr_data
  ADD COLUMN CUSTOMER_IF_PHR_AUTH_SUB varchar(50) DEFAULT NULL AFTER CUSTOMER_IF_PHR_ID,
  ADD KEY idx_phr_data_auth_sub (CUSTOMER_IF_PHR_AUTH_SUB, CUSTOMER_IF_PHR_DATA_ID),
  MODIFY COLUMN CUSTOMER_IF_PHR_LOGIN_ID varchar(50) DEFAULT NULL;

ALTER TABLE customer_folders
  ADD COLUMN folder_auth_sub varchar(50) DEFAULT NULL AFTER folder_id,
  ADD KEY idx_folders_auth_sub_sort (folder_auth_sub, folder_sort_order, create_date),
  MODIFY COLUMN folder_login_id varchar(50) DEFAULT NULL,
  MODIFY COLUMN create_login_id varchar(50) DEFAULT NULL;

ALTER TABLE customer_folder_chat
  ADD COLUMN chat_auth_sub varchar(50) DEFAULT NULL AFTER chat_id,
  ADD UNIQUE KEY uk_folder_chat_sub_str (chat_auth_sub, chat_str_id),
  ADD KEY idx_folder_chat_sub_date (chat_auth_sub, create_date),
  MODIFY COLUMN create_login_id varchar(50) DEFAULT NULL;

-- customer_if_log 는 customer_if_auth_sub 가 이미 있다. 조회 키가 되므로 인덱스만 보강한다.
ALTER TABLE customer_if_log
  ADD KEY idx_if_log_auth_sub_date (customer_if_auth_sub, customer_if_create_date),
  MODIFY COLUMN customer_if_login_id varchar(50) DEFAULT NULL;
```

**백필 — 배포 전. 반드시 한 세션에서 이어서 실행한다.** `CREATE TEMPORARY TABLE`은 세션 스코프라 창을 바꾸거나 연결이 끊기면 `tmp_owner_map`이 사라져 이후 UPDATE가 "table doesn't exist"로 실패한다.

```sql
-- 공통 매핑을 임시 테이블로 한 번만 만든다.
-- HAVING COUNT(DISTINCT ...) = 1 을 빼면 안 된다 — 한 번호에 sub 가 둘이면(번호 재사용)
-- 어느 쪽이 현재 소유자인지 로그만으로는 알 수 없고, 잘못 고르면 남의 건강정보가 붙는다.
CREATE TEMPORARY TABLE tmp_owner_map AS
SELECT customer_if_login_id AS login_id,
       MIN(customer_if_auth_sub) AS auth_sub
FROM customer_if_log
WHERE customer_if_auth_sub IS NOT NULL AND customer_if_login_id IS NOT NULL
GROUP BY customer_if_login_id
HAVING COUNT(DISTINCT customer_if_auth_sub) = 1;

UPDATE customer_if_phr t JOIN tmp_owner_map m ON t.CUSTOMER_IF_PHR_LOGIN_ID = m.login_id
   SET t.CUSTOMER_IF_PHR_AUTH_SUB = m.auth_sub WHERE t.CUSTOMER_IF_PHR_AUTH_SUB IS NULL;

UPDATE customer_if_phr_data t JOIN tmp_owner_map m ON t.CUSTOMER_IF_PHR_LOGIN_ID = m.login_id
   SET t.CUSTOMER_IF_PHR_AUTH_SUB = m.auth_sub WHERE t.CUSTOMER_IF_PHR_AUTH_SUB IS NULL;

UPDATE customer_folders t JOIN tmp_owner_map m ON t.folder_login_id = m.login_id
   SET t.folder_auth_sub = m.auth_sub WHERE t.folder_auth_sub IS NULL;

UPDATE customer_folder_chat t JOIN tmp_owner_map m ON t.chat_login_id = m.login_id
   SET t.chat_auth_sub = m.auth_sub WHERE t.chat_auth_sub IS NULL;

UPDATE customer_if_log t JOIN tmp_owner_map m ON t.customer_if_login_id = m.login_id
   SET t.customer_if_auth_sub = m.auth_sub WHERE t.customer_if_auth_sub IS NULL;
```

### B-5. 파기 배치용 인덱스 (T6, 배포 전)

```sql
ALTER TABLE customer_if_log ADD KEY idx_if_log_create_date (customer_if_create_date);
```

파기는 소유자와 무관하게 생성일만 훑는다. 선두 컬럼이 생성일인 인덱스가 없으면 매일 풀스캔이다. (`customer_chat_report`는 `idx_chat_report_create_date`가 이미 있다. `customer_if_phr_data`는 PHR 보관 최소화 때 `idx_phr_data_create_date`를 추가했다.)

### B-6. 백필 전 사전 확인 — 계정보다 오래된 행 (T5)

```sql
-- 그 번호로 남은 가장 이른 로그보다 더 오래된 미배정 행이 있는 번호.
-- 나오면 그 번호는 UPDATE 대상에서 빼고 수동으로 판단한다.
SELECT m.login_id, m.first_seen, x.tbl, x.oldest
FROM (
  SELECT customer_if_login_id AS login_id, MIN(customer_if_create_date) AS first_seen
  FROM customer_if_log WHERE customer_if_login_id IS NOT NULL
  GROUP BY customer_if_login_id
) m
JOIN (
  SELECT CUSTOMER_IF_PHR_LOGIN_ID AS login_id, 'phr' AS tbl,
         MIN(CUSTOMER_IF_PHR_CREATE_DATE) AS oldest
  FROM customer_if_phr WHERE CUSTOMER_IF_PHR_AUTH_SUB IS NULL
  GROUP BY CUSTOMER_IF_PHR_LOGIN_ID
  UNION ALL
  SELECT folder_login_id, 'folders', MIN(create_date)
  FROM customer_folders WHERE folder_auth_sub IS NULL GROUP BY folder_login_id
  UNION ALL
  SELECT chat_login_id, 'folder_chat', MIN(create_date)
  FROM customer_folder_chat WHERE chat_auth_sub IS NULL GROUP BY chat_login_id
) x ON x.login_id = m.login_id
WHERE x.oldest < m.first_seen;
```

빈 결과면 그대로 진행한다.

**번호중복 대상 확인**(한 번호에 sub가 둘 이상):

```sql
SELECT customer_if_login_id,
       GROUP_CONCAT(DISTINCT customer_if_auth_sub) AS subs,
       MIN(customer_if_create_date) AS first_seen,
       MAX(customer_if_create_date) AS last_seen
FROM customer_if_log
WHERE customer_if_auth_sub IS NOT NULL AND customer_if_login_id IS NOT NULL
GROUP BY customer_if_login_id
HAVING COUNT(DISTINCT customer_if_auth_sub) > 1;
```

사용 시각으로 소유 구간을 나눈 뒤 각 행의 `create_date`를 보고 sub를 직접 지정한다. **판단이 서지 않으면 채우지 말고 그 행들을 파기하는 편이 안전하다** — 누구 것인지 모르는 개인정보를 남기는 것보다 낫다. 어느 쪽이든 결정과 근거를 기록으로 남긴다.

### B-7. 백필 잔여 확인 (T5)

```sql
SELECT 'phr' t, COUNT(*) n FROM customer_if_phr WHERE CUSTOMER_IF_PHR_AUTH_SUB IS NULL
UNION ALL SELECT 'phr_data',    COUNT(*) FROM customer_if_phr_data  WHERE CUSTOMER_IF_PHR_AUTH_SUB IS NULL
UNION ALL SELECT 'folders',     COUNT(*) FROM customer_folders      WHERE folder_auth_sub IS NULL
UNION ALL SELECT 'folder_chat', COUNT(*) FROM customer_folder_chat  WHERE chat_auth_sub IS NULL
UNION ALL SELECT 'if_log',      COUNT(*) FROM customer_if_log       WHERE customer_if_auth_sub IS NULL;
```

**전화번호 컬럼을 DROP한 뒤에는 이 쿼리가 돌지 않는다**(`login_id` 조인이 없어 `auth_sub IS NULL` 부분만 유효하다). 현재 코드의 `OwnerlessRowCountRepository.countRowsMissingAuthSub`가 `auth_sub`만 보고 같은 수치를 낸다.

## 부록 C. 내부 API 호출 절차

로컬 맥에서는 내부 NLB에 닿지 않는다. **VDI 또는 같은 VPC 안에서** 호출한다.

```bash
BASE=http://<환경별 NLB 호스트>:8081     # backend-api-main 의 myHealthCare.api.url 과 같은 값
KEY=$(aws ssm get-parameter --name "/skix-medcare/dev/INTERNAL_API_KEY" \
      --with-decryption --query Parameter.Value --output text)
ADMIN=<실행자 식별자>                     # 접속기록의 actor 가 된다. 생략하면 UNIDENTIFIED
```

### 보유기간 파기

```bash
# 1) 모의 실행 — 대상 건수만 본다. 여기 숫자가 예상보다 크면 기간 설정·정책을 다시 본다
curl -s -X POST -H "X-Internal-Api-Key: $KEY" -H "X-Acting-Admin: $ADMIN" \
     "$BASE/medcare/v1/internal/retention/purge?apply=false"

# 2) 건수가 납득되면 실행. 테이블당 최대 RETENTION_BATCH_LIMIT(기본 5000) 행이라
#    잔여가 남으면 반복 호출한다
curl -s -X POST -H "X-Internal-Api-Key: $KEY" -H "X-Acting-Admin: $ADMIN" \
     "$BASE/medcare/v1/internal/retention/purge?apply=true"
```

첫 실행은 누적분이 많을 수 있으므로 **수동으로, 상한 단위로 나눠** 소진한다. 로그에서 테이블별 삭제 건수와 기준일을 확인한다. 소진이 끝나면 태스크 정의에 `RETENTION_AUTO_PURGE=true`를 넣고 배포한다(이후 매일 04:30 KST 자동).

### 사용자 단위 전체 파기

```bash
# 1) 모의 실행
curl -s -X POST -H "X-Internal-Api-Key: $KEY" -H "X-Acting-Admin: $ADMIN" \
     "$BASE/medcare/v1/internal/users/purge?authSub=<sub>&apply=false"

# 2) 실제 파기
curl -s -X POST -H "X-Internal-Api-Key: $KEY" -H "X-Acting-Admin: $ADMIN" \
     "$BASE/medcare/v1/internal/users/purge?authSub=<sub>&apply=true"

# 3) 멱등 확인 — 재실행하면 0행/0건이 나와야 한다
```

로그에서 "사용자 파기 완료 - user: …, 케이론 대화 N건, 로컬 M행"을 확인하고, 케이론에서도 해당 사용자 대화가 사라졌는지 확인한다.

### 대화 적재 대사·복구

```bash
# 어긋남 확인 — checkFailedUsers / missingInKmeta / missingSearchIndex 가 전부 0 이어야 한다
curl -s -H "X-Internal-Api-Key: $KEY" "$BASE/medcare/v1/internal/conversations/drift"

# 누락분만 재변환
curl -s -X POST -H "X-Internal-Api-Key: $KEY" -H "X-Acting-Admin: $ADMIN" \
     "$BASE/medcare/v1/internal/conversations/reconcile"

# 전체 재변환 (reconcile 로 해소되지 않을 때)
curl -s -X POST -H "X-Internal-Api-Key: $KEY" -H "X-Acting-Admin: $ADMIN" \
     "$BASE/medcare/v1/internal/conversations/convertAll"
```

대화 라우팅은 **읽기 전용 스위치**다 — 변환 서비스가 라우팅과 무관하게 항상 `kmeta_*`에 적재하므로, 문제가 생기면 라우팅을 되돌려도 데이터 공백이 없다(즉시 복구 수단). 다만 적재가 안 된 환경에서 `INTERNAL`이면 **예외가 아니라 빈 목록**이 나간다.
