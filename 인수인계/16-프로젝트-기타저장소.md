## 0. 세 줄 요약

1. 이 문서는 단독 문서로 분리하기엔 작지만 운영 의존성이 큰 저장소를 묶는다. DDL은 배포의 전제이고, 맵·영상 계열은 메인 API가 성공해도 별도 프로세스에서 실패할 수 있다.
2. 맵 변환 SQS는 기능 브랜치에 머물고 히트맵은 대체 설계 단계다. 스트리밍과 시그널은 운영 코드를 갖지만 브랜치 승격·재부팅 복구·시크릿 관리가 미완성이다.
3. 키 서비스 저장소에는 운영 런타임 소스가 없어 코드 수정부터 시작할 수 없다. 실배포본과 소유권을 먼저 확보해야 한다.

## 1. db-schema

### 역할과 구조

`dev.sql`, `stg.sql`, `prod.sql`에 환경별 기준 DDL을 모아 둔다. 자동 migration 도구가 아니라 사람이 필요한 구문을 검토해 실행하는 방식이다. 최근에는 다음 영역이 추가·변경됐다.

- MQTT 발행·수신 로그와 오류 컬럼
- 좌표 기반 날씨·외부 API 호출량·`map_id`
- 원격 맵핑 세션
- 직접 구독 시도·감사 원장
- 현재 기기 계약 캐시 테이블

### 운영 원칙과 남은 일

1. 대상 DB의 현재 스키마를 먼저 덤프하고 DDL diff를 만든다.
2. 앱 코드보다 DDL을 먼저 적용하되, 생성 직후 소비가 시작되는 기능은 플래그를 끈다.
3. 컬럼 추가는 nullable·기본값·인덱스 비용을 확인하고 온라인 적용 가능성을 판단한다.
4. 세 SQL 파일의 동일 변경이 환경별로 빠지지 않았는지 비교한다.

가장 큰 부채는 저장소가 실제 적용 상태를 보증하지 않는다는 점이다. `device_current_contract`, 맵 변환 큐 테이블, 날씨 백필, 원격 맵핑 원장이 세 환경에 존재하는지는 **미확인**이다.

## 2. backend-map-converter

### 역할과 구성

Java 17·Spring Boot 3.2·Maven 기반 서비스다. 기기가 올린 맵을 S3에서 읽고 변환 작업을 수행해 결과를 돌려준다. 기존 HTTP 진입점은 `/ReqMapOptimization`, `/ReqAuthKey`이며 Maven은 WAR를 만든다. 실제 EC2 배포 경로와 프로세스 방식은 **미확인**이다.

```text
기기/플랫폼 → 변환 요청 → 작업 원장 → SQS worker → S3 원본·결과 → 완료 통보
```

### 최근 작업과 상태

- SQS 기반 비동기 변환, 작업 상태·재시도·DLQ 구조가 `refactor/mapconvert` 계열 브랜치에 구현됐다.
- 대표 커밋은 `2d4f02e`이며 기준 브랜치에 머지되지 않았다.
- 개발계에서 관련 DDL과 활성 플래그의 순서가 뒤집히면 시작 즉시 실패할 수 있다.
- 브랜치가 오래됐으므로 현재 `dev`에 단순 병합하기보다 충돌과 계약 변경을 검토해 다시 얹는 편이 안전하다.

### 우선 확인

1. 실제 변환 프로세스·WAR·JVM과 S3 bucket·prefix를 확인한다.
2. 작업 원장 DDL을 먼저 적용하고 queue·DLQ·visibility timeout을 만든다.
3. 다크 배포에서 소비를 끈 채 요청 생성까지만 확인한다.
4. 작은 맵, 대형 맵, 중복 요청, worker 재시작, poison message를 검증한다.

## 3. backend-hitmap

### 역할과 상태

Java 17·Spring Boot 3.5·Maven 기반의 공기질 히트맵 계산 서비스이며 `/hitmap` 경로를 제공한다. 현재 구조는 별도 서비스가 계산 요청을 받아 결과를 만드는 방식이다.

최근 6개월간 작성자 코드 커밋은 없고, 맵 변환 worker에 계산을 흡수할 수 있는지 조사·설계만 진행됐다. 현재 `main`은 2025-09-22 커밋이며 `stg`가 병합 이력 기준 2커밋 앞선다.

### 남은 일

- 실제 호출자와 호출량, 실행 프로세스, 입력·출력 저장소를 확인한다.
- 대체 worker가 같은 결과를 만드는지 고정 샘플로 비교한다.
- 호출자 전환, 관찰 기간, 롤백 기준을 잡은 뒤에만 기존 프로세스를 내린다.
- 코드 작성자가 아닌 운영 소유자와 장애 연락 경로는 **미확인**이다.

## 4. skix-streaming

### 역할과 구성

Kinesis Video Streams 기반 영상 생성·업로드·출동 연동을 담당하는 Java 서비스다. 현재 빌드 파일은 Java 25·Spring Boot 4 계열을 가리키며, 환경별 Gradle 프로필로 jar를 만들어 EC2에서 수동 실행한다.

주요 흐름은 영상 세션 요청, 기기 영상 처리, 보안 서비스 내부 호출, 앱 FCM 통보다. 최근에는 인증 주체 해석, 내부 API 전환, 로그 개인정보 제거, 업로드·출동 경로 안정화가 반영됐다.

### 위험과 운영 확인

| 우선순위 | 확인 항목 |
|---|---|
| P0 | `main`이 `stg`보다 6커밋 뒤다. 운영 반영 범위와 실행 jar를 대조한다. |
| P0 | 프로세스가 재부팅 뒤 자동 복구되는지 systemd·supervisor·기동 스크립트를 확인한다. |
| P1 | 플랫폼 내부 API 주소가 환경에 맞는지 확인한다. 잘못된 host는 FCM·사용자 조회를 끊는다. |
| P1 | KVS·S3·내부 API 권한과 시크릿이 파일이 아닌 주입 경로를 쓰는지 확인한다. |
| P2 | 업로드·출동 호출의 timeout·재시도·멱등성을 실영상으로 검증한다. |

빌드와 배포 명령은 저장소의 현재 Gradle profile 정의를 기준으로 다시 확인한다. 실행 서버·jar 경로·포트는 **미확인**이다.

## 5. skix-streaming-signal

### 역할과 구성

Node.js·Socket.IO 기반 시그널링 서버다. 영상 참여자 사이 offer·answer·ICE candidate를 전달하고 세션 연결 상태를 중계한다. EC2에서 Node 프로세스로 수동 실행되는 구조다.

최근에는 식별정보가 로그에 남지 않도록 정리하고 연결·해제 이벤트를 보완했다. `main`은 `stg`보다 3커밋 뒤다.

### 위험과 남은 일

- `.env`가 형상에 남아 있어 실제 값 사용 여부와 로테이션 상태를 확인해야 한다. 새 값은 저장소에 기록하지 않는다.
- 프로세스 관리자가 명확하지 않다. 재부팅·crash 뒤 자동 복구와 로그 rotation을 확인한다.
- ALB/NLB의 WebSocket timeout, sticky 동작, CORS origin을 환경별로 실측한다.
- 운영 연결 수·재접속률·메모리 증가를 관찰할 지표가 **미확인**이다.

## 6. skix-streaming-kms

### 역할과 현재 한계

보안영상 콘텐츠 키를 보관·조회하는 서비스로 알려져 있으나, 확인한 저장소에는 운영 런타임 구현이 없다. `main`·`master`와 설명·템플릿 수준 파일만으로는 빌드, 테스트, 배포, 장애 분석을 수행할 수 없다.

운영 흐름에서는 RSA 개인키가 Redis에 보관되고 복호화된 콘텐츠 키가 내부 응답으로 전달되는 것으로 파악된다. 내부 HTTP·네트워크 격리에만 의존하면 평문 키 노출 범위가 넓다.

### 인계 전제

1. 실제 런타임 소스와 배포 산출물, 담당 소유권을 확보한다.
2. 서버·포트·내부 LB·Redis DB·키 생성·회전·폐기 절차를 확인한다.
3. 로그와 API 응답에 개인키·평문 콘텐츠 키가 남는지 실측하고 즉시 마스킹한다.
4. 앱 임시 공개키로 콘텐츠 키를 재래핑하는 목표 구조와 호환 기간을 설계한다.
5. 소스 확보 전에는 이 저장소만 수정해 문제가 해결됐다고 판단하지 않는다.

실제 배포 버전, 런타임, 모니터링, 장애 대응자는 모두 **미확인**이다.

## 7. 공통 운영 체크리스트

### 첫 주

1. 각 저장소의 브랜치 HEAD와 실제 서버 산출물 checksum을 연결한다.
2. EC2 프로세스의 systemd·기동 스크립트·사용자·포트·로그 경로를 기록한다.
3. DB DDL → 큐·bucket·권한 → 다크 배포 → 소비 활성화 순서를 지킨다.
4. 스트리밍·시그널링은 실제 기기와 앱으로 연결·재접속·서버 재시작을 검증한다.
5. 런타임 소스가 없는 서비스는 소유권과 원본을 확보할 때까지 변경 작업을 보류한다.

### 장애 시

| 증상 | 첫 확인 |
|---|---|
| 맵 변환이 대기에서 멈춤 | 작업 원장 상태 → SQS visible/in-flight → worker 로그 → S3 객체·권한 |
| 히트맵이 비어 있음 | 호출자 요청 → 입력 맵·센서 데이터 → 계산 프로세스 → 결과 저장 위치 |
| 영상 연결 실패 | 시그널 Socket.IO → KVS 채널·STS → 스트리밍 프로세스 → 기기 응답 |
| 영상은 되지만 알림이 없음 | 스트리밍의 플랫폼 내부 API 주소·응답과 FCM 요청을 확인 |
| 재부팅 뒤 전체 기능 중단 | 각 EC2의 프로세스 관리자와 자동 시작 상태 확인 |
| DDL 적용 뒤 API 오류 | 적용 환경·스키마·컬럼 기본값·인덱스와 앱 실행 버전을 함께 확인 |

## 8. 미확인 항목

- 여섯 저장소의 환경별 실제 배포 버전과 산출물 checksum.

- 스트리밍 계열 시크릿 로테이션, WebSocket timeout, 운영 모니터링.
- 키 서비스의 런타임 소스, 배포본, 소유자, 키 회전·폐기 절차.
