## 0. 세 줄 요약

1. 기기 텔레메트리(IoT Core MQTT → Kinesis → Lambda)가 **RDS에 하루 1억 건 넘게 쓰던 구조**를 뜯어고쳤다. 최신 상태는 Redis, 시계열 이력은 S3+Athena, RDS에는 집계·관계형 데이터만 남기는 방향이다.
2. 그 과정에서 람다 3종(Redis·RDS·Router) 재작성, IoT 룰 11종 → 4종 통합, WAS·security의 **MQTT 직접 구독을 SQS 소비로 전환**, 제어 명령 발행을 **HTTPS(IoT Data Plane)로 전환**, 발행 성공/실패 로그를 도입했다. 코드는 전부 `main`까지 반영됐다.
3. 남은 것은 **람다 실배포 상태 확인**, **공기질 원장 INSERT 제거(Athena 집계 대사 후)**, 협력사가 만든 **FOLLOW_ME 버그 수정 머지**, **aqtarget republish 룰 삭제**, **MQTT 코드 제거**, **스트리밍 서비스의 SQS 전환 조율**이다.

## 1. 배경

### 1-1. 용어

| 용어 | 뜻 |
|---|---|
| **텔레메트리** | 기기가 주기적으로 올리는 상태 메시지. `status`(동작 상태·배터리), `air_quality`(공기질), `heartbeat`(살아있음 신호), `location`(위치), `part`(부품) 등 |
| **airbot / aqm** | 나무엑스 제품 2종. airbot은 이동형 공기청정 로봇(DB `device_type`=`ABT`), aqm은 고정형 공기질 측정기(`AQM`, 무선은 `AQM_WLS`) |
| **토픽** | MQTT 주소. 형식 `skmg/{product}/{serial}/v1/{type}[/{subtype}]`. 예: `skmg/airbot/ABC123/v1/status` |
| **IoT Core / IoT 룰** | AWS의 MQTT 브로커 / 브로커에 들어온 메시지를 SQL로 골라 다른 AWS 서비스로 보내는 규칙 |
| **KDS (Kinesis Data Stream)** | IoT 룰이 메시지를 넣는 스트림. 개발계 이름 `skmg-airbot-kds-dev`. 파티션 키가 같은 메시지는 같은 샤드로 가서 순서가 보장된다 |
| **ESM (Event Source Mapping)** | Kinesis → Lambda 연결 설정. 배치 크기·재시도·**필터**를 여기서 정한다. 필터에 안 맞는 레코드는 람다를 호출하지 않고 버린다 |
| **Firehose / 브론즈** | Kinesis 내용을 S3에 파일로 떨구는 서비스 / 가공 없는 원본 계층. 이 문서에서 "브론즈 적재"는 전 토픽 원문을 S3에 쌓는 것 |
| **Athena** | S3 파일을 SQL로 조회하는 서비스. 스캔한 바이트만큼 과금 |
| **파티션 프로젝션** | Athena 테이블에서 `year/month/day/hour` 파티션을 크롤러 없이 규칙으로 계산하는 설정 |
| **Redis 람다 / RDS 람다 / Router 람다** | `benjamin-lambda` 저장소의 `Redis/`, `RDS/`, `Router/`. 각각 캐시 쓰기, MySQL 이력 INSERT, SQS 분배를 한다 |
| **WAS** | `backend-api-main`(나무엑스 앱·관제 API). security는 `skix-security`(보안 서비스) |
| **write-back** | 람다가 RDS에 매번 쓰던 값을 Redis에만 쓰고, 스케줄러가 1분마다 Redis → RDS로 모아 쓰는 방식 |
| **hot row** | 같은 행에 쓰기가 몰리는 것. `statistics_operation`은 기기당 1행(약 7천 행)인데 하루 1억 번 UPSERT를 받았다 |
| **lastSeen** | Redis 키 `lastSeen:{serial}`. status·air_quality·heartbeat 중 마지막 수신 시각(epoch ms) |
| **원장** | 공기질 원본 이력 테이블 `history_airbot_air_quality`, `history_aqm_air_quality` |
| **요약테이블** | 원장을 시간/일 단위로 집계한 `statistics_air_quality_hour/day`, `statistics_aqm_air_quality_hour/day` |
| **DLQ** | Dead Letter Queue. 여러 번 처리 실패한 SQS 메시지가 옮겨지는 큐 |
| **FIFO 큐 / MessageGroupId** | 순서 보장 SQS 큐 / 순서를 보장할 단위. 여기서는 serial(기기) |
| **aqtarget** | aqm 공기질 메시지에 `AQTarget` 필드가 있을 때 WAS가 따로 처리하는 파생 메시지. 원래 IoT 룰이 `.../aqtarget` 토픽으로 재발행(republish)했다 |

### 1-2. 문제

| # | 문제 | 규모 (2026-06~07 실측·추정) |
|---|---|---|
| 1 | RDS 람다가 status·air_quality·heartbeat 수신마다 `statistics_operation`을 UPSERT. 기기당 1행인 테이블에 쓰기가 몰려 redo/binlog 폭증과 행 락 경합 | 하루 약 1억 UPSERT. heartbeat만 약 6,300만(시각 컬럼 하나 갱신) |
| 2 | 공기질 원장에 무한 누적 INSERT. 매 INSERT마다 device/contract/company/user 조인 서브쿼리 동반. 삭제 배치 없음 | 운영 airbot만 하루 330만+ 건 |
| 3 | Redis 람다 **배치 크기 1**(레코드 1건당 호출 1회), 재시도 무한(-1), 필터 없음 | 하루 약 1억 호출. heartbeat가 전체의 58% |
| 4 | 람다 코드 품질: 매 호출마다 DB 커넥션 생성, multi-statement로 실패 감지 불가, 위치 기반 `?` 30여 개(컬럼-값 밀림 위험) | – |
| 5 | 람다를 콘솔에서 직접 편집하고 의존성은 Layer로 따로 관리 → Git과 실배포본이 어긋남 | – |
| 6 | IoT 룰이 토픽별 11종으로 파편화. 약 3% 토픽(aqtarget 재발행 등)은 어떤 룰에도 안 걸려 S3에 없음. 일부 룰은 파티션 키가 `newuuid()`라 기기별 순서 보장 없음. 미리 만들어진 통합 룰은 파티션 키가 `${topic(4)}`(= 상수 `v1`)라 켜면 한 샤드로 몰리는 상태 | – |
| 7 | S3 적재가 비압축 JSON | 하루 약 35GB |
| 8 | 같은 MQTT 메시지를 CloudWatch Logs에도 이중 적재 | 하루 4천만 건, 약 20GB, 월 약 $450 |
| 9 | WAS·security가 **서버인데 MQTT로 IoT Core를 직접 구독**. 배포·재시작 중 수신 메시지 유실, 같은 clientId 재접속 시 기존 연결 강제 종료, 처리 실패 메시지는 조용히 사라짐 | – |
| 10 | 발행(제어 명령) 성공/실패 기록이 WAS에는 없고, security는 성공만 기록되는 버그 | – |

### 1-3. 목표

- RDS를 실시간 쓰기 경로에서 뺀다. **최신 상태 = Redis, 시계열 = S3+Athena, RDS = 관계형·집계만.**
- 람다 호출 수와 비용을 줄이고, 람다 배포를 Git 기준으로 재현 가능하게 만든다.
- 모든 IoT 메시지를 빠짐없이 S3에 남긴다(브론즈 완전성). 조회는 Athena로.
- 서버의 IoT 수신을 SQS로 바꿔 배포 중 유실을 없애고, 실패를 DLQ로 드러나게 한다.
- 전환은 **설정 토글**로 한다. 코드 배포만으로는 동작이 바뀌지 않고, 롤백은 설정값 되돌리기로 끝나야 한다.

### 3-2. 람다 인벤토리

런타임은 셋 다 **Node.js 22.x, ESM(`.mjs`)**, 핸들러는 `index.handler`. 의존성은 zip 안의 `node_modules`에 포함되어 Layer가 없다. 함수 이름은 개발계 기준 Redis=`ds_to_cache_cluster_dev`, RDS=`ds_to_aurora_dev`로 확인됐다. **Router 함수 이름과 stg/prd 함수 이름은 미확인**(콘솔 Lambda 목록에서 트리거가 Kinesis인 함수를 찾으면 된다. stg/prd는 접미사만 다를 것으로 예상했으나 확인 안 됨).

#### (1) Redis 람다 — `Redis/index.mjs`

| 항목 | 내용 |
|---|---|
| 역할 | 텔레메트리 최신값을 Redis에 SET. **RDS를 건드리지 않는다** |
| 트리거 | Kinesis ESM. 배치 크기 **200**, 재시도 **2회**, 오류 시 배치 분할(bisect) **켬** |
| ESM 필터 | `data.topic` suffix ∈ `/status`, `/air_quality`, `/location`, `/part`, `/heartbeat` |
| 입력 | Kinesis 레코드(base64 JSON). IoT 룰이 원 페이로드에 `topic`, `prefix`, `meta_*`를 덧붙인 형태 |
| 출력 | Redis SET (키 목록 §3-3) |
| 환경변수 | `REDIS_HOST`, `REDIS_PORT` 필수. `LOCAL_REDIS=true` 또는 `REDIS_MODE=single`이면 단일 노드, 아니면 클러스터 + TLS |
| 실패 처리 | 레코드 단위로 격리(`Promise.allSettled`). **예외를 던지지 않고 `statusCode 500`만 반환**한다. 캐시는 다음 텔레메트리로 곧 덮이므로 재시도로 샤드를 막는 것보다 유실이 낫다는 판단 |
| 토픽 판정 | 토픽을 `/`로 나눠 5 또는 6 세그먼트만 처리. `skmg/{product}/{type}`로 줄여 switch |

| 실패 처리 | SQS 부분 실패·오류 시 **예외를 던진다** → Kinesis가 배치를 재처리. 중복은 FIFO 중복제거 ID(시퀀스 번호)가 5분 창 안에서 막는다 |

### 3-5. IoT 룰 최종 구성 (dev 기준 이름, 2026-07-07 확정)

| 룰 | 토픽 | 역할 | 파티션 키 | S3 prefix |
|---|---|---|---|---|
| `iot_rule_skmg_kds_dev` | `skmg/#` | 전 토픽 통합 수집 | `${topic(3)}` = serial | 토픽에서 serial 빼고 `/`→`_` |
| `iot_rule_skmg_jobEvent_kds_dev` | `$aws/events/jobExecution/+/+` | 펌웨어 잡 실행 상태 이벤트 | `${topic(4)}` = jobId | 리터럴 `'aws_events_jobexecution'` |
| `iot_rule_skmg_jobProtocol_kds_dev` | `$aws/things/+/jobs/#` | 기기↔Jobs 서비스 프로토콜 왕복 | `${topic(3)}` = thingName | 리터럴 `'aws_things_jobs'` |

통합 룰 SQL에는 원 페이로드 외에 아래 필드를 덧붙인다.

```sql
topic()      AS topic,
-- prefix: 토픽에서 serial 세그먼트를 빼고 '/' → '_'
replace(regexp_replace(topic(), "^([^/]+/[^/]+)/[^/]+/(.*)", "$1/$2"), "/", "_") AS prefix,
timestamp()  AS meta_ingest_ts,    -- 브로커 수신시각 epoch ms (기기 시계 무관)
clientid()   AS meta_client_id,    -- MQTT 클라이언트 ID (= serial)
sourceip()   AS meta_source_ip,    -- 발행자 소스 IP
principal()  AS meta_principal     -- 인증 주체 (X.509 인증서 ID)
```

위는 문서로 남긴 설계값을 옮긴 것이고 룰 SQL 원문은 Git에 없다. 실제 SQL은 IoT 콘솔 → 규칙 → `iot_rule_skmg_kds_{env}`에서 확인한다. `meta_`는 파이프라인이 주입한 필드라는 네임스페이스다. 기기 페이로드 필드와 충돌하지 않게 붙였다. 레코드당 약 150B 늘지만 CloudWatch 이중 적재 제거로 상쇄된다.

| 룰 | 사유 |

| `iot_rule_skmg_iotlogs_cloudwatch` (`skmg/#` → CloudWatch) | 고볼륨 이중 적재. CloudWatch 수집료 GB당 약 $0.76. Athena `iot_messages_raw`로 대체 |

| 큐 | 소비자 | 설정 위치 |

### 3-7. 애플리케이션 토글

기본값은 전부 "기존 MQTT 동작"이다. 코드만 배포해서는 아무 것도 바뀌지 않는다.

| 키 | 값 | 의미 |
|---|---|---|
| `aws.sqs.enabled` | `true` | SQS 리스너 빈 생성 |
| `aws.iot.subscribe-enabled` | `false` | MQTT 구독 끔. `sqs.enabled=true`와 동시에 `true`면 기동 시 "이중 처리" 경고 로그 |
| `aws.iot.publish-mode` | `mqtt` → `https` | 발행 전송 방식. `https`는 `IotDataPlaneClient.publish`(QoS 0, IAM SigV4) |

**구독 off + `https`이면 MQTT 클라이언트 자체가 생성되지 않는다.** 인증서·clientId·재연결 관리가 사라진다. WAS는 `IoTConfiguration`의 `@ConditionalOnExpression`, security는 `AwsIotMqttClient.isDisabled()`로 처리. security 헬스체크(`MqttHealthIndicator`)는 이 모드에서 `UP`("Disabled - SQS consume + HTTPS publish mode")을 보고한다.

| 저장소 | 값이 있는 곳 | 현재 커밋된 값 |
|---|---|---|
| `backend-api-main` main | `src/main/resources-{vdi,stag,prod}/application.yml` | 3환경 모두 `sqs.enabled: true` / `subscribe-enabled: false` / `publish-mode: https` |
| `backend-api-main` dev·stg | `src/main/resources/application-{dev,stg,prd}.yml` (이후 별건 작업으로 설정 파일 구조가 바뀜) | 동일 |
| `skix-security` (3브랜치) | 공통 `application.yml`에 기본값(`false`/`true`/`mqtt`), 환경값은 `deploy/task-definition-{dev,stg,prd}.json` env | 3환경 모두 `AWS_SQS_ENABLED=true`, `AWS_IOT_SUBSCRIBE_ENABLED=false`, `AWS_IOT_PUBLISH_MODE=https` |

### 3-8. 발행 로그

| 저장소 | 구현 | 동작 |
|---|---|---|
| `skix-security` | `MqttPublisher.publish()`/`publishCommand()`를 try/finally로 재작성 | 성공·실패 모두 `mqtt_publish_log`에 기록. 실패 예외는 호출자에게 그대로 재전파 |
| `backend-api-main` | `PublishDeviceService.publish()` | 성공·실패 모두 기록. 기존의 "발행 실패를 흡수하는" 동작은 유지. dev·stg에는 09-03~04 별건 수정으로 로그 적재가 `MqttPublishLogWriter`(`REQUIRES_NEW` 독립 트랜잭션)로 분리되고 발행이 트랜잭션 커밋 이후로 옮겨졌다. **이 분리는 main에 없다** |

발행은 SQS 같은 재시도/DLQ가 없다. 제어 명령은 멱등하지 않아 시스템이 재시도하면 기기가 명령을 두 번 실행할 수 있어서다. 대신 DB 로그(사후 추적)와 DLQ 알람(실시간 탐지)으로 "실패를 빨리 아는 것"을 목표로 했다.

## 4. 메시지·데이터 계약

### 4-1. Router → SQS 메시지

```
MessageBody            : 기기가 보낸 원 JSON (topic / prefix / meta_* 제거)
MessageAttributes.topic: "skmg/airbot/ABC123/v1/getSchedule"   (aqtarget은 합성 토픽 "skmg/aqm/{serial}/v1/aqtarget")
MessageGroupId         : serial   (jobExecution은 thingArn 끝 조각)
MessageDeduplicationId : Kinesis sequenceNumber
```

소비자(WAS·security)는 `@Header("topic")`으로 토픽을 받아 **토픽 마지막 세그먼트(topicEnd)로 핸들러를 고른다.** MQTT 시절 코드 경로를 그대로 재사용하므로 본문 형식이 MQTT 시절과 같아야 한다.

### 4-2. 토픽 → 소비자 매핑

- **WAS(benjamin 큐)** 35종: `mapping`, `setMap`, `setClean`, `error`, `aqmCall`, `moveTo`, `setConfig`, `getConfig`, `event`, `setSchedule`, `started`, `getSchedule`, `getOutdoorWI`, `setOutdoorWI`, `comeback`, `control`, `statusClean`, `getAQMList`, `aq_map`, `getDeviceLogResponse`, `initStatus`, `factoryReset`, `getLLMOutdoorWI`, `getLLMWF`, `getFirmwareVersion`, `getLatestVersion`, `getHomeInformation`, `otaEvent`, `getMapInformation`, `cleanResult`, `AILogData`, `toggleSchedule`, `getS3URL`, `mapUpload`, `getHoliday`. 추가로 `aqtarget`(합성), `$aws/events/jobExecution/{jobId}/{status}`(WAS가 `IN_PROGRESS`/`succeeded`/`failed`/`rejected`를 `jobUpdate` 핸들러로 매핑).
- **security 큐** 16종: `pin`, `securityMode`, `upload`, `lowLight`, `networkUnstable`, `lowBattery`, `event`, `requestSubscriptionStatus`, `kvsSessionStart`, `kvsSessionTerminate`, `kvsConnected`, `kvsHeartbeat`, `kvsSessionClosed`, `dispatchVideoUpload`, `dispatchVideoUploadCompleted`, `undock`. 단 `skmg/security/…` 네임스페이스만.
- 두 서비스가 같은 이름(`event`, `upload`)을 쓰지만 Router가 `skmg/security/` prefix를 먼저 가르므로 섞이지 않는다.

**새 토픽을 서버가 받게 하려면 세 곳을 같이 고친다**: ① `infra/esm-filters.json`의 Router 필터(→ 콘솔 ESM 필터에 반영) ② `Router/index.mjs`의 `BENJAMIN_ACTIONS` 또는 `SECURITY_ACTIONS` ③ 소비자 쪽 분기(WAS `IotInboundMessageHandler.VALID_TOPIC_ENDS`, security `MqttMessageHandler`의 토픽 분기). 한 곳이라도 빠지면 **오류 없이 조용히 버려진다.** 전환 직후 `getS3URL`이 이렇게 빠져 있다가 리뷰에서 발견됐다.

### 4-3. Athena 테이블

| 테이블 | 스키마 | 파티션 | 용도 |
|---|---|---|---|
| `iot_messages_raw` | `payload string` 한 컬럼(원문 한 줄) | `prefix`(**injected**), `year`, `month`, `day`, `hour` | 전 토픽 원문 조회. 필드는 `json_extract_scalar(payload, '$.serial')` |
| `airbot_air_quality` | JSON SerDe, `serial`, `air_quality` struct, `location` struct 등 | `year/month/day/hour` 프로젝션 | 스케줄러 집계 |
| `aqm_air_quality` | JSON SerDe | 동일 | 스케줄러 집계 |

- `prefix`가 injected 파티션이라 **WHERE에 `prefix = '...'`를 반드시 넣어야** 한다. `SELECT DISTINCT prefix`는 안 된다. 폴더 목록은 `aws s3 ls s3://<버킷>/`로 본다.
- 버킷: 개발계 `airbot-s3-lake-dev`, 운영계 `skmg-benjamin-prd-s3-lake`. 검증계는 미확인.
- 파티션 프로젝션에서 `month/day/hour`는 두 자리(`digits=2`) 설정이 필수다.
- **시간대**: 페이로드 최상위 `timestamp`는 UTC(`...Z`), MySQL 이력의 `create_date`는 KST. 조인할 때 9시간 보정을 빼먹으면 값이 그럴듯하게 틀린다. 파티션 `hour`가 UTC인지 KST인지는 Firehose 설정에 달려 있고 **확정되지 않았다.** 파티션을 넉넉히 잡고 `timestamp`로 정밀 필터링하는 게 안전하다.
- Firehose 버퍼 때문에 최근 1~5분은 Athena에 아직 없다. 실시간은 IoT Core 콘솔의 MQTT 테스트 클라이언트로 본다(`$aws` 토픽도 구독 가능).

## 5. 되돌리면 안 되는 설계 결정

| # | 결정 | 바꾸면 생기는 일 |
|---|---|---|
| 1 | **Kinesis 파티션 키는 `${topic(3)}`(serial)** | 원래 통합 룰은 `${topic(4)}`였는데 이는 모든 토픽에서 상수 `v1`이다. 전량이 샤드 하나로 몰려 쓰기 한도 초과(`WriteProvisionedThroughputExceeded`)가 난다. `newuuid()`로 두면 같은 기기 메시지가 샤드에 흩어져 순서가 깨지고, RDS 람다의 FOLLOW_ME 시작/종료 판정이 뒤집힐 수 있다 |
| 2 | **`$aws/...` 잡 룰의 prefix는 리터럴**(`'aws_events_jobexecution'`, `'aws_things_jobs'`) | 공용 prefix 정규식을 쓰면 jobId가 폴더 이름에 들어가 S3에 잡마다 폴더가 무한히 생긴다. Athena injected 파티션도 쓸 수 없게 된다 |
| 3 | **Redis 람다는 예외를 던지지 않는다** | 던지면 Kinesis가 같은 배치를 재시도하느라 그 샤드 전체가 멈춘다. 캐시는 다음 텔레메트리로 곧 덮이므로 유실이 정체보다 낫다. 반대로 **Router 람다는 던진다.** SQS 적재 실패는 이벤트 유실이라 재처리가 필요하고, 중복은 FIFO 중복제거가 막는다 |
| 4 | **ESM 재시도 2회 + bisect** (무한 재시도 금지) | 무한(-1)이면 poison 레코드 하나가 Kinesis 보존기간 내내 샤드를 막는다 |
| 5 | **write-back UPSERT는 `COALESCE(VALUES(x), x)`** | Redis 키 그룹이 통째로 없을 때(캐시 리셋 직후 등) 해당 컬럼을 NULL로 덮어 기존 값을 지운다. 7/8 리뷰에서 발견해 고쳤다 |
| 6 | **write-back 활동 판정 창은 1시간**(`ACTIVE_WINDOW_MS`) | 이 테이블을 읽는 집계 SQL이 `-1H` 윈도우를 쓴다. 창을 줄이면 집계에서 기기가 빠지고, 늘리면 꺼진 기기의 마지막 값이 계속 "최신"으로 다시 써진다. `create_date`를 lastSeen으로 쓰는 것도 같은 이유(쓴 시각이 아니라 받은 시각) |
| 7 | **Router는 `topic`·`prefix`·`meta_*`를 페이로드에서 제거하고 보낸다** | 7/13에 실제로 났다. 붙인 채 보내면 WAS의 DTO 역직렬화가 `UnrecognizedPropertyException`으로 실패하고, 원문을 저장하는 컬럼 길이가 넘친다. MQTT 시절과 같은 순수 페이로드여야 한다 |
| 8 | **공기질 신선도는 `airQualityLastSeen`, 활동 판정은 `lastSeen`** (분리 유지) | `lastSeen`은 heartbeat·status로도 갱신된다. 이걸로 공기질 신선도를 판단하면 heartbeat만 오는 기기의 오래된 공기질이 "최신"으로 보인다. 구역 키 `lastSeen:{serial}:{areaId}`는 공기질에서만 쓰므로 원래 공기질 전용이다 |
| 9 | **SQS 소비는 리스너 스레드에서 동기 처리하고 예외를 전파** | 처음 구현은 비동기 스레드/이벤트버스로 넘기고 바로 반환했다. 그러면 처리가 실패해도 SQS는 성공으로 보고 삭제한다. DLQ가 한 번도 채워지지 않는 "죽은 DLQ"가 된다. MQTT 경로는 비동기를 유지한다(전송별로 실패 의미가 다르다) |
| 10 | **영구 실패만 ack, 나머지는 재시도** (WAS `IotInboundMessageHandler.isPermanent`) | FIFO는 한 메시지가 실패하면 같은 MessageGroupId(같은 기기)의 뒤 메시지가 전부 막힌다. 파싱 오류·컬럼 폭 초과 같은 영구 실패를 재시도하면 그 기기의 정상 메시지까지 수신 횟수가 차서 통째로 DLQ로 간다(08-06 운영 사고). 반대로 AWS SDK 예외는 `retryable()`이 대부분 false라 판정 기준으로 쓰면 안 된다. DB 연결 실패는 개별 타입으로 빼 두었다(상위 타입으로 묶으면 유실) |
| 11 | **컷오버는 재배포가 아니라 설정 토글, 기본값은 기존 동작** | 기본값을 새 동작으로 바꾸면 "배포 = 전환"이 되어 배포 리스크와 운영 리스크가 합쳐진다. 롤백도 이미지 되돌리기가 필요해진다 |
| 12 | **SQS 소비와 MQTT 구독을 동시에 켜지 않는다** | 같은 메시지를 두 번 처리한다. 제어 응답·이력이 두 벌 쌓인다. 기동 로그에 경고가 뜨도록 해 두었다 |
| 13 | **발행 실패를 시스템이 재시도하지 않는다** | 제어 명령(청소 시작, 이동 등)은 멱등하지 않다. 대신 `mqtt_publish_log`에 실패를 남긴다. security `success` 컬럼의 `DEFAULT 1`은 스키마를 앱보다 먼저 적용할 때 구버전 INSERT가 거절되지 않게 하려는 것이므로 지우지 않는다 |
| 14 | **Router의 WAS 라우팅은 `parts[1]`이 `airbot`/`aqm`일 때만** | WAS의 옛 MQTT 구독은 `skmg/+/+/+/event` 같은 광역 와일드카드라 security·streaming 토픽까지 우연히 받고 있었다. 이 조건을 빼면 WAS 큐에 남의 이벤트가 쌓이고 WAS 핸들러가 엉뚱한 기기 이벤트를 처리한다 |
| 15 | **aqtarget은 Router가 합성하고, republish된 `.../aqtarget` 토픽은 Router가 무시** | 둘 다 받으면 aqtarget이 두 번 큐에 들어간다. Router 필터에 `/aqtarget`을 넣지 않는다 |
| 16 | **`statistics_operation` 테이블은 없애지 않는다** | FOTA 대상 선정이 모듈 버전으로 필터·정렬한다. Redis로는 값 필터·집계를 못 한다. 없앤 것은 텔레메트리발 hot-row UPSERT뿐이다 |
| 17 | **DynamoDB로 옮기지 않는다** (검토 후 기각) | 텔레메트리는 같은 키에 같은 값을 반복해서 쓴다. Redis 덮어쓰기는 비용이 늘지 않지만 DynamoDB는 쓰기마다 과금된다. 하루 1억 건 기준 온디맨드 월 약 $1,600으로, 현행 Kinesis+Lambda(약 $650)의 2~3배 |
| 18 | **Parquet 실버 계층은 아직 만들지 않는다** | 지금 공기질 데이터의 소비자는 집계 배치 하나다. "변환 1회 + 집계 1회 스캔"이 "JSON 직접 1회 스캔"보다 비싸다. 같은 데이터를 반복 조회하는 소비자가 생길 때 도입한다 |
| 19 | **스케줄러는 Athena JDBC가 아니라 AWS SDK를 쓴다** | 스케줄러 DB는 Spring Boot 자동설정 단일 데이터소스다. JDBC로 두 번째 데이터소스를 붙이면 기존 MyBatis 설정 전체를 손대야 한다 |
| 20 | **요약테이블 `map_id`는 `device_map_history`에서 집계 대상 시각 기준으로 조회** | 배치 시점의 현재 `device_map`으로 조인하면, 기기가 다른 지도로 옮겨진 뒤 과거 집계가 새 지도에 붙는다 |

## 7. 배포 방법

### 7-1. 람다 배포 (zip 업로드)

```bash
cd benjamin-lambda
./deploy.sh            # 각 디렉터리에서 npm ci --omit=dev 후 zip
ls dist/
#  rds-lambda.zip  redis-lambda.zip  router-lambda.zip  lambda-zips.tar.bz2
```

- `package-lock.json` 기준 `npm ci`라 재현 가능하다. zip 하나에 코드와 `node_modules`가 다 들어 있다(Layer 불필요). 해외 법인 등 다른 조직에도 zip만 넘기면 배포가 끝난다.
- VDI에서 Lambda 콘솔 → 함수 → 코드 → ".zip 파일 업로드". CloudShell을 쓸 때는 `lambda-zips.tar.bz2` 하나만 올리고 `tar -xjf lambda-zips.tar.bz2`로 푼다.
- 런타임 **Node.js 22.x**, 핸들러 `index.handler`. 환경변수는 콘솔에서 관리한다(§3-2).
- **콘솔에서 코드를 직접 고치지 않는다.** Git이 유일한 원본이다.
- `dist/`와 `*.zip`은 `.gitignore` 대상이다. 로컬 `dist/`에 있는 zip은 7/7 빌드본이라 배포 전 다시 빌드한다.

### 7-2. ESM(트리거) 설정

| 항목 | Redis 람다 | RDS 람다 | Router 람다 |
|---|---|---|---|
| 배치 크기 | 200 | (미확인, 200 권장) | (미확인) |
| 재시도 | 2 | 2 권장 | 2 권장 |
| 오류 시 배치 분할 | 켬 | 켬 | 켬 |
| 필터 | `infra/esm-filters.json`의 `redis` | 같은 파일 `rds` | 같은 파일 `router` |

필터 JSON은 `mappings[].filters[]`의 각 원소가 ESM 필터 패턴 하나다. 콘솔 → 람다 → 구성 → 트리거 → Kinesis 트리거 편집 → 필터 기준에 원소를 하나씩 넣는다(패턴 사이는 OR). Kinesis ESM 필터는 레코드 본문을 `data`로 참조한다.

필터 변경 후 확인: 람다의 `Invocations` 지표가 줄었는지, CloudWatch 로그에 `parse error`나 `missing serial`이 늘지 않는지.

### 7-3. IoT 룰 컷오버 (환경별 1회, 이미 실행됨)

1. 콘솔: 통합 룰 파티션 키를 `${topic(3)}`으로 수정(비활성 상태 유지).
2. CloudShell: 개별 KDS 룰 11종 disable → 통합 룰 enable. **몇 초 유실은 감수하고 중복은 피한다**(주기 텔레메트리라 몇 초 유실은 무해하지만 중복 INSERT는 DB에 남는다).
3. 검증: Kinesis `IncomingRecords`가 유지되거나 약 3% 증가, `WriteProvisionedThroughputExceeded`=0, S3에 새 폴더(`skmg_aqm_v1_aqtarget` 등) 생성, 람다 로그 조용함, `lastSeen:*` 갱신.
4. `iotlogs_s3` 룰 제거는 **통합 룰에 meta 4종을 넣은 뒤**에(접속 감사 정보 공백 방지).
5. stg/prd에서 반복. 룰 이름은 환경별 덤프로 확인한다.

### 7-4. 애플리케이션 SQS/HTTPS 컷오버 (이미 실행됨. 재구축·롤백 시 순서)

## 9. 운영 중 자주 만날 상황

| 상황 | 확인 방법 |
|---|---|
| "앱에서 기기 상태(배터리·충전·전원)가 이상해요" | Redis `GET battery:{serial}`, `GET operation:{serial}`, `TTL power:{serial}`. `power` 키가 없으면 OFF로 보인다. airbot은 status가 2분 넘게 안 오면 OFF, aqm 무선은 31분 |
| 관제 대시보드 수치가 멈춤 | `statistics_operation.create_date`가 최근 1분 안인지. 아니면 ① `GET lastSeen:{serial}` 값이 갱신되는지(Redis 람다) ② 스케줄러 로그 `write-back: N active devices upserted` |
| 공기질 요약 그래프에 특정 시간이 비어 있음 | 스케줄러 로그 `createCollectAirQualityHour error`. Athena 실패는 예외를 삼켜 **다음 시간에 자동 복구되지 않는다.** 해당 시각을 수동으로 재집계해야 한다(같은 SQL을 Athena 콘솔에서 실행 후 INSERT, 또는 임시로 target 시각을 바꿔 메서드 실행) |
| "명령을 보냈는데 기기가 반응이 없어요" | WAS: `SELECT * FROM mqtt_publish_log WHERE serial='<serial>' ORDER BY id DESC LIMIT 20;` / security: `SELECT * FROM security.mqtt_publish_log WHERE serial='<serial>' ORDER BY id DESC LIMIT 20;` (`published_at`은 UTC). `success=0`이면 `error_message`. `success=1`인데 반응이 없으면 기기 쪽(오프라인·펌웨어). 기기 응답은 Athena `prefix='skmg_airbot_v1_response_<action>'` |
| DLQ 알람 | ① DLQ 메시지를 콘솔에서 몇 건 열어 `topic` 속성과 serial 분포 확인 ② 소비자 로그에서 같은 시각 `IoT handler failed` 검색 ③ 반복 실패(코드 버그)면 고친 뒤 redrive, 일시 실패면 SQS 콘솔 "DLQ 재드라이브" ④ 영구히 처리 불가하면 폐기. **FIFO 특성상 한 기기의 한 메시지가 막히면 그 기기의 뒤 메시지가 줄줄이 DLQ로 간다**(08-06 사례: getSchedule 응답이 `op_param` TEXT 64KB를 넘어 기기 1대의 8개 토픽이 통째로 DLQ) |
| `IoT handler permanent failure - 재시도 없이 ack` 로그 | 파싱 오류·컬럼 폭 초과 등으로 **버려진** 메시지. 재처리 불가하므로 로그의 handler·원인으로 코드 수정 여부 판단 |
| 서버가 특정 토픽을 무시함 | §4-2의 세 곳(ESM 필터, Router 화이트리스트, 소비자 화이트리스트) 확인. Router는 대상 아니면 로그 없이 버린다 |
| 소비자 기동 시 `SQS 소비와 MQTT 구독이 동시에 활성화됨` 경고 | 설정 실수. `subscribe-enabled=false`로 바로잡는다. 그대로 두면 이중 처리 |
| security 헬스체크 DOWN (`Not connected - reconnecting`) | MQTT 모드로 돌아가 있다는 뜻. HTTPS+SQS 모드면 `Disabled - SQS consume + HTTPS publish mode`로 UP이어야 한다. 태스크 정의 env 확인 |
| 람다 로그 키워드 | Redis: `redis set failed: n/m`, `Cache command build failed`, `Record decode/parse failed` / RDS: `history insert failed: n/m`, `Failed to process followMe history tracking` / Router: `SQS batch failures`, `SQS send error`, `jobExecution missing thingArn`, `missing serial`, `parse error` |
| Kinesis 적체 | `IteratorAge` 지표 상승 → 해당 람다 오류·스로틀 확인. Router가 SQS 실패로 예외를 계속 던지면 적체된다 |
| 기기 원문을 보고 싶음 | Athena `iot_messages_raw`(부록 E). 최근 1~5분은 IoT Core MQTT 테스트 클라이언트 |
| security가 이벤트를 받았는지 | security는 수신 메시지를 성공·실패 모두 `security.mqtt_subscribe_log`에 남긴다(SQS 경로 포함). `WHERE serial='<serial>' ORDER BY id DESC` |
| robotStatus 이력이 필요함 | RDS 어디에도 시계열이 없다(`operation:` 덮어쓰기, `statistics_operation` 기기당 1행, `history_status`는 FOLLOW_ME만). `prefix='skmg_airbot_v1_status'` 원문이 유일한 경로 |

```
 (1)     (2)        (3)      (4)     (5)      (6)       ← IoT SQL topic(N), 1부터
```

- 파티션 키 `${topic(3)}` = serial은 모든 `skmg` 토픽(6세그먼트 `response/*` 포함)에서 성립한다.
- S3 prefix 예: `skmg/airbot/{serial}/v1/air_quality` → `skmg_airbot_v1_air_quality`
- `$aws/...` 토픽은 이 구조가 아니므로 공용 정규식·파티션 키를 쓰면 안 된다(§5의 2번).

원칙: **수집은 전부, 선별은 소비자에서.** 모든 `skmg` 토픽이 Kinesis에 들어가고 각 소비자가 ESM 필터로 자기 몫만 받는다. 서버가 발행한 명령 토픽도 S3에는 남지만(감사 로그) Router가 버리므로 큐로 되돌아오는 루프는 없다.

### B-2. 텔레메트리 (기기 → 서버, 주기 발행)

| type | 제품 | 소비자 | 일 볼륨(운영 참고) |
|---|---|---|---|
| heartbeat | airbot, aqm | Redis(`lastSeen`, `heartbeat`) | 약 6천만 (전체의 58%) |
| status | airbot, aqm | Redis(`operation`/`battery`/`sensor`/`power`/`firmware`), RDS(airbot FOLLOW_ME → `history_status`) | 다수 |
| air_quality | airbot, aqm | Redis(`air_quality` 등), RDS(원장, 제거 예정), Athena 집계. aqm에 `AQTarget` 있으면 Router → WAS(aqtarget) | airbot 약 330만 |
| location | airbot | Redis(`location`) | – |
| part | airbot | Redis(`part`) | – |
| error | airbot, aqm | Router → WAS | – |
| AILogData | airbot | Router → WAS | – |

### B-3. WAS가 받는 토픽 (옛 MQTT 공유 구독 37종 → 지금은 benjamin 큐)

- **공통**: `started`, `initStatus`, `error`, `event`, `factoryReset`, `otaEvent`, `getLatestVersion`, `getHomeInformation`, `getMapInformation`, `response/getConfig`, `response/setConfig`, `response/getDeviceLogResponse`, `response/getFirmwareVersion`

- **AWS**: `$aws/events/jobExecution/+/+` (펌웨어 잡 상태)

### B-4. 명령/응답 규약

- 서버 → 기기 명령: `skmg/{product}/{serial}/v1/command/{action}`. Router는 `parts[4]=='command'`로 식별해 제외.
- 기기 → 서버 응답: `skmg/{product}/{serial}/v1/response/{action}` (명령 페이로드의 `replyTo`).

### B-5. security (`skmg/security/{serial}/v1/...`)

- 구독(기기 → 서버): `event`, `requestSubscriptionStatus`, `response/{pin, securityMode, upload}`, `status/{lowBattery, lowLight, networkUnstable}`, 그리고 07-20에 추가된 `kvsSessionStart`, `kvsSessionTerminate`, `kvsConnected`, `kvsHeartbeat`, `kvsSessionClosed`, `dispatchVideoUpload`, `dispatchVideoUploadCompleted`, `undock`
- 발행(서버 → 기기): `command/{action}`(+`replyTo=response/{action}`), `notifySubscriptionStatus`

### B-6. 스트리밍 (`skmg/streaming/{serial}/{version}/...`)

- 발행: `command/{start, stop, undock, video/upload}`
- 구독: `response/{start, stop, undock, video/upload}`, `request/crypto/video-encrypt-key/provision`, `skmg/+/+/request/crypto/aes/save`(제품 무관, 7세그먼트)
- **Router 미라우팅.** 스트리밍 서비스가 직접 구독 중(§6).

### B-7. 특수 흐름

- **aqtarget**: republish 룰이 aqm `air_quality`에서 `AQTarget`이 있으면 `skmg/aqm/{serial}/v1/aqtarget`으로 재발행. 통합 룰 이전에는 이 토픽이 KDS에 안 들어가 "3% 미수집"의 주된 정체였다. 지금은 Router가 같은 일을 하므로 룰 삭제 대상.
- **`$aws/events/jobExecution/{jobId}/{status}`**: jobEvent 룰로 브론즈 + Router → WAS.
- **`$aws/things/+/jobs/#`**: 기기 잡 프로토콜 채터. jobProtocol 룰로 브론즈에만.

```sql
--   airbot/aqm을 왜 나눴는가 (운영 EXPLAIN ANALYZE로 확인된 병목):
--     history_airbot_air_quality, history_aqm_air_quality는 서로 다른 테이블이라

--     한 세션에서 순차로 끝내고 싶다면 하위 호환용 backfill_air_quality_map_id를 쓴다.
--
-- MySQL Workbench "Safe Updates" 모드(Error 1175) 대응:
--   JOIN UPDATE는 WHERE에 KEY 컬럼(id)을 직접 쓰지 않아 Workbench 기본 설정에서 막힘.
--   프로시저 내부에서 세션 단위로 SQL_SAFE_UPDATES를 잠시 해제함.
--
-- 성능 최적화 (신규 인덱스 추가 없이 기존 PK만 활용):
--   history_* 원장 테이블은 create_date로 필터링하면 세컨더리 인덱스 스캔 후

--   id는 AUTO_INCREMENT이고 create_date는 삽입 시점 타임스탬프라 사실상 같은 순서이므로,
--   먼저 create_date 인덱스로 해당 구간의 id 최소/최대값만 저렴하게 구한 뒤(LIMIT 1),
--   본 집계 쿼리는 FORCE INDEX (PRIMARY) + id BETWEEN 으로 클러스터드 인덱스를 직접
--   레인지 스캔하도록 바꿔 룩업 비용을 없앰. create_date 조건은 안전망으로 유지하고
--   클럭 역전 등 예외 대비로 id 경계에 ±5000 여유를 둠. (동일 create_date 타임스탬프에 여러 건이 몰려도 순서 미보장 대비)
-- ============================================================================

DELIMITER $$

DROP PROCEDURE IF EXISTS backfill_air_quality_map_id_airbot$$

CREATE PROCEDURE backfill_air_quality_map_id_airbot(
    IN p_start_date DATE,
    IN p_days INT
)
BEGIN
    DECLARE v_end_date DATE;
    DECLARE v_old_sql_safe_updates INT DEFAULT @@SQL_SAFE_UPDATES;
    DECLARE v_airbot_id_start BIGINT;
    DECLARE v_airbot_id_end BIGINT;

    SET v_end_date = DATE_ADD(p_start_date, INTERVAL p_days DAY);
    SET SQL_SAFE_UPDATES = 0;

    SELECT id INTO v_airbot_id_start
    FROM history_airbot_air_quality
    WHERE create_date >= p_start_date
    ORDER BY create_date ASC LIMIT 1;

    SELECT id INTO v_airbot_id_end
    FROM history_airbot_air_quality
    WHERE create_date < v_end_date
    ORDER BY create_date DESC LIMIT 1;

    -- airbot 시간집계
    UPDATE statistics_air_quality_hour sah
        JOIN (
            SELECT serial, area_id,
                   DATE_FORMAT(create_date, '%Y-%m-%d %H:00:00') AS bucket,
                   MAX(map_id) AS map_id
            FROM history_airbot_air_quality FORCE INDEX (PRIMARY)
            WHERE id BETWEEN v_airbot_id_start - 5000 AND v_airbot_id_end + 5000
              AND create_date >= p_start_date AND create_date < v_end_date
              AND map_id IS NOT NULL
            GROUP BY serial, area_id, bucket
        ) src ON src.serial = sah.serial
             AND src.area_id = sah.area_id
             AND src.bucket = sah.create_date
    SET sah.map_id = src.map_id
    WHERE sah.map_id IS NULL
      AND sah.create_date >= p_start_date AND sah.create_date < v_end_date;

    -- airbot 일집계
    UPDATE statistics_air_quality_day sad
        JOIN (
            SELECT serial, area_id,
                   DATE(create_date) AS bucket,
                   MAX(map_id) AS map_id
            FROM history_airbot_air_quality FORCE INDEX (PRIMARY)
            WHERE id BETWEEN v_airbot_id_start - 5000 AND v_airbot_id_end + 5000
              AND create_date >= p_start_date AND create_date < v_end_date
              AND map_id IS NOT NULL
            GROUP BY serial, area_id, bucket
        ) src ON src.serial = sad.serial
             AND src.area_id = sad.area_id
             AND src.bucket = DATE(sad.create_date)
    SET sad.map_id = src.map_id
    WHERE sad.map_id IS NULL
      AND sad.create_date >= p_start_date AND sad.create_date < v_end_date;

    SET SQL_SAFE_UPDATES = v_old_sql_safe_updates;

    SELECT p_start_date AS batch_start, v_end_date AS batch_end;
END$$
```

## 부록 E. Athena 조회 예시

7월 팀 공지에 넣었던 다섯 유형(기기별 원문, 에러 추적, 값 조건 검색, 시간대별 집계, FOTA 조사)을 인수자용으로 다시 쓴 것이다. 공지 원문 그대로는 아니다.

DB는 환경별 `benjamin-dev` / `benjamin-stg` / `benjamin-prd`. **`prefix`와 시간 파티션은 항상 WHERE에 넣는다**(안 넣으면 전체 스캔 과금).

```sql
-- 1) 기기 한 대의 status 원문 (특정 시간대)
SELECT payload
FROM iot_messages_raw
WHERE prefix = 'skmg_airbot_v1_status'
  AND year = 2026 AND month = 9 AND day = 22 AND hour BETWEEN 1 AND 3
  AND json_extract_scalar(payload, '$.serial') = '<serial>'
ORDER BY json_extract_scalar(payload, '$.timestamp');

-- 2) 에러 추적
SELECT json_extract_scalar(payload, '$.serial')          AS serial,
       json_extract_scalar(payload, '$.error.errorCode') AS error_code,
       json_extract_scalar(payload, '$.error.errorDate') AS error_date   -- 기기 로컬(KST)
FROM iot_messages_raw
WHERE prefix = 'skmg_airbot_v1_error'
  AND year = 2026 AND month = 9 AND day = 22;

-- 3) 값 조건 검색 (배터리 20% 미만)
SELECT json_extract_scalar(payload, '$.serial') AS serial,
       json_extract_scalar(payload, '$.timestamp') AS ts,
       json_extract_scalar(payload, '$.battery.chargeRate') AS battery
FROM iot_messages_raw
WHERE prefix = 'skmg_airbot_v1_status'
  AND year = 2026 AND month = 9 AND day = 22
  AND CAST(json_extract_scalar(payload, '$.battery.chargeRate') AS integer) < 20;

-- 4) 시간대별 메시지 수
SELECT hour, count(*) AS cnt
FROM iot_messages_raw
WHERE prefix = 'skmg_aqm_v1_air_quality'
  AND year = 2026 AND month = 9 AND day = 22
GROUP BY hour ORDER BY hour;

-- 5) FOTA 조사 (펌웨어 잡 상태 이벤트)
SELECT payload
FROM iot_messages_raw
WHERE prefix = 'aws_events_jobexecution'
  AND year = 2026 AND month = 9 AND day = 22
  AND json_extract_scalar(payload, '$.thingArn') LIKE '%<serial>';

-- 6) 브로커 수신 시각 vs 기기 시각 (기기 시계 오차 진단, meta 필드 추가 이후 데이터)
SELECT json_extract_scalar(payload, '$.timestamp')      AS device_ts_utc,
       from_unixtime(CAST(json_extract_scalar(payload, '$.meta_ingest_ts') AS bigint) / 1000) AS broker_ts_utc
FROM iot_messages_raw
WHERE prefix = 'skmg_airbot_v1_heartbeat'
  AND year = 2026 AND month = 9 AND day = 22 AND hour = 3
  AND json_extract_scalar(payload, '$.serial') = '<serial>';
```

- JSON 경로의 필드 이름(`battery.chargeRate`, `error.errorCode` 등)은 WAS 코드가 읽는 필드 기준이다(`WriteBackService`, `ResponseDeviceService.error`). 모르면 1번 쿼리로 원문을 먼저 한 줄 본다.
- MySQL `create_date`(KST)와 맞춰 볼 때는 `timestamp`(UTC)에 9시간을 더한다.
- 규모 감각(운영, 2026-08): status 토픽 1시간 약 12만 행, 스캔 약 11MB.
