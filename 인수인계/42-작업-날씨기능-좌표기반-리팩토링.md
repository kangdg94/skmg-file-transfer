## 0. 세 줄 요약

1. 날씨를 **주소별로 저장하던 구조를 좌표(약 1km 격자) 기준 Redis 캐시 + 이력 테이블 1개로** 바꿨다. 주소·기기 시리얼·LLM 지역명은 이제 좌표를 얻는 입력 수단일 뿐이고, OpenWeather 호출은 한 클래스에서만 한다. 기기 MQTT 전문과 관제 대시보드 응답 모양은 바꾸지 않았다.
2. 코드는 dev·stg에 전부 들어가 있다. 운영계는 **스케줄러가 최신(`main` = stg)인 반면 API는 07-16 상태**라, 08-10 이후 보강(캐시 신선도 70분, 기기 날씨 코드 오분류 수정, 외부 API 호출량 계측, 파트너용 날씨 API)이 운영 API에 없다.
3. 남은 것은 전부 운영 작업이다. 환경별 실제 DB 상태 확인, 과거 이력 백필 마무리, 레거시 컬럼·테이블 정리, 행정구역 마스터 교체(2026-07-01 광주·전남 통합과 인천 개편 반영), stg 시험용 강제값 제거, iOS 죽은 코드 삭제가 남았다.

## 1. 배경

### 1-1. 용어

| 용어 | 뜻 |
|---|---|
| **OpenWeather** | 외부 날씨 API 제공자(`api.openweathermap.org`, 2.5 API). 현재 날씨·대기질·일별 예보(최대 16일)·대기질 예보 4종을 쓴다. |
| **Google Geocoding** | 주소 문자열을 좌표로 바꾸는 외부 API(`maps.googleapis.com`). LLM이 임의 지역명을 물었을 때만 쓴다. 호출 건별 과금이다. |
| **location_key** | 좌표를 소수 둘째 자리로 반올림한 문자열 `"{위도}_{경도}"`(예 `37.57_126.98`). 위도 기준 약 1.1km, 경도 기준 약 0.9km 격자다. Redis 키와 이력 테이블 PK의 기준이다. |
| **weather_address** | 기존 행정구역 테이블(시도/시군구/읍면동 + 대표 좌표, 약 3,800행). 예전엔 날씨 저장의 키였고, 지금은 **행정구역 드롭다운 목록 + 주소→좌표 1차 변환용 마스터**로 역할이 줄었다. `district=''` 이고 `street=''` 인 행이 시도 대표 행, `street=''` 인 행이 시군구 대표 행이다. |
| **weather_street / weather_street_dust** | 기존 날씨·미세먼지 이력 테이블(각 3,600만 행 이상, `weather_address.id` 기준). **신규 적재가 중단됐고 아무도 읽지 않는다.** 백필 원본으로만 남아 있다. |
| **outdoor_weather_history** | 신규 실외 날씨 이력 테이블. 날씨·대기질을 한 행으로 합쳐 `location_key` 기준으로 쌓는다. 앱 차트와 컨설팅 리포트가 읽는다. |
| **user_building.x / y** | 사용자 홈 좌표. **x = 위도, y = 경도**(DB 실측 확정: x는 전부 37.x대, y는 126~128대). 컬럼 주석과 반대이므로 주의한다. |
| **SWR (stale-while-revalidate)** | 캐시가 오래됐어도 허용 범위 안이면 일단 그 값을 돌려주고 뒤에서 새로 받아오는 방식. |
| **예열** | 스케줄러 배치가 수집한 결과를 API가 읽는 Redis 캐시에 미리 넣어 두는 것. 예열된 격자는 API가 OpenWeather를 따로 부르지 않는다. |
| **MQTT 날씨 토픽 4종** | 기기(에어봇)가 날씨를 받는 경로. `setOutdoorWI`(제품 등록 시 서버가 push), `getOutdoorWI`(기기가 현재 날씨 요청), `getLLMOutdoorWI`(LLM 발화용 날씨 예보), `getLLMWF`(LLM 발화용 대기질 예보). |
| **HOME_CHANGE** | 홈 주소 변경 시 서버가 연동 기기 전부에 새 주소를 보내는 이벤트(`PUT /app/building/location`, opCommand `CREV0007`). |
| **SGIS** | 통계청 통계지리정보서비스. 행정구역 목록과 대표 좌표를 주는 공공 API. `weather_address` 재생성에 쓴다. |
| **province_abb** | 시도 약칭(서울, 부산, 경기 …). 대시보드 시도별 스냅샷 Redis 키에 쓴다. |

### 1-2. 문제

리팩토링 전에는 **날씨를 `weather_address` 3,800개 행정동마다 매시간 전량 수집**해 `weather_street(_dust)`에 쌓고, 조회할 때마다 주소 문자열을 행정동에 맞추는 휴리스틱(약 300줄)으로 찾았다. 이 구조에서 다음 문제가 확인됐다.

| # | 문제 | 영향 |
|---|---|---|
| 1 | `getOutdoorWI`가 기기가 보낸 주소를 **전부 무시**하고 항상 DB의 홈 주소 날씨를 응답 | 기기 주소는 DB의 사본(`setOutdoorWI`·HOME_CHANGE로 동기화)이라 실사용 영향은 없었지만, 코드가 거짓 의도를 말하고 있었다 |
| 2 | LLM 경로의 geocoding 최근접 선택에서 **위도·경도를 뒤바꿔 비교** | 동명 지역처럼 Google이 후보를 여러 개 줄 때 거리 순위가 사실상 무작위였다 |
| 3 | 스케줄러 `@Async`가 자기 호출이라 **무효**, 3,800건 외부 호출 내내 트랜잭션 점유 | 스레드 풀 설정이 아무 효과가 없었고, OpenWeather 지연 시 DB 커넥션 풀 고갈 위험 |
| 4 | geocoding 결과를 **캐시하지 않음** | 같은 지역명도 매번 과금. 실측 월 청구 약 9만 원 |
| 5 | 최신값 조회가 매번 `GROUP BY address_id + MAX(create_date)` 전체 스캔 | 테이블이 커질수록 느려짐 |
| 6 | 공유 `RestTemplate`에 **읽기 타임아웃이 설정되지 않음**(주석과 달리 connect 타임아웃만) | 외부 응답 지연 시 스레드가 무한 대기. 이 빈은 OASYS·콜센터 등 다른 도메인과 공유한다 |
| 7 | 오류를 `"GeoCodingFalse"` 같은 **문자열 센티널**로 표현하고 호출부가 문자열 비교로 분기 | 오타·변경에 조용히 깨짐 |
| 8 | 신설 행정동이 `weather_address`에 없으면 날씨 수집·조회 자체가 안 됨 | 2년간 신설 지명이 반영되지 않은 상태였다(§8-3) |

### 1-3. 목표

- 날씨 저장·캐시 키는 **좌표 격자(`location_key`) 하나**로 통일한다. 주소·시리얼·LLM 지역명은 좌표를 얻는 입력 수단으로 격하한다.
- **OpenWeather 호출은 `OpenWeatherClient` 한 곳, 날씨 조회는 `WeatherQueryService` 한 곳**에서만 한다.
- 현재값·예보는 휘발성이라 **Redis**에 둔다(MySQL hot-row UPSERT의 redo log 부하를 피한다). MySQL 신규 테이블은 append-only 이력 **1개**뿐이다.
- 수집 대상은 "연동 기기 홈 좌표 + 시도 대표 좌표"로 좁힌다.
- **기기 MQTT 전문, 관제 대시보드 응답의 필드 모양은 바꾸지 않는다.**
- 비용 절감은 부수 효과다. 실측(07-09) 결과 활성 격자는 2,748개로 기존 3,800개 대비 약 28% 감소에 그쳤다(월 약 547만 → 396만 콜). 리팩토링의 근거는 위 구조 문제들이다.

범위 밖: LLM 서버(`backend-cloud-llm-lambda`)의 날씨 컨텍스트 조립 로직은 다루지 않았다.

조회 정책(`WeatherQueryService.get`):
1. 입력 → `LocationResolver` → `location_key`. `weather:active` ZSET에 현재 시각으로 기록.
2. Redis에 값이 없으면 OpenWeather를 **동기 호출**해 저장 후 반환.
3. 값의 나이(`fetchedAt` 기준)가 fresh 기준을 넘었으면 **기존 값을 즉시 반환**하고 뒤에서 갱신.
4. Redis TTL(stale 상한)이 지나면 키가 사라지므로 2번으로 간다.
5. OpenWeather 실패는 예외로 올린다. 문자열 센티널은 없앴다.

### 3-3. 데이터

**MySQL — `outdoor_weather_history`** (DDL 전문은 부록 B)

| 항목 | 내용 |
|---|---|
| PK | `(location_key, collected_at)` |
| 파티션 | `collected_at` 기준 월 단위 `p202510` ~ `p202712` + `p_max`. 백필 데이터가 2025-10-31부터라 과거 파티션이 먼저 있어야 한다 |
| 한 행 = | 한 격자·한 수집 시각의 날씨 + 대기질. 둘 중 하나가 실패하면 그쪽 컬럼만 NULL |
| 컬럼 | `observed_weather_at`, `observed_air_quality_at`(두 API 관측 시각이 달라 따로 둔다), `temperature`, `humidity`, `pm10`, `pm25`, `pm10_level`, `pm25_level`(0~3 숫자), `aqi`(1~5), `source` |
| 읽는 곳 | 앱 `daily/airbot`·`daily/aqm`(pm25·pm10·습도·기온 4개), 컨설팅 리포트(기온·습도·pm10_level·pm25_level), 파트너 API |
| 조회 기준 | 전부 `collected_at`(적재 시각). 처음엔 관측 시각으로 파티션을 잡았다가 조회가 전부 적재 시각 기준이라 프루닝이 안 먹어 재설계했다 |
| 실시간 행과 백필 행의 시각 | 실시간은 배치 실행 시각 그대로(예 `09:35:12`), 백필은 정시로 절삭(`09:00:00`). 앱 쿼리는 30분 눈금마다 "그 시각 이전 최신 행"을 집으므로 섞여도 동작한다 |
| 보존 기간 | **미확정.** 설계 시 예시는 2년. 오래된 파티션 DROP 절차는 아직 없다 |

**MySQL — `external_api_call_count`**: PK `(called_minute, app, vendor, endpoint)`. `app`은 `API`/`SCHEDULER`, `vendor`는 `OPENWEATHER`/`GOOGLE_GEOCODING`. `called_minute`은 **KST 분 단위**(코드에서 `Asia/Seoul` 고정). 요청 경로에서 DB를 건드리지 않고 인스턴스 메모리에 모았다가 60초마다 가산 UPSERT한다. 인스턴스 여러 대가 같은 PK에 더하는 구조라 리더 선출이 필요 없다.

**Redis** (기존 인스턴스 공용, `weather:` 네임스페이스로만 분리)

| 키 | 값 | fresh 기준 | Redis TTL(stale 상한) | 쓰는 곳 |

| `weather:cur:{location_key}` | `{"fetchedAt": epoch ms, "data": OpenWeather 원문}` | **70분** (운영 `main`은 30분) | 2시간 | API 온디맨드 + 스케줄러 예열 |

| `GET /api/app/device/airQuality/daily/airbot`, `daily/aqm` | `outdoor_weather_history` (홈 좌표 → `location_key`) | 없음. 단, **백필되지 않은 과거 날짜는 외기 그래프가 비어 나온다** |
| 컨설팅 리포트 외기 그래프 | `outdoor_weather_history` | 위와 같음 |

### 4-2. 신설: 행정구역 조회

| 신규 | 구 경로 (deprecated 어댑터, 응답 동일) |
|---|---|
| `GET /api/regions/provinces` | `GET /api/dashboard/weather/province` |

### 4-3. 삭제 (하드 삭제 완료)

`POST /api/weather`, `/api/weather/dust`, `/api/app/weather`, `/api/app/weather/dust`, `/api/weather/select`, `/api/weather/finalAddressSelect`, `/api/weather/airPollutionForecast`, `/api/weather/oneCallApiCurrent`

삭제 근거: iOS·Android·관제 프론트 세 저장소의 `develop` 브랜치에서 경로 문자열을 전수 검색해 호출부 0건(07-09). 운영 access log 확인은 하지 않기로 결정했다. 삭제 후 누가 호출하면 404가 난다.

### 4-4. 파트너용 내부 엔드포인트 (09-03, dev·stg만)

```http
GET /internal/v1/openapi/buildings/{buildingId}/weather?userId=...&include=current,daily&days=7
```

- `skix-openapi` 전용. 파트너가 직접 부르지 않는다. `/internal/v1/openapi/**` 전체에 공유키 인터셉터가 걸린다.
- OpenWeather 원문을 그대로 넘기지 않고 제공자 중립 모델로 정규화한다. 날씨 상태 enum은 기기용 `DeviceWeatherCondition`과 **분리**했다(외부 스펙 enum이라 값을 늘리면 코드 생성 클라이언트가 깨진다).
- 현재 날씨만 캐시 나이 10분 상한. 넘으면 동기 재조회하고, 실패하면 stale을 감추지 않고 503. 파트너 용도가 "비 오면 실외 로봇 복귀"라 한 시간 전 "맑음"을 정상으로 주면 안 되기 때문이다.
- 오류: 400 `INVALID_REQUEST`(days 1~16 밖), 404(홈 없음), 422(홈 좌표가 빈 값·비숫자·범위 밖), 503(재조회 실패).
- 인가는 `OpenApiBuildingService`와 같은 규칙. 남의 홈 좌표 날씨를 조회하면 그 자체가 위치 노출이다.

## 5. 되돌리면 안 되는 설계 결정

"더 깔끔해 보이게 고치면 사고가 나는" 것만 남겼다.

| # | 결정 | 바꾸면 생기는 일 |
|---|---|---|
| 1 | **`location_key` 포맷은 세 곳(API `LocationKeyUtil`, 스케줄러 `LocationKeyUtil`, 백필 SQL `FORMAT(x,2)`)이 완전히 같아야 한다.** 격자 크기를 바꾸려면 세 곳을 한 번에 바꾸고 이력을 재키잉해야 한다 | 한 곳만 바꾸면 쓰는 쪽과 읽는 쪽 키가 달라져 앱 외기 그래프가 조용히 비고, Redis 예열이 무효가 된다. 오류는 나지 않는다 |
| 2 | **`x` = 위도, `y` = 경도.** 새 코드는 `lat`/`lon` 이름만 쓰고 `x`/`y` 해석은 `LocationResolver`와 매퍼 밖으로 새지 않게 했다 | 컬럼 주석이 반대로 적혀 있어 "주석대로 고치는" 실수가 가장 흔하다. 뒤집으면 전 기기 날씨가 엉뚱한 곳(또는 OpenWeather 400 `wrong latitude`)이 된다. 리팩토링 전 geocoding 버그가 바로 이것이었다 |
| 3 | **현재 날씨·대기질의 fresh 기준(70분)은 배치의 같은 키 재수집 간격(60분 + 실행 순서 변동)보다 커야 한다.** 배치가 격자 순서를 `location_key`로 정렬하는 것도 재수집 간격을 고정하려는 것이다 | 짧게 잡으면 배치가 채운 값이 곧 stale로 판정되어 API가 OpenWeather를 다시 부른다. 운영 `main`이 지금 이 상태다(30분). 운영 활성 격자가 5,000개를 넘어 배치가 10분대로 길어지면 재검토한다 |
| 4 | **Redis 캐시 키 prefix·TTL·봉투 형식(`{"fetchedAt", "data"}`)은 API `WeatherCacheType`/`WeatherCacheRefresher`와 스케줄러 `WeatherApiCacheWriter`가 동일해야 한다.** 스케줄러는 파싱 검증을 통과한 응답만 캐시한다 | 형식이 어긋나면 API가 `envelope.getJSONObject("data")`에서 예외를 낸다. 한쪽만 TTL을 바꾸면 예열 효과가 사라진다 |
| 5 | **geocoding 캐시에는 Google 후보 좌표 목록만 넣고, 최근접 선택은 매 호출 그 시리얼의 홈 기준으로 다시 계산한다** | 최종 좌표를 캐시하면 동명 지역("중구" 등)을 A 기기가 먼저 조회한 결과를 B 기기도 30일간 받는다. 외부 리뷰에서 실제로 잡힌 버그다 |
| 6 | **`getOutdoorWI`는 요청 주소를 쓰지 않고 DB 홈 주소 기준으로 응답한다** | 기기 주소는 DB의 동기화 사본이라 존중해도 정상 케이스에선 같고, 동기화가 실패한 경우엔 DB가 더 정확하다. "요청 주소를 존중하도록 개선"하면 오히려 나빠진다. 다른 지역 날씨는 `getLLMOutdoorWI`가 담당한다 |
| 7 | **기기 날씨 코드는 OpenWeather condition id로 판정한다. `description` 문자열 비교를 쓰지 않는다.** `lang` 파라미터도 붙이지 않는다 | `description`은 `lang`과 엔드포인트에 따라 언어가 바뀐다(`forecast/daily`는 `lang`을 무시하고 항상 영문). 현재 날씨에 `lang=ko`가 붙는 순간 문자열 분기가 전부 빗나가 **전 기기가 빈 코드를 받는다.** 실제로 `lang=ko` 때문에 "예보가 한글"이라고 오해해 잘못된 코드가 나간 적이 있다 |
| 8 | **수집 대상은 매 사이클 `device`·`user_building`에서 새로 계산한다.** 별도 "활성 위치" 테이블을 두지 않는다. `weather:active` ZSET은 수집 대상과 무관하다 | 앱이 조회할 수 있는 키는 "지금 연동된 기기의 홈 좌표"뿐이라, 매번 재계산하면 정확히 그만큼 수집된다. 신규 연동 기기는 다음 사이클(최대 1시간)부터 자동 포함된다. 별도 목록을 두면 동기화가 새 실패 지점이 된다 |
| 9 | **OpenWeather 호출은 `OpenWeatherClient`(API)·`WeatherFetchExecutor`(스케줄러)에서만.** URL은 `UriComponentsBuilder`로 조립한다 | 흩어지면 타임아웃·계측·한도 관리가 다시 흩어진다. 문자열 연결은 입력에 `{`·`}`가 있으면 URI 템플릿으로 해석된다 |
| 10 | 신설 클래스 이름에 **`Location*`을 쓰지 않는다** (`Region*` 사용) | "location"이 코드베이스에서 기기 물리 위치를 뜻해 `device.location` 패키지에 동명 빈이 있다. 07-15 개발계에서 `ConflictingBeanDefinitionException`으로 기동 실패했다 |
| 11 | MyBatis XML에서 `<>` 대신 `!=` | `<>`가 XML 태그로 해석되어 `sqlSessionFactory` 생성 실패 → **모든 매퍼가 함께 죽는다**(07-15 개발계 실증) |
| 12 | **파괴적 DB 작업(컬럼 DROP, 테이블 교체)은 새 빌드가 그 환경에 배포된 뒤에만 한다** | "코드 참조 0건"은 브랜치 기준이지 떠 있는 빌드 기준이 아니다. 07-15 개발계에서 구 빌드가 떠 있는 채로 `weather_address_id`를 지워 `Unknown column`이 났다 |
| 13 | **`weather_address` 전면 교체는 백필이 끝난 뒤에만 한다** | 교체하면 id가 전부 새로 발급된다. 백필 프로시저는 `weather_street.address_id` → `weather_address.id`로 좌표를 얻으므로, 교체 후 백필하면 **엉뚱한 좌표로 이력이 쌓인다.** 부득이하면 백필의 조인 대상을 `weather_address_backup_*`로 바꾼다 |
| 14 | **백필은 한 세션에서 순차로 실행한다** (`backfill_outdoor_weather_history` 통합 프로시저) | 스크립트 주석은 "날씨·대기질 두 세션 병렬"을 권하지만, 07-15 실측에서 두 프로시저가 같은 PK 행을 동시에 UPSERT해 **락 대기 1205 오류**가 났다. 주석이 낡은 것이다 |
| 15 | **호출량 계측은 요청 경로에서 DB를 쓰지 않는다** (메모리 집계 → 60초 flush 전용 스레드) | LLM 예보 호출이 쓰기 트랜잭션 안이라 롤백 시 계측도 롤백되고, 분 버킷 행 잠금이 외부 HTTP 대기 동안 유지되어 동시 호출이 직렬화된다. readOnly 트랜잭션은 읽기 복제본으로 가서 INSERT가 실패할 수도 있다. 또 API에 `@EnableScheduling`을 켜지 않는다 — 켜면 이후 추가되는 업무성 `@Scheduled`가 인스턴스 수(4대)만큼 중복 실행된다 |
| 16 | 공유 `RestTemplate`에 connect·response 타임아웃을 명시했다 | 날씨 외 OASYS·콜센터 호출에도 적용된다. 되돌리면 외부 응답 지연 시 스레드가 무한 대기한다 |

## 7. 배포 방법

### 7-1. 순서와 이유 (expand → migrate → contract)

배포 당일 경로에는 되돌릴 수 없는 DB 작업이 없다. 전부 "추가"라 문제가 생기면 구 jar 재배포로 완전히 복귀한다. 지우는 작업은 안정화 후로 분리했다.

```
[사전 · 앱 영향 없음]
 1. outdoor_weather_history 생성 (부록 B, 파티션 포함)
 2. external_api_call_count 생성 (§3-3)
 3. 백필 프로시저 생성 (부록 C) → 최신 14일 백필 (한 세션 순차, 7일 이하 단위)

[배포 당일 · 같은 배포 창에서 연달아]
 4. backend-scheduler-main
 5. backend-api-main          ← 반드시 4와 같은 창
 6. frontend-web-backoffice   ← 반드시 5 이후

[안정화 1~2주]
 7. 나머지 백필: 최신 → 과거 역순 7일씩, 2025-10-31까지 (약 55회)
 8. OpenWeather 분당 사용량, 시간당 적재 건수, 앱 외기 그래프 모니터링

[안정화 확인 후 · 파괴적 작업, 순서 중요]
 9. drop_weather_legacy_columns.sql (부록 D)     ← 새 API 빌드(e5bdb01b 이후)가 떠 있어야 함
10. weather_address SGIS 교체 (부록 E)           ← 백필 완료 + 9 이후
11. weather_street / weather_street_dust 제거, DB 함수 2개 DROP ← 백필 건수 대사 후 (DBA)
```

| 순서 제약 | 어기면 |
|---|---|
| 1·3 → 5 | 앱 `daily/*`와 컨설팅 리포트가 테이블 없음 오류 또는 빈 그래프 |
| 4와 5를 같은 창에 | 새 스케줄러는 `weather_street`에 쓰지 않는다. 구 API는 `weather_street`를 읽으므로 둘 사이 간격만큼 구 API의 날씨가 낡는다 |
| 5 → 6 | 구 백엔드에는 `/api/regions/*`가 없어 지역 드롭다운 화면 5종(대시보드 3종, 기기·제품 검색, 제품 등록)이 즉시 404. 프론트에는 구 URL 폴백이 없다 |
| 5 → 9 | 구 빌드가 `weather_address_id`·`MATCH(address)`를 참조해 `Unknown column` |
| 7 완료 → 10 | §5의 13번 |
| 9 → 10 | 교체 후엔 `weather_address_id` 백업의 의미가 사라진다(가리키는 id가 새로 발급됨) |

배포 창은 매시 41~50분(운영 기준, 구 배치 종료 직후)으로 잡았었다. 운영 cron이 `:35`이므로 배치가 끝난 뒤 시작하면 데이터 공백이 최소다.

**현재 운영에서 남은 순서**: 스케줄러는 이미 최신 브랜치다. 다음 운영 API 승격(`stg` → `main`)에는 날씨 후속 5건이 함께 들어가며, 그 전에 운영 DB에 `external_api_call_count`가 있어야 API 계측 flush가 오류를 내지 않는다(없어도 요청 처리엔 영향 없음).

### 7-2. 배포 후 검증

로그(CloudWatch):

| 대상 | 키워드 | 기대 |
|---|---|---|
| 스케줄러 | `collectOutdoorData work time` | 운영 약 5분 30초 |
| 스케줄러 | `outdoor_weather_history 적재 완료 - 조회 N건, 대상 위치 M개, 캐시 예열 weather a성공/b실패, airQuality c성공/d실패` | 실패 0에 가까움 |
| 스케줄러 | `outdoor_weather_history 수집 실패 - x: , y:` | 없음. 있으면 해당 좌표 확인 |
| API | `deprecated endpoint 호출` | 운영 프론트 승격 전엔 있음, 후엔 사라져야 함 |
| API | `Weather condition id not mapped to a device code` | 돌풍·토네이도 때만 |
| API | `Device weather condition overridden` | **stg에서만.** dev·prd에서 보이면 설정 오류 |

DB:

```sql
-- 방금 정시 적재 건수 (운영 기대 ≈ 활성 격자 수 + 17)
SELECT COUNT(*) FROM outdoor_weather_history
WHERE collected_at >= DATE_FORMAT(NOW(), '%Y-%m-%d %H:00:00');

-- 부분 실패 비율
SELECT SUM(temperature IS NULL) AS weather_null, SUM(pm10 IS NULL) AS aq_null, COUNT(*) AS total
FROM outdoor_weather_history
WHERE collected_at >= NOW() - INTERVAL 1 DAY;

-- 분당 외부 호출량 (배치 창에서 1,000 근처, 전체 1,600/분 이내가 목표)
SELECT called_minute, app, vendor, SUM(call_count) AS calls
FROM external_api_call_count
WHERE called_minute >= NOW() - INTERVAL 2 HOUR
GROUP BY called_minute, app, vendor ORDER BY calls DESC LIMIT 20;
```

주의: `outdoor_weather_history.collected_at`은 스케줄러 JVM의 `LocalDateTime.now()`로 찍히고, 백필 행은 원본 `create_date`를 쓴다. 스케줄러 JVM 시간대는 확인하지 못했다(§8-1의 4번). 위 첫 쿼리의 `NOW()`는 DB 시간대라 두 시간대가 다르면 0건으로 보일 수 있다.

API·Redis:

```bash
# 지역 목록 (관제 Admin JWT 필요)

```

기능 확인: 관제 대시보드 3종 날씨·대기질, 지역 드롭다운 5개 화면, 앱 에어봇·AQM 외기 그래프(백필된 날짜), 기기 LLM에 "부산 날씨 어때" 류 질문 → Redis `weather:fc:*` 생성.

## 9. 운영 중 자주 만날 상황

| 상황 | 확인 방법 |
|---|---|
| "앱 외기 그래프가 비어 있어요" | ① 그 날짜가 백필됐는지: `SELECT EXISTS(SELECT 1 FROM outdoor_weather_history WHERE collected_at >= '<날짜>' AND collected_at < '<날짜+1>') AS filled;` ② 기기의 홈 좌표가 있는지: `SELECT ub.x, ub.y FROM device d JOIN user_building ub ON ub.id = d.building_id WHERE d.serial = '<serial>';` ③ 그 격자 이력이 있는지: `location_key = CONCAT(FORMAT(x,2),'_',FORMAT(y,2))` 로 조회. 이사한 경우 옛 위치 이력은 새 위치에서 보이지 않는다(리팩토링 전과 같은 특성) |
| 신규 연동 기기의 과거 외기 이력이 없다 | 정상. 연동 다음 사이클(최대 1시간)부터 쌓인다. 같은 격자에 다른 기기가 있었으면 그 이력이 바로 보인다 |
| 기기가 날씨를 못 받는다 (`getOutdoorWI` 무응답) | API 로그 `Device weather location could not be resolved: reason=findCoordinateBySerialFalse` → 홈 좌표 없음. `Device weather lookup failed` → OpenWeather 호출 실패(키·한도·네트워크) |
| 기기 날씨 표시가 실제와 다르다 | stg면 먼저 `weather.override`에 그 시리얼이 있는지. 운영이면 `main`이 아직 구 문자열 판정이라 804(가장 흐림)가 "흐림"으로, 520·522·531 소나기가 비로, smoke·fog·dust가 빈 값으로 나간다(§2-1) |
| LLM이 "맑겠습니다"라고 하는데 기기는 "흐림" | stg 강제값이 한쪽만 적용된 경우다. 강제값은 두 경로(코드·예보 원문) 모두 덮도록 만들었으니 운영이면 실제 예보와 현재값 차이다 |
| 대시보드 시도별 미세먼지가 전부 비어 있다 | `weather:province:*` 키는 TTL 3시간이라 **배치가 3시간 이상 멈추면 사라진다.** 스케줄러 로그 `collectOutdoorData` 확인 |
| 관제 지역 드롭다운에 새 행정구역이 없다 | §8-3의 15번. 버그 아님 |
| OpenWeather 429(한도 초과) | `external_api_call_count`로 분당 호출량 확인. 배치 창과 겹치는지, 같은 키를 쓰는 다른 환경 cron과 겹치는지(`:35`/`:43`/`:51`) |
| Google geocoding 비용이 늘었다 | `vendor='GOOGLE_GEOCODING'` 분당 호출. `weather:geo:*`가 사라졌는지(Redis 재기동·flush) |
| 스케줄러 `wrong latitude` 400 | 홈 좌표 위경도가 뒤집힌 행. 수집 쿼리에 범위 필터가 있어 대부분 걸러지지만, 한국 밖 좌표가 된 경우는 통과한다. `user_building` 원본 수정 |

DROP PROCEDURE IF EXISTS backfill_outdoor_weather_history_weather$$

CREATE PROCEDURE backfill_outdoor_weather_history_weather(
    IN p_start_date DATE,
    IN p_days INT
)
BEGIN
    DECLARE v_end_date DATE;
    DECLARE v_id_start BIGINT;
    DECLARE v_id_end BIGINT;

    SET v_end_date = DATE_ADD(p_start_date, INTERVAL p_days DAY);

    SELECT id INTO v_id_start
    FROM weather_street
    WHERE create_date >= p_start_date
    ORDER BY create_date ASC LIMIT 1;

    SELECT id INTO v_id_end
    FROM weather_street
    WHERE create_date < v_end_date
    ORDER BY create_date DESC LIMIT 1;

    INSERT INTO outdoor_weather_history (location_key, collected_at, observed_weather_at, temperature, humidity, source)
    SELECT
        CONCAT(FORMAT(wa.x, 2), '_', FORMAT(wa.y, 2)) AS location_key,
        DATE_FORMAT(ws.create_date, '%Y-%m-%d %H:00:00') AS collected_at,
        ws.report_date AS observed_weather_at,
        CAST(ws.temp AS DECIMAL(5,2)),
        CAST(ws.humidity AS UNSIGNED),
        'OPENWEATHER'
    FROM weather_street ws FORCE INDEX (PRIMARY)
    JOIN weather_address wa ON wa.id = ws.address_id
    WHERE ws.id BETWEEN IFNULL(v_id_start, 0) - 5000 AND IFNULL(v_id_end, 0) + 5000
      AND ws.create_date >= p_start_date AND ws.create_date < v_end_date
      AND ws.report_date IS NOT NULL
      AND ws.temp IS NOT NULL AND ws.temp != ''
      AND wa.x IS NOT NULL AND wa.x != '' AND wa.y IS NOT NULL AND wa.y != ''
    ON DUPLICATE KEY UPDATE
        observed_weather_at = VALUES(observed_weather_at),
        temperature = VALUES(temperature),
        humidity = VALUES(humidity);

    SELECT p_start_date AS batch_start, v_end_date AS batch_end, ROW_COUNT() AS rows_affected;
END$$

CREATE PROCEDURE backfill_outdoor_weather_history_air_quality(
    IN p_start_date DATE,
    IN p_days INT
)
BEGIN
    DECLARE v_end_date DATE;
    DECLARE v_id_start BIGINT;
    DECLARE v_id_end BIGINT;

    SET v_end_date = DATE_ADD(p_start_date, INTERVAL p_days DAY);

    SELECT id INTO v_id_start
    FROM weather_street_dust
    WHERE create_date >= p_start_date
    ORDER BY create_date ASC LIMIT 1;

    SELECT id INTO v_id_end
    FROM weather_street_dust
    WHERE create_date < v_end_date
    ORDER BY create_date DESC LIMIT 1;

    -- pm10_level/pm25_level 은 원본 텍스트 등급 컬럼을 복사하지 않고, 원시 pm10/pm25 값으로
    -- WeatherKoreanModule.pm10Level/pm25Level 과 동일한 구간으로 재계산한다 (0~3, 좋음/보통/나쁨/매우나쁨).
    INSERT INTO outdoor_weather_history (location_key, collected_at, observed_air_quality_at, pm10, pm25, pm10_level, pm25_level, aqi, source)
    SELECT
        CONCAT(FORMAT(wa.x, 2), '_', FORMAT(wa.y, 2)) AS location_key,
        DATE_FORMAT(wsd.create_date, '%Y-%m-%d %H:00:00') AS collected_at,
        wsd.report_date AS observed_air_quality_at,
        ROUND(CAST(wsd.pm10 AS DECIMAL(10,2))),
        ROUND(CAST(wsd.pm25 AS DECIMAL(10,2))),
        CASE WHEN CAST(wsd.pm10 AS DECIMAL(10,2)) <= 50 THEN 0
             WHEN CAST(wsd.pm10 AS DECIMAL(10,2)) <= 100 THEN 1
             WHEN CAST(wsd.pm10 AS DECIMAL(10,2)) <= 200 THEN 2
             ELSE 3 END,
        CASE WHEN CAST(wsd.pm25 AS DECIMAL(10,2)) <= 25 THEN 0
             WHEN CAST(wsd.pm25 AS DECIMAL(10,2)) <= 50 THEN 1
             WHEN CAST(wsd.pm25 AS DECIMAL(10,2)) <= 75 THEN 2
             ELSE 3 END,
        CASE WHEN wsd.aqi_int_string IS NULL OR wsd.aqi_int_string = '' THEN NULL
             ELSE CAST(wsd.aqi_int_string AS UNSIGNED) END,
        'OPENWEATHER'
    FROM weather_street_dust wsd FORCE INDEX (PRIMARY)
    JOIN weather_address wa ON wa.id = wsd.address_id
    WHERE wsd.id BETWEEN IFNULL(v_id_start, 0) - 5000 AND IFNULL(v_id_end, 0) + 5000
      AND wsd.create_date >= p_start_date AND wsd.create_date < v_end_date
      AND wsd.report_date IS NOT NULL
      AND wsd.pm10 IS NOT NULL AND wsd.pm10 != ''
      AND wsd.pm25 IS NOT NULL AND wsd.pm25 != ''
      AND wa.x IS NOT NULL AND wa.x != '' AND wa.y IS NOT NULL AND wa.y != ''
    ON DUPLICATE KEY UPDATE
        observed_air_quality_at = VALUES(observed_air_quality_at),
        pm10 = VALUES(pm10),
        pm25 = VALUES(pm25),
        pm10_level = VALUES(pm10_level),
        pm25_level = VALUES(pm25_level),
        aqi = VALUES(aqi);

    SELECT p_start_date AS batch_start, v_end_date AS batch_end, ROW_COUNT() AS rows_affected;
END$$

def get_access_token(consumer_key: str, consumer_secret: str) -> str:
    resp = requests.get(
        f"{BASE_URL}/auth/authentication.json",
        params={"consumer_key": consumer_key, "consumer_secret": consumer_secret},
        timeout=10,
    )
    resp.raise_for_status()
    body = resp.json()
    if body.get("errCd") not in (0, "0", None):
        raise RuntimeError(f"accessToken 발급 실패: {body}")
    return body["result"]["accessToken"]


class TokenManager:
    def __init__(self, consumer_key: str, consumer_secret: str):
        self.consumer_key = consumer_key
        self.consumer_secret = consumer_secret
        self.token = get_access_token(consumer_key, consumer_secret)
        self.issued_at = time.time()

    def get(self) -> str:
        # 4시간 만료 - 여유 있게 3.5시간마다 재발급
        if time.time() - self.issued_at > 3.5 * 3600:
            self.token = get_access_token(self.consumer_key, self.consumer_secret)
            self.issued_at = time.time()
        return self.token


def fetch_stage(token_mgr: TokenManager, cd: str = "") -> list:
    params = {"accessToken": token_mgr.get(), "pg_yn": "0"}
    if cd:
        params["cd"] = cd
    resp = requests.get(f"{BASE_URL}/addr/stage.json", params=params, timeout=10)
    resp.raise_for_status()
    body = resp.json()
    if body.get("errCd") not in (0, "0", None):
        raise RuntimeError(f"stage 조회 실패(cd={cd}): {body}")
    return body.get("result", [])

    name = item.get("addr_name")
    cd = item.get("cd")
    lat, lon = utmk_to_latlon(item.get("x_coor"), item.get("y_coor"))
    return cd, name, lat, lon

def sql_escape(value) -> str:
    if value is None:
        return "NULL"
    return "'" + str(value).replace("'", "''") + "'"


def build_insert_statements(rows: list) -> list:
    statements = []
    for province, province_abb, province_acr, district, street, x, y in rows:

            f"{sql_escape(district)}, {sql_escape(street)}, {sql_escape(x)}, {sql_escape(y)});"
        )
    return statements

        "--",
        "-- build_weather_address_from_sgis.py 로 자동 생성됨. 실행 순서:",
        "--   0) FK 제거  1) 백업 생성  2) TRUNCATE  3) 재적재  4) 건수 확인  5) 최근접 조회 확인",
        "-- TRUNCATE는 MySQL에서 암묵적 COMMIT을 유발해 트랜잭션으로 묶어도 되돌릴 수 없음 -",
        "-- 반드시 백업 테이블이 먼저 만들어진 뒤 진행되는 순서 그대로 실행할 것.",
        "--",
        "-- 전제조건 (순서 중요):",
        "--   1. outdoor_weather_history 백필 완료 - 백필이 weather_address를 구 id로 조인하므로",
        "--      교체(id 전면 재발급) 후 백필하면 좌표 오염. 남았으면 조인 대상을 backup 테이블로 변경.",
        "--   2. user_building.weather_address_id 컬럼 삭제 완료 (drop_weather_legacy_columns.sql)",
        "-- (weather_street/weather_street_dust 폐기 완료 후 재실행하는 경우 0)의 FK 제거는",
        "--  이미 없어서 에러가 나므로 해당 줄만 건너뛸 것)",
        "-- ============================================================================",
        "",
        "-- 0) 폐기 예정 테이블의 FK 제거 - weather_address.id 참조 FK가 있으면 TRUNCATE가 에러 1701로 거부됨",
        "ALTER TABLE weather_street DROP FOREIGN KEY weather_street_weather_address__FK;",
        "ALTER TABLE weather_street_dust DROP FOREIGN KEY weather_street_dust_weather_address__FK;",
        "",
        "-- FK 복구용 DDL (전체 롤백 시에만 - weather_address를 백업에서 되돌린 뒤에만 성공.",
        "-- 새 id 상태에서는 기존 address_id들이 검증에 걸려 ADD 실패)",
        "-- ALTER TABLE weather_street ADD CONSTRAINT weather_street_weather_address__FK",
        "--     FOREIGN KEY (address_id) REFERENCES weather_address (id);",
        "-- ALTER TABLE weather_street_dust ADD CONSTRAINT weather_street_dust_weather_address__FK",
        "--     FOREIGN KEY (address_id) REFERENCES weather_address (id);",
        "",
        "-- 1) 백업 (되돌리기용)",
        f"CREATE TABLE weather_address_backup_{backup_suffix} AS SELECT * FROM weather_address;",
        "",
        "-- 2) 전체 삭제",
        "TRUNCATE TABLE weather_address;",
        "",
        f"-- 3) 재적재 (SGIS 기반, {len(rows)}행)",
    ]
    parts.extend(build_insert_statements(rows))
    parts.extend([
        "",
        f"-- 4) 건수 확인 - {len(rows)}이어야 정상",
        "SELECT COUNT(*) AS total_rows FROM weather_address;",
        "SELECT COUNT(DISTINCT province_abb) AS province_count FROM weather_address WHERE district='' AND street='';",
        "",
        "-- 5) 좌표 최근접 조회 동작 확인 - 서울시청 좌표는 시도 대표 행 좌표와 동일하므로 대표 행(서울특별시, district/street 빈값)이 나오는 게 정상 (질문 입도 보존 검증)",
        "SELECT province, province_abb, district, street FROM weather_address",
        "WHERE x IS NOT NULL AND x != '' AND y IS NOT NULL AND y != ''",
        "ORDER BY ST_Distance_Sphere(",
        "    POINT(CAST(y AS DECIMAL(11,7)), CAST(x AS DECIMAL(10,7))),",
        "    POINT(126.9783, 37.5667))",
        "LIMIT 1;",
    ])
    return "\n".join(parts)


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--key", required=True, help="SGIS consumer_key (서비스 ID)")
    parser.add_argument("--secret", required=True, help="SGIS consumer_secret (보안 Key)")
    parser.add_argument("--out", default=None, help="출력 파일명 (기본: weather_address_replace_YYYYMMDD.sql)")
    parser.add_argument(
        "--debug-raw",
        action="store_true",
        help="STEP 0: 시도 목록 raw JSON만 찍어보고 종료(필드명/신설 지역 반영 여부 확인용)",
    )
    args = parser.parse_args()

    token_mgr = TokenManager(args.key, args.secret)

    provinces = fetch_stage(token_mgr)

    if args.debug_raw:
        print("=== 시도 목록 raw 응답 (필드명/신설 지역 반영 여부 확인용) ===")
        print(json.dumps(provinces, ensure_ascii=False, indent=2))
        sys.exit(0)

    rows = []
    for p_item in provinces:
        p_cd, p_name, p_lat, p_lon = parse_item(p_item)
        if not p_name:
            continue
        p_abb, p_acr = province_abb_acr(p_name)

        # province 대표 행 (district='' street='')
        rows.append((p_name, p_abb, p_acr, "", "", p_lat, p_lon))
        print(f"[province] {p_name}")

        districts = fetch_stage(token_mgr, cd=p_cd)
        for d_item in districts:
            d_cd, d_name, d_lat, d_lon = parse_item(d_item)
            if not d_name:
                continue

            # district 대표 행 (street='')
            rows.append((p_name, p_abb, p_acr, d_name, "", d_lat, d_lon))

            streets = fetch_stage(token_mgr, cd=d_cd)
            for s_item in streets:
                _, s_name, s_lat, s_lon = parse_item(s_item)
                if not s_name:
                    continue
                rows.append((p_name, p_abb, p_acr, d_name, s_name, s_lat, s_lon))

            print(f"  [district] {d_name} - {len(streets)}개 읍면동")

    today = datetime.date.today().strftime("%Y%m%d")
    out_path = args.out or f"weather_address_replace_{today}.sql"

    script = build_replace_script(rows, backup_suffix=today)
    with open(out_path, "w", encoding="utf-8") as f:
        f.write(script)

    print(f"\n총 {len(rows)}행 -> {out_path} (백업+TRUNCATE+INSERT+확인 쿼리 포함, 실행 준비 완료)")


if __name__ == "__main__":
    main()
